# source_files — исходные материалы от организаторов/заказчика

Сырые материалы, полученные по задаче №3 «Билайн Бизнес» (хакатон «Лидеры цифровой
трансформации»). Ничего в этой папке не редактировалось руками команды — это входные
данные "как есть".

## Файлы

### `Билайн Бизнес.pdf`
Официальное техническое задание (2026 г.). Описывает кейс целиком: контекст задачи,
обязательный функционал MVP, три группы обязательных ограничений (квалификация, время,
ресурс), формат входных/выходных данных, справочники (навыки, типы транспорта,
приоритеты), уровни реализации (обязательный MVP / доп. возможности), программно-
аппаратные требования, требования к презентации, документации, критерии оценки и вес
каждого критерия. **Это первоисточник** — при любом противоречии с расшифровкой Q&A или
обсуждениями команды именно ТЗ имеет приоритет, если явно не сказано иное представителем
заказчика.

### `transcript_clean.txt`
Автоматическая (Whisper) расшифровка сессии вопросов и ответов с постановщиком задачи
(Даниил Тхор, владелец продукта BeKeeper Beeline) и ментором (Григорий Ситников), а также
архитектором BeKeeper (Матвей Олексенко). Разбита на тематические блоки (датасет, навыки,
приоритеты, транспорт, временные окна, статусы заявок, базовый алгоритм, метрики, формат
результатов и др.) — это **живые уточнения к ТЗ**, снимающие большинство неоднозначностей
формулировок. Ключевые ответы уже вынесены в `SUMMARY.md` и `TECHNICAL_CONSTRAINTS.md`.

### `Нормативы.xlsx`
Таблица нормативов длительности работ по 4 типам заявок (в минутах), с разбивкой на
"дорога до клиента", "технические работы" и "оформление документов":

| Тип работы | Дорога | Работы | Документы | Норматив (итого) |
|---|---|---|---|---|
| Подключение клиентов (базовая) | 20 | 60 | 10 | 90 |
| Авария на ТКД | 20 | 80 | 0 | 100 |
| Дозаказ оборудования | 20 | 10 | 10 | 40 |
| Локальная заявка / ремонт у клиента | 20 | 30 | 0 | 50 |

Команда решила не использовать фиксированные 20 минут "дороги" из норматива буквально, а
заменить эту часть расчётным временем маршрута (геокодер + API маршрутизации), оставив
только "рабочую" часть норматива как фиксированную длительность работ на объекте.

### `Dataset/` — тестовые данные по трём независимым регионам
Для каждого из трёх регионов (**Восток**, **Юго-восток**, **Югоцентр**) даны 2 файла:

- **`<Регион> Синтетические данные.xlsx`** — заявки без указания исполнителя (колонки:
  Заявка (ID), Тип заявки BK, Тип заявки HD, Начало, Окончание, Район, Адрес, [Подключение],
  Гигабитное подключение). В последних строках отдельно указан **адрес офиса** региона —
  это стартовая точка всех инженеров этого региона. Именно эти файлы — основной вход для
  алгоритма распределения.
- **`<Регион> Контрольное распределение.xlsx`** — те же заявки, но уже с фактическим
  реальным исполнителем ("Бригада …") и статусом BK (Отправлена / В пути / В работе /
  Выполнена / Отменена / Просрочена / Не отправлена). Это **не эталон и не критерий
  качества**, а лишь один из возможных вариантов ручного распределения диспетчером для
  ориентира — свой алгоритм не обязан его повторять и может распределить иначе/эффективнее.

Три региона независимы друг от друга: разные офисы, разные наборы исполнителей ("бригад"),
заявки и исполнители одного региона не пересекаются с другим (даже если фамилия исполнителя
случайно совпала — см. кейс "бригада Каушнян" в двух регионах, это совпадение при
обезличивании, а не одна и та же бригада).

Все данные приведены на один рабочий день — **17.08.2026**, время московское (МСК).

## Дополнительные файлы этой папки

- **`SUMMARY.md`** — краткая выжимка всех финальных уточнений заказчика по ключевым темам
  (датасет, навыки, приоритеты, транспорт, временные окна, статусы, базовый алгоритм,
  метрики, формат ответа) — без "воды" и без отвергнутых по ходу обсуждения вариантов.
- **`TECHNICAL_CONSTRAINTS.md`** — быстрый технический референс: точный формат входных и
  выходных данных, кто такой "инженер" (бизнес-роль, поля, ограничения), обязательные
  ограничения алгоритма, метрики, что не требуется реализовывать.
