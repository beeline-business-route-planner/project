## 1. Кто такой "инженер" (исполнитель, "бригада")

- В данных подписан как **"Бригада <Фамилия>"**, но фактически это **один конкретный
  человек** — заказчик прямо подтвердил, что бригада в этой задаче = один исполнитель, на
  заявку выезжает не группа.
- Поля инженера (минимальный набор из ТЗ): **ID/имя, стартовая точка, начало и конец смены,
  от 1 до 3 навыков, тип транспортного средства**.
- Навыки — **1–3 одновременно** из справочника (см. ниже), могут пересекаться у разных
  исполнителей (кто-то умеет всё, кто-то — только один тип работ). Компетенции/квалификацию
  команда моделирует самостоятельно, если её нет в исходных данных — за основу берутся типы
  работ, которые бригада имеет право выполнять. **Жёсткое правило**: если у бригады нет
  нужной квалификации, заявка этого типа на неё назначаться не должна.
- Транспорт — **ровно один тип** на исполнителя, из справочника (см. ниже); при отсутствии
  в исходных данных — моделируется командой самостоятельно.
- Стартовая точка = адрес офиса **своего региона** (три независимых региона/офиса/пула
  исполнителей — не пересекаются). **Исключение**: для бригад, обслуживающих удалённые
  города Подмосковья (например, Кашира, Ступино, Домодедово), стартовая точка — не офис
  региона, а самостоятельно определяемая точка в соответствующем городе («дом» исполнителя,
  откуда он начинает день); реальные GPS-координаты не нужны.
- Смена: по датасету напрямую не приходит; из обсуждений команды принято ориентировочное
  предположение — около 12 часов (~9:00–21:00), возможен обеденный перерыв — но это не
  подтверждено заказчиком и не является жёстким требованием ТЗ. Официально: только "начало
  и конец смены" как входное поле, без фиксированных значений.
- Ограничения по работе:
  - может приехать на заявку раньше начала окна и **ждать**, но **не может начать работу
    раньше начала окна**;
  - несколько заявок в одном временном промежутке у одного исполнителя — нормально, если
    суммарный норматив укладывается в отведённое время;
  - для аварийной заявки используется норматив **100 минут**; начало её выполнения — это
    момент её фактического поступления (авария возникает в течение рабочего дня как
    событие, а не имеет фиксированное окно "00:01–23:59") — она может потребовать
    оперативного изменения уже построенного маршрута бригады;
  - исполнитель не может переключаться между регионами (закреплён за своим регионом);
  - оборудование, необходимое для выполнения заявок дня, выдаётся исполнителю в офисе **в
    начале дня, сразу на весь рабочий день** (базовый сценарий). При перепланировании на
    бригаду можно назначать только те заявки, для которых у неё есть нужное оборудование;
    допустимый запас оборудования (сколько заявок покрывает выданный комплект) команда
    определяет самостоятельно в рамках своей модели.
- В системе у инженера **нет отдельного личного кабинета / входа** — единственный
  пользователь прототипа это диспетчер (подтверждено заказчиком напрямую). Авторизация не
  требуется.

## 2. Формат входных данных

### Какие файлы фактически переданы

- `<Регион> Синтетические данные.xlsx` — штатный вход заявок. Слово «синтетические» в
  имени не меняет назначение книги.
- `<Регион> Контрольное распределение.xlsx` — справочный пример ручного плана диспетчера,
  а не вход, эталон результата или перечень доступных инженеров.
- `Нормативы.xlsx` — источник нормативов длительности.

Полноценной входной книги инженеров среди материалов организаторов нет, хотя ТЗ задаёт
обязательные поля инженера. Актуальный user case закрывает этот пробел отдельной книгой
инженеров. Контрольное распределение нельзя использовать для восстановления их навыков,
смен, транспорта или стартовых точек.

Исходное имя книги — описание для человека, а не машинный discriminator. В рабочем
контракте роль определяется по обязательным колонкам, необходимые поля извлекаются, а
дополнительные колонки игнорируются.

### Поля ВК / HD

В датасете колонки "Тип заявки ВК" и "Тип заявки HD" — **не два разных вида работ**, а
классификаторы одной и той же заявки из двух разных систем: **ВК** — Beekeeper (внутренняя
система), **HD** — HelpDesk (сторонняя система, откуда пришла заявка). У систем могут быть
разные классификаторы одной и той же заявки; соответствие между значениями ВК и HD команда
определяет самостоятельно по фактическим данным.

### Заявка — минимальные поля (п. 2.4 ТЗ)
| Поле | Комментарий |
|---|---|
| ID | |
| координаты или адрес | геокодирование адреса разрешено любым сервисом (OSM/Яндекс/2ГИС) |
| длительность в минутах | норматив выполнения, зависит от типа работы |
| начало и конец временного окна | обещанное клиенту время визита (согласованное) |
| приоритет | числовой ранг по типу работы, **1 (авария) / 2 (подключение) / 3 (ремонт,
  дозаказ)** — меньше число, выше приоритет (см. справочник) |
| требуемый навык | один из справочника (см. ниже) |
| требуемый тип транспорта | опционально, только при наличии ограничения |

### Инженер — минимальные поля
| Поле | Комментарий |
|---|---|
| ID/имя | |
| стартовая точка | адрес офиса региона (или "дом" — для удалённых бригад Подмосковья) |
| начало и конец смены | |
| навыки | 1–3 из справочника |
| тип транспортного средства | ровно один |

### Событие перепланирования — минимальные поля
| Поле | Комментарий |
|---|---|
| тип события | срочная заявка / отмена заявки / недоступность инженера |
| время события | |
| ID заявки или инженера | |
| (для новой срочной заявки) | полный набор полей заявки |

### Рекомендуемые единицы измерения
- время — `HH:MM`
- длительность и время в пути — минуты
- расстояние — километры
- координаты — широта/долгота

### Справочники
**Требуемый навык (1 на заявку):**
1. Локальные работы
2. Работы на подключение и дозаказы
3. Аварийные работы

**Тип транспортного средства (1 на инженера):**
1. Автомобиль
2. Пешеход
3. Велосипед
4. Общественный транспорт

**Приоритет заявки** — целочисленный ранг по типу работы (меньше = приоритетнее), это
**единственная и основная** шкала приоритета, не два отдельных поля:
1. Авария
2. Подключение
3. Ремонт / Дозаказ (одноуровневые между собой — организатор не дал им отдельного порядка)

Формулировка ТЗ про «обычная/срочная» — грубая 2-бакетная проекция этой же шкалы (`urgent`
= ранг 1–2, `normal` = ранг 3), не отдельный независимый источник правды; если её нужно
показать на UI/в контракте отдельным полем — вычисляется из ранга, не хранится/назначается
параллельно.

Для пешехода/велосипеда/общественного транспорта время в пути допустимо считать по
усреднённой скорости/времени "от точки до точки" — расчёт реальных маршрутов общественного
транспорта не обязателен (решение, которое всё же умеет комбинировать способы перемещения и
реалистично считать маршрут для бригад без авто — дополнительный плюс при оценке).

### Нормативы длительности (из `Нормативы.xlsx`)
| Тип работы | Норматив, мин |
|---|---|
| Подключение (базовая) | 90 |
| Авария на ТКД | 100 |
| Дозаказ оборудования | 40 |
| Локальная заявка / ремонт у клиента | 50 |

Норматив включает время дороги (обычно 20 мин фиксированных в таблице) — по решению
команды эта часть подлежит замене на расчётное время маршрута, а не бралась буквально как
константа.

### Масштаб тестовых данных
- 10–15 инженеров, не более 100 заявок всего, один рабочий день. Количество бригад команда
  определяет самостоятельно; число бригад из контрольного распределения можно использовать
  только как ориентир.
- В данных должны встречаться все 3 навыка, разные комбинации навыков у исполнителей, все
  типы транспорта, пересекающиеся временные окна и минимум один конфликт, где простое
  последовательное распределение хуже оптимального.
- Если данные синтезируются командой самостоятельно — ориентировочное распределение типов
  заявок: **40% локальных, 40% подключений, 10% аварий, 10% дозаказов**.

## 3. Обязательные ограничения алгоритма (п. 2.2 ТЗ)

Минимальная версия ОБЯЗАНА проверять только три группы — усложнять сверх этого не требуется:

| Ограничение | Правило |
|---|---|
| **Квалификация** | требуемый навык заявки ⊆ список навыков инженера |
| **Время** | время в пути + длительность работы укладываются в смену инженера; начало работы попадает во временное окно заявки |
| **Ресурс** | если у заявки указан требуемый тип транспорта — у инженера должен быть именно он (учёт оборудования — необязательное усложнение, см. §1 про запас оборудования) |

Если выполнить все заявки невозможно — сервис обязан явно показать неназначенные заявки и
на понятном диспетчеру языке указать причину (нет свободных исполнителей на время, нет
навыка, нет нужного транспорта, не влезает во временное окно/смену).

## 4. Перепланирование в течение дня

- Перепланирование в течение рабочего дня **возможно и ожидаемо**, хотя для базового
  решения хакатона достаточно статического планирования (расписание строится один раз по
  исходной выгрузке); поддержка динамического перепланирования — дополнительная
  возможность, не обязательное требование.
- Факт закрытия заявки (выполнена/отменена) фиксирует **диспетчер** на основании информации
  от бригады. Закрытые заявки в дальнейшее перепланирование не включаются.
- Статус "Отменена" может появиться при отказе клиента **или** когда бригада определила,
  что выполнить заявку невозможно — не только при отказе клиента.
- При перепланировании учитывается приоритет типов работ (см. §2 — авария → подключение →
  ремонт/дозаказ): например, заявка на подключение может иметь приоритет выше, чем заявка
  на ремонт, а аварийная заявка может потребовать немедленного изменения уже построенного
  маршрута бригады.
- Ранее озвученное клиенту время визита **может быть скорректировано** при
  перепланировании — коммуникацию с клиентом об изменении времени берёт на себя служба
  поддержки (не диспетчер и не алгоритм).
- При перепланировании на бригаду можно назначать только те заявки, для которых у неё есть
  нужное оборудование (см. §1).
- Решение рассматривает один рабочий день; судьба заявок, ушедших "за кадр" (перенос на
  следующий день) — вне скоупа задачи.

## 5. Базовый алгоритм для сравнения (п. 2.3 ТЗ)

Формально зафиксирован для единого сравнения: заявки обрабатываются **по порядку
поступления** и назначаются **первому по порядку во входных данных доступному** инженеру,
удовлетворяющему обязательным ограничениям; порядок посещения = порядок назначения;
глобальная оптимизация не выполняется. Не требуется доказывать математический оптимум —
подойдёт готовая библиотека, эвристика или собственная логика.

Для обязательного MVP маршрут **начинается в стартовой точке** инженера; возвращение в
стартовую точку не требуется.

## 6. Формат выходных данных (п. 2.4.2 ТЗ)

- Для каждого исполнителя — упорядоченный список заявок, плановое время
  прибытия/начала работ, пробег по маршруту.
- Для каждой заявки — назначенный исполнитель либо статус «не назначена».
- Для неназначенной заявки — явная причина понятным диспетчеру языком.
- Для плана в целом — количество задействованных исполнителей, пробег по каждому
  исполнителю и суммарный пробег.
- После перепланирования — наглядное отображение того, какие назначения/порядок/маршруты
  изменились (команда реализует как `old` (удалено) / `new` (добавлено) / без пометки
  (не изменилось)).
- Для выбранного маршрута — краткое объяснение, какие ограничения и факторы повлияли на
  решение (без избыточной детализации "портянкой").

## 7. Обязательные метрики (п. 2.3, 8.1 ТЗ)

1. **Выполнение всех заявок наименьшим количеством персонала** — считается количество
   уникальных исполнителей с хотя бы одной назначенной заявкой.
2. **Пробег по маршруту** — отдельно на каждого исполнителя и суммарно по всему плану.

Обязательно требуется **сравнение с базовым вариантом** (см. §5) по этим двум метрикам.
Дополнительные метрики (необязательные, но приветствуются): минимальное время в пути,
максимальное число выполненных заявок, % полезной загрузки исполнителя (время
работы+дорога / длительность смены), покрытие срочных заявок, нарушения/опоздания.

## 8. Уровни реализации

| Уровень | Что входит |
|---|---|
| Обязательный MVP | распределение заявок, 3 группы ограничений, маршруты на карте, одно перепланирование, понятное объяснение, обязательные метрики |
| Доп. возможности | сравнение нескольких вариантов, красивые метрики, ручное переназначение, несколько сценариев изменений, прогноз опозданий, динамическое перепланирование, реалистичный расчёт маршрутов общественного/комбинированного транспорта |

## 9. Явно НЕ требуется

Полноценная FSM-платформа, мобильное приложение, авторизация (проверка прав доступа —
именно authorization, не аутентификация), Kafka, микросервисная промышленная
отказоустойчивость, тестирование на тысячах заявок, отдельный ЛК/вход для роли "инженер",
расчёт реальных маршрутов общественного транспорта (как обязательное требование).
