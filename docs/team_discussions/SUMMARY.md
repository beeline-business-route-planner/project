## Роли и авторизация — ФИНАЛЬНО РЕШЕНО

**Единственный пользователь системы — диспетчер.** Отдельного личного кабинета/входа для
инженера или бригадира не будет. Авторизация (проверка прав доступа) и аутентификация
(логин/пароль) не реализуются.

> Отвергнуто по пути: на созвоне 1 команда долго не могла решить, требуется ли различать
> "authorization" (в ТЗ явно не нужна) и "authentication" (обсуждали, что можно/нужно
> реализовать логин-пароль и ЛК для инженера/бригадира отдельно), придумывалась сложная
> иерархия ролей Админ → Диспетчер + Бригадир → Инженер с полным CRUD. Всё это снято прямым
> ответом заказчика в Q&A-сессии: "единственный пользователь прототипа — диспетчер... инженеру
> достаточно получать маршрут вне системы" (см. `../source_files/transcript_clean.txt`,
> блок "Дополнительные вопросы: чат и участники"). Сущности "Бригада" как отдельной таблицы
> с CRUD, бригадиром и передачей оборудования между инженерами — тоже отменены за
> ненадобностью.

## Сущности

- **Инженер** — самостоятельная единица (один человек), не связан с сущностью "Бригада".
  Поле "бригада" в исходных данных используется только для чтения контекста, отдельная
  модель БД под него не создаётся.
- 4 таблицы БД: **заявка, инженер, событие_перепланирования, план**.
  - координаты заявки хранятся прямо в таблице заявки (отдельная таблица не нужна);
  - индексы: геоданные, тип события (для событий перепланирования), требуемый навык и тип
    транспорта (для заявок/инженеров — ускоряет фильтрацию инженеров под заявку);
  - таблица "план" хранит связку заявка↔инженер по конкретному прогону планирования, с
    уникальным ID и временем создания — нужно для истории/сравнения планов.
- Статусы заявки (enum): **в пути, в работе, выполнено, не отправлено / не назначена,
  отменено, отправлено, просрочено**. По умолчанию новая заявка имеет статус "не назначена";
  меняется на "назначена/в работе и т.д." только после того, как диспетчер утвердит план.
  Источник истины по статусам — сам диспетчер (частичная автоматическая простановка статусов
  по времени допустима, но с обязательной возможностью ручной корректировки диспетчером;
  самостоятельно "додумывать" статусы система не должна).
- Типы заявки по срочности: **обычная / срочная** (срочная = подключение или
  авария/глобальная проблема на весь день).

## Алгоритм планирования

**Текущая реализация (по состоянию на созвон 4): "послойный точечный граф".**
На каждый 2-часовой временной промежуток строится граф расстояний/весов между заявками,
конечная точка одного временного графа становится стартовой для графа следующего
промежутка. Вес заявки складывается из норматива выполнения (минуты) и расстояния/времени в
пути; на каждый временной промежуток введён лимит суммарного веса (~400 единиц) — не даёт
слишком плотно набивать одному инженеру задачи в рамках двух часов.

Первые результаты прогона на тестовых датасетах: покрытие >30% заявок, загрузка инженера
~76% (по чистой работе) / ~96% (с дорогой), время работы алгоритма ~1.5 сек.

**Выявленная проблема:** алгоритм обрабатывает инженеров последовательно (сначала
максимально нагружает первого, затем второго и т.д.) → первые инженеры перегружены,
последние простаивают.

**Принятое решение:** реализовать алгоритм в **двух режимах**:
1. минимизация количества задействованных инженеров (текущее поведение, приоритетно по
   ТЗ как основная метрика);
2. равномерное распределение нагрузки между всеми доступными инженерами (по требованию —
   масштаб фиксирован: 10–15 инженеров ежедневно).

> Отвергнутые по пути варианты (для истории, не реализуются): (1) "жадный алгоритм", где
> инженер как "дальнобойщик" выбирает ближайшую по весу заявку без учёта графовой связности;
> (2) полный перебор всех перестановок заявок ("49 вариантов между 7 позициями") — отброшен
> из-за неопределённой масштабируемости и отсутствия учёта временных окон; (3) единый граф
> сразу на весь день без разбиения на 2-часовые промежутки — заменён на послойный вариант
> из-за сложности единой формулы веса, одинаково корректно работающей на коротких (40 мин) и
> длинных (100 мин) нормативах.

Отдельно принято: время в пути = **расчётное**, а не фиксированные "20 минут дороги" из
норматива — получается через геокодер + API маршрутизации (в частности, обсуждался
Яндекс.Карты API с ограничением пробного периода 7 дней/100 запросов в день — способ обхода
лимита через несколько аккаунтов признан неэтичным и отклонён в пользу оптимизации числа
запросов).

## Архитектура

**Микросервисная**, минимум 3 логических сервиса:
1. **Сервис оптимизации** — принимает данные (инженеры + заявки + координаты), не работает
   с БД напрямую, выдаёт готовый план (stateless относительно БД).
2. **Сервис перепланирования / сравнения планов** — берёт старый план и заново
   сгенерированный новый, сопоставляет их и возвращает единый JSON с пометками `old`
   (удалено) / `new` (добавлено) / без пометки (не изменилось). Реализуется отдельно от
   алгоритма планирования — переиспользует тот же "обычный" алгоритм оптимизации, просто
   вызванный повторно с новыми входными данными.
3. **Бэкенд (API)** — эндпоинты, схемы данных, БД.

Инфраструктура — отдельный инфра-репозиторий, поднимающий БД (+ опционально Redis, S3,
Grafana/Loki/Prometheus); бэкенд и сервисы подключаются к его Docker-сети. Паттерн работы с
БД и подключения — по прецеденту из существующего репозитория FemVault на GitHub.

## UI / экраны

### Главный экран
- Карта + переключатель вкладок «Заявки» / «Инженеры».
- Вкладка «Заявки»: на карте — точки всех заявок. Клик по заявке (в списке слева или на
  карте) → открывается окно с информацией о заявке и **прорисовывается маршрут** назначенного
  на неё инженера.
- Вкладка «Инженеры»: на карте только точки заявок (без маршрутов), пока не выбран конкретный
  инженер; при выборе — отображается **только его** маршрут и список его заявок. Показывать
  маршруты остальных инженеров серым цветом решили **не делать** — визуальный шум.
- При отдалении карты — кластеризация нескольких близких заявок в одну точку с числом
  (логика на фронтенде).
- Статус-борд: сколько заявок в работе / в пути / просрочено / отменено.
- Кнопки управления планированием (загрузка данных, пересчитать, утвердить) с главного экрана
  **убраны** — перенесены в отдельный экран планирования.

### Экран планирования (отдельная страница, не дашборд/модалка)
- Слева — список всех планов (сегодня / неделя / все остальные), активный план подсвечен.
- Поле загрузки Excel/JSON с двумя таблицами (инженеры + заявки) — единым запросом с двумя
  полями.
- Кнопки «Сгенерировать» / «Перегенерировать», «Утвердить».
- Основная область — отображение выбранного/сгенерированного плана по инженерам и заявкам.
- При перепланировании: подтверждение действия → индикатор загрузки → отображение сравнения
  (удалённые заявки — красным, новые — зелёным, без изменений — серым/зачёркнуто).
- При пустом состоянии главного экрана (нет данных) — баннер по центру с предложением перейти
  к планированию; автоматический редирект решили **не делать**.

### Журнал и аналитика
- История всех планов с уникальными ID, сравнение текущего и прошлых планов.
- Фильтрация заявок (по месту/типу/приоритету/району).
- Аналитика: количество заявок, типы, приоритетность.
- Выгрузка отчёта о дне — **и таблица (Excel/CSV, аналог контрольного распределения), и PDF**
  (оформление — в стилистике исходного ТЗ).

## API — согласованный список endpoint'ов

1. `GET` — все заявки за текущий день.
2. `GET` — все инженеры за текущий день.
3. `GET` — заявка по ID.
4. `GET` — инженер по ID.
5. `PATCH` — изменение статуса заявки (ручная корректировка диспетчером).
6. `GET` — экран планирования: список всех планов из БД, отсортированный по дате.
7. `POST` — загрузка входных данных (**один** endpoint на обе таблицы — инженеры и заявки, два
   поля файлов в одном запросе).
8. `POST` — сгенерировать / перегенерировать план.
9. `POST` — утвердить план.
10. `POST` / `PATCH` — зарегистрировать событие перепланирования (срочная заявка, отмена,
    недоступность инженера).
11. `GET` / `POST` — генерация отчёта о дне (таблица + PDF).

## Метрики (дополнительно к обязательным из ТЗ)

Помимо обязательных (кол-во исполнителей, суммарный/подушевой пробег — см.
`../source_files/TECHNICAL_CONSTRAINTS.md`), команда добавляет:
- **процент полезной загрузки инженера** — доля времени смены, занятая работой+дорогой,
  относительно всей длительности смены (для нескольких вариантов плана можно показывать
  средний % по всем инженерам, например «вариант 1 — 88%, вариант 2 — 78%»);
- покрытие заявок, доля срочных заявок, число нарушений/опозданий, время в пути, число
  изменений при перепланировании.
