# Frontend: экраны, данные и интеграция

React + TypeScript + Vite в `frontend/` — рабочее место диспетчера поверх
[действующего backend API](BACKEND.md). Экран показывает один выбранный округ и
день, хотя backend умеет импортировать несколько округов одним запросом.

## Что делает диспетчер

| Экран | Реальные действия и данные |
|---|---|
| Контроль дня | Список заявок/инженеров, фильтры, карта, карточки из `GET /api/requests/{id}` и `/engineers/{id}`. Статус заявки сегодняшнего дня меняется через `PATCH /api/requests/{id}/status`; отмена вынесена в событие. |
| Планирование | Два блока. **«День округа»** показывает только допустимое по user case: пока первичный план дня не утверждён — зону загрузки пары XLSX (`POST /api/planning/initial`); после утверждения — события дня (`/planning/events`: срочная заявка, инженер выбыл/вернулся, отмена) и «Пересчитать» (`/planning/replan`); пока событие ждёт решения, новые события заблокированы; архивный день — только просмотр. **«Версии плана»** — история, выбранная версия (`/plans/{id}`), решение `/approve` / `/reject`, XLSX, диаграмма дня или diff. Клик по заявке на диаграмме открывает её на карте «Контроля дня». |
| Аналитика | Одна страница по рабочему плану дня: итог (назначено, бригады из доступных, пробег, полезная загрузка с разбросом, время в дороге, срочные вовремя, опоздания); **обязательное по ТЗ (§7) сравнение первичного плана с базовым вариантом** — исполнители, суммарный пробег, назначено (из `baseline_metrics` initial-плана); бюджет смены каждой бригады (работа / дорога / свободно, пробег по бригаде); «Требует внимания» — неназначенные по причинам и опоздания, клик открывает заявку на карте; заявки по типам и статусам; версии дня с Δ пробега. ZIP дневных PDF — `/reports/daily`, CSV версий формируется локально. |

После импорта или перерасчёта появляется **кандидат** `pending`. Пока он не
утверждён, `GET /api/plans/current` и обзор рабочего дня показывают последний
утверждённый план. В списке версий видны также отклонённые кандидаты. Если API
вернул региональную ошибку внутри HTTP 200, UI должен показать её пользователю;
сам по себе успешный HTTP-статус не означает успешного планирования.

Ручное планирование явное: в «Дне округа» — выбор «Рассчитать автоматически» /
«Составить вручную» при загрузке XLSX, а после утверждения дня — карточка «Составить
вручную» (Excel можно загрузить в любой момент дня); у версии на рассмотрении — кнопка
«Исправить вручную». Утверждённый план вручную не редактируется. Редактор
(`src/components/ManualPlanEditor.tsx`) — полноэкранный: слева неназначенные с поиском,
справа бригады; заявку перетаскивают на бригаду или выбирают кликом и нажимают на
бригаду, неподходящие по навыку/транспорту бригады приглушены с причиной; порядок —
перетаскиванием, закреплённые (начатые) остановки не двигаются. «Проверить» считает на
сервере время, дорогу и разницу с рабочим планом, «Сохранить версию» создаёт версию на
рассмотрение; до утверждения рабочий день не меняется. При ручном initial
сравнение с текущим планом не показывается, пока такого плана нет. «История действий»
собирается из истории версий и их статусов, а не из отдельного audit API. В
принудительном demo-режиме часть действий показывает демонстрационный сценарий,
но не меняет сервер.

## Карта и маршруты

`GET /api/plans/{id}` отдаёт `engineers[].stops` с координатами, порядком,
плановым временем и расстояниями, а также старт инженера (`start_latitude/longitude`).
Это **точки маршрута**, не геометрия дорог; дорогу по запросу браузера строит
2ГИС (`src/api/dgisRouting.ts`) через собственный прокси `/dgis-routing`, который
добавляет ключ на сервере (nginx в Docker, Vite в разработке). Backend для карты
не нужен.

- **Маркеры.** Офис округа — флаг, один на округ. API не отдаёт офис отдельно,
  поэтому офисом считается старт, общий для большинства бригад. Удалённые бригады
  Подмосковья (Кашира, Ступино, Домодедово) по ТЗ стартуют из «дома» в своём
  городе — он рисуется иконкой дома и только у выбранной бригады. Заявки группируются, только если
  на экране ближе 34 px; одиночная заявка всегда стоит точно на своём адресе,
  с zoom 15 группируются только точные совпадения адреса. Клик по группе
  приближает карту к её заявкам и карточку не открывает (`GET /api/requests/{id}`
  не вызывается). Группа на одном адресе при zoom 17 уже не разделится —
  там клики по очереди открывают её заявки.
- **Выбранный инженер.** Его заявки — синие маркеры с номером по порядку плана
  (`1,2` — два визита на один адрес), остальные заявки приглушены. Линия идёт
  офис → 1 → 2 → … по транспорту инженера:
  - машина, пешком, велосипед — Routing API 7 (`routing/7.0.0/global`,
    `driving`/`walking`/`bicycle`), до 10 точек на запрос, куски стыкуются;
  - общественный транспорт — Public Transport API (`public_transport/2.0`) по
    каждому переезду: поездка цветом линии/маршрута, пешие участки пунктиром;
    если варианта нет (слишком близко), участок строится пешком.
  Короткий пунктир соединяет адрес с точкой, где маршрут касается дороги. Если
  2ГИС не нашёл участок (например, в зону без машин), он рисуется красным
  пунктиром по прямой, а подпись на карте показывает число таких участков.
  Результаты кэшируются в памяти вкладки.
- **Камера.** При открытии и смене округа карта охватывает все заявки и офисы,
  при выборе инженера — его офис и точки, после построения — ещё и саму линию.
  Обновление статусов камеру не двигает. Кнопка «прицел» возвращает этот вид.

Лимиты ключа: не больше 10 промежуточных точек на запрос (иначе HTTP 403) и
квота запросов (HTTP 429 «too many requests»). На 429 карта сразу прекращает
запросы на минуту, соединяет точки по порядку красным пунктиром и пишет, что
лимит исчерпан. Не больше двух запросов одновременно; готовые маршруты
хранятся в `localStorage` (до 60 штук), так что перезагрузка квоту не тратит.
Этот же ключ стоит в `backend/config.toml` (`[dgis]`) — при `provider = "dgis"`
бэк расходует ту же квоту.
Повторный расчёт плана backend при выборе инженера не происходит. Координаты в
MapGL передаются как `[longitude, latitude]`.

`VITE_2GIS_KEY` нужен карте MapGL и попадает в браузерный bundle — это неизбежно,
ограничивайте его по домену в кабинете 2ГИС. Ключ маршрутов `DGIS_ROUTING_KEY`
(нужен доступ к Routing и Public Transport API; пусто — используется
`VITE_2GIS_KEY`) остаётся на сервере: браузер ходит в `/dgis-routing/...` без ключа.

## Запуск и режимы данных

```bash
cd frontend
npm ci
cp .env.example .env
npm run dev
```

Адрес — <http://localhost:5173>. Локальный Vite proxy передаёт `/api` на backend
`127.0.0.1:8000`. Backend и его зависимости запускаются отдельно по
[`backend/README.md`](../backend/README.md). Значения `frontend/.env`:

- `VITE_API_BASE_URL=/api` — базовый путь API; в Docker его обслуживает nginx
  фронта (`frontend/nginx/default.conf.template`), CORS не нужен.
- `VITE_DEMO_MODE=false` — строгая проверка backend; при ошибке не подменять
  реальные данные демоданными. `auto` (значение по умолчанию) может перейти в
  демо при недоступности API/плана; `true` включает демонстрацию принудительно.
- `VITE_2GIS_KEY` — карта; `DGIS_ROUTING_KEY` — линии маршрутов (только dev-сервер).

Весь проект одной командой (`docker compose up -d --build` из корня) — см.
[README](../README.md); фронт там собирается в nginx на <http://localhost:8088>.

Чтобы вручную проверить интеграцию, используйте `VITE_DEMO_MODE=false`, рабочие
ключи и XLSX **на текущий московский день**. Историческая книга без режима
симуляции в backend не подтверждает сквозной сценарий. Проверки frontend:
`npm run typecheck` и `npm run build`.

## Где менять код

| Потребность | Файлы |
|---|---|
| Переходы между экранами и общий shell | `src/App.tsx`, `src/components/Shell.tsx` |
| HTTP-клиент, методы, backend-типы | `src/api/client.ts`, `services.ts`, `types.ts` |
| Загрузка плана, адаптация API в UI-модель, операции | `src/hooks/usePlanner.ts` |
| Контроль, планирование, журнал | `src/pages/Dashboard.tsx`, `Planning.tsx`, `Journal.tsx` |
| Карта | `src/components/MapPanel.tsx` |
| Маршруты 2ГИС для карты | `src/api/dgisRouting.ts` |
| Dev proxy и сборка | `vite.config.ts`, `package.json` |

Схема слоёв всего проекта — [ARCHITECTURE.md](ARCHITECTURE.md). Для нового API-метода
сначала сверяйте backend OpenAPI и `src/api/types.ts`, затем адаптацию в `usePlanner`;
иначе экран может показать старую демо-модель вместо серверного состояния.
