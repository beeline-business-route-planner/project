# Git-флоу проекта

Правила работы с ветками и коммитами для всей команды. Цель — чтобы `main` всегда был
стабильным (то, что реально показываем на защите), а вся текущая разработка и её
согласование происходили через `dev`.

## Структура веток

```
main                    # только стабильные, согласованные версии (для защиты/демо)
 └── dev                # основная ветка разработки — сюда мёржатся все рабочие ветки
      ├── feature/...   # новая функциональность
      ├── fix/...       # исправление багов
      ├── refactor/...  # рефакторинг без изменения поведения
      ├── docs/...      # документация
      ├── chore/...     # рутина: конфиги, зависимости, CI, инфраструктура
      └── test/...      # тесты
```

- **`main`** — защищённая ветка. Обновляется **только** через PR из `dev`, и только когда
  функциональность в `dev` проверена и согласована командой. Никаких прямых коммитов и
  прямых PR из `feature/*`/`fix/*` в `main`.
- **`dev`** — основная ветка интеграции. Все рабочие ветки создаются от неё и мёржатся
  обратно в неё через Pull Request.
- **Рабочие ветки** (`feature/*`, `fix/*`, `refactor/*`, `docs/*`, `chore/*`, `test/*`) —
  создаются от актуального `dev`, живут ровно до мёржа своего PR, после мержа — удаляются.

## Соглашение об именах веток

Формат: `<slug>/<короткое-название-через-дефис>`

| Slug | Когда использовать |
|---|---|
| `feature/` | новая функциональность (эндпоинт, экран, алгоритм и т.п.) |
| `fix/` | исправление бага в уже существующем функционале |
| `refactor/` | изменение структуры/качества кода без изменения поведения |
| `docs/` | только документация (README, схемы, конспекты) |
| `chore/` | инфраструктура, зависимости, конфиги, CI/CD, не относящееся к коду фич |
| `test/` | добавление/правка тестов без изменения продуктового кода |

Название после slug — короткое, на английском, через дефис, отражает суть задачи, без
номеров задач "на всякий случай" (если есть таск-трекер — можно добавить номер в конец).

Примеры:
```
feature/route-optimization-graph
feature/dispatcher-planning-screen
fix/timezone-offset-in-time-window
refactor/split-optimizer-service
docs/gitflow
chore/setup-infra-repo
test/schedule-conflict-cases
```

## Рабочий процесс

1. Обновить локальный `dev`:
   ```
   git checkout dev
   git pull origin dev
   ```
2. Создать рабочую ветку от `dev`:
   ```
   git checkout -b feature/route-optimization-graph
   ```
3. Коммитить небольшими логическими шагами (см. правила коммитов ниже).
4. Периодически подтягивать актуальный `dev` в свою ветку, чтобы не копить конфликты:
   ```
   git fetch origin
   git rebase origin/dev
   ```
   (или `git merge origin/dev`, если rebase неудобен команде — главное придерживаться одного
   способа).
5. Запушить ветку и открыть **Pull Request в `dev`** (не в `main`).
6. PR проходит ревью минимум одним участником команды, обсуждаются комментарии, вносятся
   правки.
7. После согласования — мёрж в `dev`, ветка удаляется.
8. Когда в `dev` накопился согласованный, проверенный руками функционал (например, перед
   очередным контрольным показом или защитой) — отдельным осознанным действием командой
   делается **Pull Request из `dev` в `main`**. Это отдельный шаг, не автоматический, и
   решение о нём принимается совместно.

## Правила Pull Request

- Один PR — одна логическая задача. Не смешивать фичу и рефакторинг в одном PR, если можно
  разделить.
- Заголовок PR — по смыслу как commit conventional (см. ниже), например:
  `feat: генерация маршрута с учётом временных окон`.
- В описании PR — что сделано и как проверить (какие сценарии прогнать вручную).
- PR должен быть замёржен только после того, как хотя бы один человек из команды его
  посмотрел (ревью может быть кратким, но должно быть).
- Мёрж в `dev` — предпочтительно **squash merge** (один чистый коммит на фичу в истории
  `dev`) либо обычный merge commit — команда выбирает единый способ и придерживается его
  для всех PR.

## Коммиты — Conventional Commits на русском

Формат заголовка коммита:

```
<тип>(<область>): <описание на русском>
```

- **Тип** — стандартный английский идентификатор Conventional Commits (не переводится, чтобы
  инструменты автогенерации changelog понимали его):
  - `feat` — новая функциональность
  - `fix` — исправление бага
  - `refactor` — рефакторинг без изменения поведения
  - `docs` — документация
  - `test` — тесты
  - `chore` — рутина/конфиги/зависимости/инфраструктура
  - `style` — форматирование, не влияющее на логику (отступы, пробелы, линтер)
  - `perf` — изменения, направленные на производительность
  - `build` — сборка, Docker, CI-пайплайны
  - `revert` — откат предыдущего коммита
- **Область** (`scope`) — необязательна, но желательна: имя модуля/сервиса, к которому
  относится изменение (`optimizer`, `api`, `planning-ui`, `db` и т.п.).
- **Описание** — на русском языке, в повелительном наклонении, с маленькой буквы, без точки
  в конце:
  - хорошо: `добавляет валидацию временного окна заявки`
  - плохо: `Добавил валидацию.`

### Примеры

```
feat(optimizer): добавляет режим равномерного распределения нагрузки
fix(planning-ui): исправляет сравнение старого и нового плана при пустом списке заявок
refactor(api): выносит логику сравнения планов в отдельный сервис
docs: описывает git-флоу проекта
chore(infra): поднимает Redis в docker-compose инфра-репозитория
test(optimizer): добавляет кейсы на пересекающиеся временные окна
```

### Тело коммита (по необходимости)

Если изменение не тривиальное — после заголовка через пустую строку добавляется тело с
объяснением **почему** сделано именно так (не "что", это видно из диффа):

```
fix(optimizer): учитывает норматив аварии отдельно от временного окна

Ранее алгоритм проверял всё окно заявки (00:01–23:59) как доступное время
исполнителя, из-за чего инженер считался занятым весь день при получении
одной аварии. Теперь резервируется только фактический норматив (100 минут),
а остальное время остаётся доступным для прочих заявок.
```

### Что нельзя

- Коммиты вида `wip`, `fix`, `правки`, `ещё немного` — без типа и описания сути.
- Смешивание в одном коммите несвязанных изменений (например, фича + правка в докере) —
  разбивать на отдельные коммиты.
- Коммиты напрямую в `main` или `dev`, минуя PR.

## Теги и релизы (опционально)

Если понадобится зафиксировать версию для сдачи (промежуточная/финальная), после мёржа
`dev → main` ставится тег:

```
git tag -a v0.1.0 -m "промежуточная сдача"
git push origin v0.1.0
```
