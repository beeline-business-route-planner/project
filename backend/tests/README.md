# Архитектура тестов backend

Тесты разложены сначала по уровню проверки, затем по домену:

- `unit/` — алгоритм, парсер, presenter, оркестрация и адаптеры с управляемыми фейками; PostgreSQL, Docker и сеть не нужны.
- `integration/database/` — настоящие миграции и PostgreSQL в одноразовом контейнере.
- `e2e/` — пользовательские цепочки initial → replan → event → approve/reject → export/report на отдельных мигрированных БД. Геокодер, матрицы и S3 заменены детерминированными фейками из `support/`.

Запуск из `backend/`:

| Команда | Что запускает | Требования |
|---|---|---|
| `make test` | Только `unit`, с порогом 65 % покрытия ветвей `src` | Python и dev-зависимости |
| `make test-integration` | Только `integration` | Локальный Docker |
| `make test-e2e` | Только `e2e` | Локальный Docker |
| `make test-full` | Все три слоя | Локальный Docker |
| `make test-matrix` | Проверка матрицы сценариев | Python |

`pytest` по умолчанию выбирает `unit`. Можно запускать один тест с `uv run pytest <путь>::<класс>::<метод> --suite=unit`; для других слоёв укажите соответствующий `--suite`.

`tests/scenarios.toml` — источник стабильных ID, описаний, слоёв и путей каждого теста. Коллекция полного выбранного слоя завершается ошибкой, если запись отсутствует, дублируется или тест переехал без обновления каталога. `TEST_MATRIX.md` генерируется командой `make test-matrix-update`; затем `make test-matrix` проверяет, что файл актуален. Новые тесты добавляются вместе с записью в каталог.

При запуске `integration` и `e2e` тестовый раннер создаёт PostgreSQL 16 через Testcontainers, отдельную БД с префиксом `*_test_` для каждого E2E-сценария, применяет настоящие Alembic-миграции и удаляет контейнер после сессии. Настройки БД и внешних ключей подменяются до импорта кода приложения. Тесты не используют рабочую БД и блокируют сетевые вызовы вне loopback; unit блокирует всю сеть. Отсутствие Docker завершает DB-слои ошибкой, не пропуском.

Существующие тесты пока сохраняют `unittest.TestCase` и `IsolatedAsyncioTestCase`, которые собирает `pytest`. Это позволяет менять организацию набора без переписывания самих проверок и постепенно переводить новые сценарии на нативный стиль pytest.

Текущий порог покрытия 65 % зафиксирован по базовому unit-прогону (67 %). Повышать его следует вместе с ростом покрытия, не снижать при добавлении кода.
