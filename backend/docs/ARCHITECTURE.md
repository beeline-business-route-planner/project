# Архитектура backend

Описывает, как устроен шаблон сейчас (`src/`), и как в него добавлять предметную логику
задачи (заявки, инженеры, планирование, перепланирование), не ломая заложенную структуру.
См. также `../../docs/team_discussions/SUMMARY.md` — там согласованное командой решение по
сущностям/эндпоинтам/сервисам верхнего уровня, этот файл — как это лечь на код backend-шаблона.

## Стек

FastAPI + uvicorn · dishka (DI) · SQLAlchemy 2.0 (async) + asyncpg + Alembic ·
pydantic-settings · prometheus-client · структурные JSON-логи. Подробности — в
`../README.md`.

## Слои

```
Request
  │
  ▼
src/api/…/router.py        HTTP-слой: FastAPI-роутеры, Pydantic-схемы запросов/ответов.
  │                        Тонкий: валидация входа → вызов сервиса → сериализация ответа.
  ▼
src/core/services/…        Слой бизнес-логики (домены): оркестрирует репозитории через UoW,
  │                        валидирует бизнес-правила, вызывает внешние клиенты (геокодер,
  │                        маршрутизация). НЕ знает про FastAPI/HTTP.
  ▼
src/core/db/
  ├── models/…             SQLAlchemy ORM-модели (таблицы БД).
  ├── dto/…                Датаклассы для передачи данных между слоями без протаскивания ORM.
  ├── repositories/…       Доступ к данным конкретной модели (CRUD + выборки), без бизнес-логики.
  └── uow.py                UnitOfWork — держит сессию, агрегирует репозитории, коммит/роллбэк.
  ▼
PostgreSQL
```

Правило: **зависимости идут только вниз**. Роутер знает про сервис, сервис — про UoW и
репозитории, репозиторий — только про свою модель. Модель не знает ни про DTO, ни про
сервис. DTO не знает про SQLAlchemy.

## Точка входа и сборка приложения

`src/main.py` — единственное место, где:
- создаётся `FastAPI(...)` и DI-контейнер `dishka` (`make_async_container(...)`);
- регистрируются миддлвари (`CORSMiddleware`, `PrometheusMiddleware`,
  `RequestLoggingMiddleware`) — порядок добавления важен: ASGI-миддлвари оборачивают друг
  друга в порядке `add_middleware`, поэтому последняя добавленная выполняется раньше при
  входе запроса;
- подключается корневой роутер `src.api.router`;
- объявлен глобальный обработчик необработанных исключений и служебные роуты `/` и
  `/metrics`.

`src/__main__.py` — просто вызывает `main()` из `src/main.py`, чтобы работал
`python -m src` / `uv run python -m src` (см. `make run`).

## Dependency Injection (dishka)

- `Provider`-классы лежат в `src/core/di/`. Один `Provider` = одна связная область
  зависимостей (сейчас — `DbProvider`: движок БД, session maker, сессия на запрос, UoW).
- Скоупы:
  - `Scope.APP` — создаётся один раз на всё приложение (engine, sessionmaker);
  - `Scope.REQUEST` — создаётся заново на каждый HTTP-запрos (сессия БД, `UnitOfWork`).
- Новый провайдер (например, для сервиса планирования или клиента геокодера) — отдельный
  файл в `src/core/di/`, регистрируется в `make_async_container(...)` в `src/main.py`.
- В роутере зависимость запрашивается через `dishka.integrations.fastapi.FromDishka`,
  а не создаётся вручную и не тянется через глобальные синглтоны.

## Слой данных: модели → DTO → репозитории → UnitOfWork

- **Модели** (`src/core/db/models/`) — источник правды о структуре БД. Наследуют `Base`
  (`src/core/db/models/base.py`), таблица называется автоматически как `cls.__name__.lower()`.
  Каждая новая модель **обязательно** импортируется в `src/core/db/models/__init__.py`,
  иначе Alembic не увидит её при автогенерации миграции (см. комментарий в
  `alembic/env.py`: `Base.metadata` собирается только из того, что реально импортировано).
- **DTO** (`src/core/db/dto/`) — неизменяемые датаклассы для передачи данных из слоя доступа
  к данным наружу (в сервис/роутер), не тянут за собой SQLAlchemy-сессию и ORM-специфику.
  Строятся из модели через `SomeDTO.from_orm(model_instance)` (`BaseDTO.from_orm`).
- **Репозитории** (`src/core/db/repositories/`) — один репозиторий на модель, наследник
  `BaseRepository[ModelType]` (`get_by_id`, `add`, `delete` уже есть в базовом классе).
  Специфичные выборки (например, "все заявки на дату Х" или "инженеры с навыком Y")
  добавляются как отдельные async-методы в конкретном репозитории, не в базовом.
- **UnitOfWork** (`src/core/db/uow.py`) — держит одну `AsyncSession` на весь запрос,
  агрегирует репозитории как атрибуты (см. закомментированный пример в файле) и отвечает
  за `commit`/`rollback`. Сервисы получают `UnitOfWork` через DI и работают с репозиториями
  только через него — не создают свои сессии.

### Как добавить новую сущность (например, `Requestpoint`/заявку)

1. `src/core/db/models/request.py` — SQLAlchemy-модель, зарегистрировать в
   `models/__init__.py`.
2. `src/core/db/dto/request.py` — `@dataclass RequestDTO(BaseDTO)` с нужными полями.
3. `src/core/db/repositories/request.py` — `class RequestRepository(BaseRepository[Request])`
   + доменные выборки.
4. Подключить репозиторий в `UnitOfWork.__init__` (`self.requests = RequestRepository(self.session)`).
5. `uv run alembic revision --autogenerate -m "add request table"` (`make migrate MSG=...`) →
   проверить сгенерированную миграцию руками → `make upgrade`.

## Сервисный слой (бизнес-логика)

В шаблоне сейчас нет каталога `src/core/services/` — его нужно завести, как только
появляется первая бизнес-логика сложнее прямого CRUD (в этой задаче это будет почти сразу:
распределение заявок, перепланирование, сравнение планов).

Соглашение:
- `src/core/services/<domain>.py`, класс `<Domain>Service`.
- Сервис получает через `__init__` всё, что ему нужно (`UnitOfWork`, при необходимости —
  клиент геокодера/маршрутизации), — никаких скрытых глобальных зависимостей.
- Сервис **не импортирует FastAPI** и ничего не знает про HTTP/Pydantic-схемы запроса —
  принимает и возвращает DTO или простые типы. Это позволяет тестировать сервис без
  поднятия HTTP-слоя.
- Регистрируется как ещё один `Provider` в `src/core/di/`, инжектится в роутер.

Ожидаемые для этой задачи сервисы (по мотивам `../../docs/team_discussions/SUMMARY.md`):
- **`PlanningService`** — построение плана: подбор допустимых инженеров под заявку по трём
  обязательным ограничениям (квалификация/время/ресурс), вызов алгоритма оптимизации
  маршрута, сохранение результата как нового `Plan`.
- **`ReplanningService`** — принимает событие перепланирования, вызывает `PlanningService`
  заново и сравнивает старый/новый план (`old`/`new`/без изменений).
- Расчёт маршрута/времени в пути (геокодирование + матрица расстояний) — вынести в отдельный
  клиент (`src/core/clients/routing.py` или аналогично), сервисы планирования используют его
  через DI, не обращаются к внешнему API напрямую россыпью по коду.

Если по ходу разработки решите вынести оптимизатор в отдельный процесс/микросервис (как
обсуждалось в `../../docs/team_discussions/SUMMARY.md`) — этот backend остаётся HTTP-фасадом
поверх него: `PlanningService` в этом случае просто ходит по HTTP/RPC к сервису оптимизации
вместо прямого вызова функции, остальной слой (роутер → сервис → UoW) не меняется.

## API-слой

- Корневой роутер `src/api/__init__.py` (`APIRouter(prefix="/api")`) — точка сборки всех
  доменных роутеров через `include_router` в `src/main.py`.
- Соглашение по доменным роутерам (заводить по мере появления доменов):
  `src/api/<domain>/router.py` (сам роутер) + `src/api/<domain>/schemas.py`
  (Pydantic request/response модели). Пример: `src/api/plans/router.py`,
  `src/api/plans/schemas.py`.
- Исключения домена — `src/api/exc/<domain>.py`, наследники `src.api.exc.base.Base`
  (см. `CODESTYLE.md`, раздел «Ошибки и исключения API»).

## Конфигурация

`src/config/config.py` — один класс `Config(BaseSettings)` с вложенными секциями
(`Database`, `Logging`, `CORS`, …). Источники в порядке приоритета: переменные окружения
(разделитель вложенности `__`, например `DATABASE__POSTGRES_HOST`) → `config.toml`. Новая
секция конфигурации (например, для геокодера/маршрутизации) — ещё один вложенный
`BaseModel`, подключается в `Config` как поле.

## Наблюдаемость

- **Логи** — структурный JSON в stdout (`src/core/logging.py`), с `request_id` из
  `contextvars` (`src/core/context.py`), собираются Promtail → Loki (docker-compose).
- **Метрики** — Prometheus-миддлварь (`src/core/metrics.py`) считает
  `http_requests_total`, `http_request_duration_seconds`, `http_requests_active`, отдаются
  на `/metrics`; Prometheus + Grafana + cAdvisor подняты в `docker-compose.yml`.
- **Request-логи** — отдельная миддлварь (`src/core/middleware.py`) логирует каждый запрос
  (метод, путь, статус, длительность) и прокидывает `X-Request-Id` в заголовки ответа.

Расширять наблюдаемость новыми доменными метриками (например, "сколько заявок не назначено
после планирования") — через `prometheus_client.Gauge`/`Counter`, объявленные рядом с
доменным сервисом, по аналогии с `src/core/metrics.py`.

## Миграции

Alembic настроен на асинхронный движок (`alembic/env.py`), URL берётся из `cfg.database`,
метаданные — из `src.core.db.models.Base.metadata`. Рабочий цикл — `make migrate MSG="..."` →
проверить сгенерированный файл в `alembic/versions/` руками (autogenerate не идеален,
особенно для индексов/constraint'ов) → `make upgrade`.

## Инфраструктура и запуск

`docker-compose.yml` поднимает backend + Postgres + мониторинг-стек одной командой
(`make up`). Для локальной разработки без Docker — поднятый отдельно Postgres +
`make upgrade && make run`. Подробности — `../README.md`.
