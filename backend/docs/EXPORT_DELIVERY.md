# Временная доставка экспортов (T09)

Два эндпоинта используют общую доставку через закрытый S3-бакет:

- `GET /api/plans/{plan_id}/export` — XLSX выбранной версии плана любого статуса.
- `GET /api/reports/daily?planning_date=YYYY-MM-DD` — ZIP дневного отчёта.

Оба возвращают JSON с `url`, `expires_at`, `filename`, `content_type` и
`size_bytes`. Ссылка формируется до загрузки объекта, но возвращается только после
успешной загрузки. При ошибке S3 ответ — 502; при ошибке генерации или превышении
лимита размера — 500. План и отчёт не меняют БД.

ZIP содержит `daily-report-YYYY-MM-DD/summary.pdf` и по одному
`daily-report-YYYY-MM-DD/<region>.pdf` для каждого округа с утверждённым
планом. Имена и порядок записей детерминированы. XLSX и ZIP создаются в памяти,
без постоянных или временных файлов на диске backend. Повторный запрос создаёт
новый объект с UUID в ключе.

## Конфигурация

Секция `s3` в typed config содержит:

| Параметр | Назначение | Значение по умолчанию |
|---|---|---:|
| `bucket_exports` | закрытый бакет экспортов | `exports` |
| `export_prefix` | префикс ключей в бакете | `exports` |
| `public_endpoint_url` | адрес S3, доступный браузеру для presigned URL | внутренний `endpoint_url` |
| `export_url_ttl_seconds` | срок действия ссылки | 900 с |
| `export_retention_hours` | требуемое хранение объекта | 24 ч |
| `max_export_size_bytes` | предельный размер готового файла | 10 000 000 байт |
| `connect_timeout_seconds` | тайм-аут подключения к S3 | 10 с |
| `read_timeout_seconds` | тайм-аут операции S3 | 60 с |

В Docker Compose бакет `S3_BUCKET_EXPORTS` создаётся отдельно, и его
anonymous policy явно переводится в `private` при инициализации. Для локального
браузера `S3_PUBLIC_ENDPOINT_URL` должен указывать на опубликованный MinIO (`http://127.0.0.1:9000` в текущем
Compose). В другом окружении нужно указать соответствующий доступный клиенту
адрес. Подпись URL привязана к host; менять host в готовой ссылке нельзя.

В локальном Docker Compose сервис `minio-export-lifecycle` перед запуском backend
настраивает правило удаления для `S3_EXPORT_PREFIX/` в закрытом бакете
`S3_BUCKET_EXPORTS`. Значения `S3_EXPORT_PREFIX` и `S3_EXPORT_RETENTION_HOURS`
передаются и backend, и инициализатору; по умолчанию это `exports/` и 24 часа.
MinIO задаёт срок целым числом суток, поэтому часы округляются вверх: например,
25 часов дают правило на 2 суток. Повторный запуск обновляет своё правило без
дублирования и сохраняет правила для других префиксов. Если для того же
префикса уже настроено чужое правило, инициализация останавливается с ошибкой.
Проверить результат можно командой:

```bash
cd backend
docker compose run --rm --no-deps --entrypoint sh minio-init -c \
  'mc alias set local http://minio:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD" >/dev/null && mc ilm rule ls "local/$S3_BUCKET_EXPORTS"'
```

В других окружениях lifecycle-правило остаётся задачей администратора S3:
backend не удаляет объекты в HTTP-запросе и не запускает таймер. Если правила
нет, ссылка истечёт, но объект останется в бакете. Typed config проверяет,
что заявленное время хранения больше срока действия ссылки, а export bucket
отличается от остальных бакетов. Фактическое удаление выполняет S3/MinIO
после обхода объектов, поэтому момент удаления может быть позже указанного срока.

## Проверка

Из каталога `backend` в установленном окружении:

```bash
.venv/bin/python -m unittest tests.test_plan_export tests.test_t09_export_delivery -v
```

Тесты проверяют структуру ZIP, безопасные имена, метаданные, TTL, ограничение
размера, ошибки S3 и отсутствие ссылки при неуспешной загрузке. Для полного
HTTP-прогона нужен отдельный тестовый PostgreSQL с утверждённым планом и
локальный MinIO с закрытым export bucket; после ответа следует скачать URL
и открыть XLSX/ZIP. Этот прогон не заменяется модульными тестами.
