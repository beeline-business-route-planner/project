# ALGORITHM.md

Как устроен алгоритмический слой (`src/core/algorithm/`) — общий контракт, пул
допустимых заявок, режимы распределения, шесть стратегий секвенирования
маршрута. Про слои/стиль кода — [../agents-docs/ARCHITECTURE.md](../agents-docs/ARCHITECTURE.md)/
[../agents-docs/CODE_STYLE.md](../agents-docs/CODE_STYLE.md). Про модели БД,
в которые в итоге ложится результат — [DATABASE.md](./DATABASE.md). Что и
почему в терминах ТЗ — [../../docs/source_files/TECHNICAL_CONSTRAINTS.md](../../docs/source_files/TECHNICAL_CONSTRAINTS.md).

**Статус на сейчас**: реализовано полностью — контракт и типы данных
(`contracts.py`, `models.py`), пул/режимы распределения
(`distribution.py`), общий движок и все шесть стратегий (`shared/`,
`strategies/`), клиент матрицы расстояний (`src/core/routing/`, см.
[ROUTING.md](./ROUTING.md)), сервис-оркестратор `AlgorithmService`
(`src/core/algorithm/service.py`), вызываемый из `PlanningService` сразу
после импорта выгрузки. В продакшен-потоке подключена только одна
стратегия — `LayeredExactStateGraph` (самая быстрая из протестированных,
см. таблицу ниже и `test/reports/OVERALL.md`); остальные пять существуют,
проходят `make check` и доступны для ручного вызова/сравнения через
`ALL_STRATEGIES` (`strategies/registry.py`), но не участвуют в реальном
планировании. `plan_replan`/`plan_on_event` — по-прежнему
`NotImplementedError` во всех шести.

## Место в общем потоке

```
PlanningService.import_initial_data(...)   — парсит выгрузку, сохраняет
  │                                            Request/Engineer, коммитит,
  │                                            затем для каждого upload_id:
  ▼
AlgorithmService.plan_initial(upload_id, region, mode)  (src/core/algorithm/service.py)
  │  грузит Request/Engineer через UoW.{requests,engineers}.get_by_upload_id,
  │  строит EngineerContext/Job из ORM-моделей,
  │  получает TravelMatrix через RoutingService.build_matrix (src/core/routing/,
  │  см. ROUTING.md) — один запрос на весь округ сразу,
  │  вызывает DistributionPlanner
  ▼
DistributionPlanner.assign(...) (src/core/algorithm/distribution.py)
  │  1. строит пул допустимых заявок на каждого инженера (см. ниже)
  │  2. сортирует инженеров по режиму (min_engineers / balanced)
  │  3. на каждого инженера по очереди вызывает выбранную стратегию:
  ▼
PlanningAlgorithm.plan_initial(context, budget_seconds) -> Route
  │  LayeredExactStateGraph — единственная подключённая сейчас стратегия
  │  из src/core/algorithm/strategies/ (остальные 5 — см. таблицу ниже)
  ▼
DistributionPlanner: вычитает занятые в Route заявки из пулов оставшихся
  инженеров, копит Route[] и оставшиеся неразмещённые заявки
  ▼
AlgorithmService: сохраняет Plan/PlanStop/PlanUnassignedRequest через UoW
```

Почему именно так — тестовые алгоритмы (`test/algorithms/`, 6 реализаций)
решают только секвенирование маршрута **одного** инженера по уже заданному
набору заявок (TSP with Time Windows + приоритеты). Распределения заявок
между несколькими инженерами там нет вообще — это отдельный слой
(`DistributionPlanner`), который нужно построить поверх.

## Пул допустимых заявок (`DistributionPlanner`)

Для каждого инженера строится пул заявок, которые ему подходят **только**
по двум статическим критериям — без учёта времени:

- совпадает `required_skill` заявки с одним из навыков инженера;
- если у заявки задан `required_vehicle_type` — он совпадает с
  `Engineer.vehicle_type`.

Единый `region` для всех `engineers`/`jobs`, переданных в
`DistributionPlanner.assign(...)`, — не третий критерий фильтрации внутри
планировщика, а гарантия вызывающего кода: `AlgorithmService` грузит
`Request`/`Engineer` по `upload_id` одной конкретной выгрузки одного
округа, округа физически не пересекаются (см. `DATABASE.md`), поэтому
внутри одного вызова `assign(...)` все точки уже одного региона.

Пулы **пересекаются**: одна заявка может годиться сразу нескольким
инженерам — итоговое закрепление решает уже сам процесс распределения, а не
этап построения пула. Заявки, не попавшие ни в один пул — причина
`no_matching_skill`/`no_matching_vehicle` (`UnassignedReason`).

### Два режима

1. **`min_engineers`** (минимальное количество инженеров) — сортировка
   инженеров округа **по убыванию** размера пула, начинаем с самого
   загруженного. Идея: сначала выжать максимум из самых "полезных"
   инженеров, оставляя менее полезных недозагруженными или свободными.
2. **`balanced`** (баланс нагрузки) — сортировка **по возрастанию** размера
   пула, начинаем с наименее загруженных. Идея: не дать самым "удачливым"
   инженерам с большим пулом отобрать себе всё лучшее раньше остальных.

После того как инженер получил маршрут (`Route` от стратегии), все
заявки из `Route.assigned_job_ids` вычитаются из пулов **всех оставшихся**
необработанных инженеров — иначе один пул мог бы отдать одну и ту же
заявку двум разным исполнителям.

Заявка, оставшаяся неразмещённой после прохода по всем инженерам её
пула — `no_time_slot` (в чей-то пул попадала, но не влезла по окну/смене)
или `no_available_engineer` (все подходящие инженеры уже заняты другими
заявками к моменту, когда до неё дошла очередь).

## Контракт стратегии (`contracts.py`)

```python
class PlanningAlgorithm(ABC):
    name: ClassVar[str]
    slug: ClassVar[str]

    @abstractmethod
    def plan_initial(self, context: EngineerPlanningContext, budget_seconds: float) -> Route: ...

    def plan_replan(self, context: EngineerPlanningContext, budget_seconds: float) -> Route:
        raise NotImplementedError(...)

    def plan_on_event(self, context: EngineerPlanningContext, budget_seconds: float) -> Route:
        raise NotImplementedError(...)
```

Три метода — три сценария планирования из `TECHNICAL_CONSTRAINTS.md`/
`DATABASE.md` (`Plan.kind`: `initial`/`manual_replan`/`event_replan`):

| Метод | Сценарий | Статус |
|---|---|---|
| `plan_initial` | первичное планирование по утренней выгрузке | реализуется в каждой стратегии |
| `plan_replan` | диспетчер нажал «пересчитать» без новых данных | `NotImplementedError` — нужно уважать `PlanStop.is_locked` (не трогать то, что уже в прошлом по времени) |
| `plan_on_event` | пересчёт из-за `ReplanningEvent` (срочная заявка/отмена/недоступность инженера) | `NotImplementedError` — нужно учитывать конкретный `ReplanningEventType` |

Каждая из шести стратегий сейчас реализует **только** `plan_initial`.
Остальные два метода поднимаются по мере того, как продумывается конкретная
механика (какие стопы блокировать, как инжектить срочную заявку в уже
частично прожитый маршрут) — эта работа отдельная от переноса самих
алгоритмов секвенирования и не блокирует первичное планирование.

## Типы данных (`models.py`)

| Тип | Роль |
|---|---|
| `Job` | заявка на уровне алгоритма — очищенная от ORM проекция `Request` (id, координаты, окно, длительность, приоритет, навык/транспорт) |
| `EngineerContext` | инженер на уровне алгоритма — проекция `Engineer` (id, стартовая точка, смена, навыки, транспорт) |
| `TravelMatrix` | `Protocol` — `minutes(from_id, to_id)`/`kilometers(from_id, to_id)`. Реализация — вне пакета `algorithm` (`src/core/routing/`), стратегии знают только про протокол, не про OSRM/2ГИС — можно тестировать на фейковой матрице без сети |
| `EngineerPlanningContext` | вход стратегии: один инженер + его пул заявок (уже профильтрованный `DistributionPlanner`) + `TravelMatrix` |
| `Stop` | одна остановка построенного маршрута — заготовка будущего `PlanStop` |
| `Route` | результат стратегии для одного инженера — упорядоченный список `Stop` |

`id` заявки/инженера одновременно служит ключом узла в `TravelMatrix` — так
стратегиям не нужен отдельный маппинг "заявка → индекс матрицы".

## Общий движок (`shared/`, перенесён из `test/algorithms/_shared/`)

Пять из шести протестированных алгоритмов в `test/algorithms/` — это не
независимые реализации, а разные комбинации вызовов одного общего модуля.
Перенесена та же расстановка:

| Файл | Что делает | Зачем общий |
|---|---|---|
| `shared/context.py` | `build_context` — конвертация публичного `EngineerPlanningContext` во внутренний `AlgorithmContext` движка (минуты вместо datetime, `office_id = engineer.id` вместо строкового sentinel `"OFFICE"`), включая **инверсию шкалы приоритета** `4 - db_priority` (в БД 1 = авария/важнее, движок везде максимизирует сумму `priority`) | без инверсии движок предпочитал бы маршруты с заявками низкого приоритета — см. докстринг `engine_priority` |
| `shared/evaluate.py` | `evaluate_route`/`independent_audit`/`materialize_route` — проверка окна/смены, расчёт arrival/start/finish, сборка публичного `Route` | одинаковые правила игры для всех стратегий — иначе они были бы несравнимы между собой |
| `shared/comparison.py` | `route_key`/`best_route` — лексикографический критерий `(count, priority, -travel, -finish)` | единый критерий «лучше/хуже» для мультистарт-стратегий и для сравнения результатов разных стратегий между собой |
| `shared/heuristics.py` | `ruin_recreate`/`relocate_descent`/`efficient_completion` | постпроцессинг-полировка, переиспользуется несколькими стратегиями |
| `shared/ortools_routing.py` | `tuned_ortools_route` — общая CP-обёртка вокруг OR-Tools | переиспользуется `ortools_multistart_gls` и `hybrid_seed_ortools_polish` — общая инфраструктура, не нарушение изоляции стратегий друг от друга |

## Шесть стратегий (`strategies/`)

Подключена в `AlgorithmService` (продакшен-поток) — только
`LayeredExactStateGraph`, самая быстрая по `test/reports/OVERALL.md`
(535–1816 мс против 3000–11000 мс у остальных). Остальные пять реализованы,
проходят `make check`, доступны через `ALL_STRATEGIES`
(`strategies/__init__.py`) для ручного вызова/сравнения, но не участвуют в
реальном планировании.

| Файл | Класс | Подход | В проде |
|---|---|---|---|
| `layered_exact_state_graph.py` | `LayeredExactStateGraph` | точная послойная динамика с Парето-доминированием — оптимальна **только** при непересекающихся окнах заявок | ✅ |
| `tasty_graph_multistart.py` | `TastyGraphMultistart` | жадное построение с 5 наборами весов + ruin-recreate | — |
| `regret_insertion_ruin_recreate.py` | `RegretInsertionRuinRecreate` | regret-2 вставка (штраф за откладывание заявки) + ruin-recreate | — |
| `ortools_multistart_gls.py` | `OrtoolsMultistartGls` | OR-Tools CP routing, Guided Local Search, `AddDisjunction` для пропуска заявок | — |
| `hybrid_seed_ortools_polish.py` | `HybridSeedOrtoolsPolish` | берёт результаты остальных 4 стратегий как посев для OR-Tools (единственное разрешённое исключение из изоляции стратегий друг от друга — так устроен сам алгоритм) | — |
| `beam_anneal.py` | `BeamAnneal` | Beam Search (ширина 500) + локальная полировка обменом соседних заявок | — |

Зависимость `ortools` (нужна двум стратегиям) добавлена в `pyproject.toml`
(`uv add ortools`).

## Известные ограничения (техдолг, не тихо замалчивать)

- **Пересекающиеся окна заявок** ломают доказуемую оптимальность
  `layered_exact_state_graph` — для инженеров с пересекающимися окнами в
  пуле нужно либо не использовать эту стратегию, либо явно принять
  эвристический (не точный) результат. Особенно актуально для аварийной
  заявки: по ТЗ у неё нет фиксированного узкого окна (окно на весь день,
  фактическое время начала — момент поступления события, см.
  `TECHNICAL_CONSTRAINTS.md`, §1), то есть её окно пересекается с окном
  вообще любой другой заявки пула этого инженера — послойная разбивка по
  `window_start` не гарантирует для таких инженеров нахождение подлинного
  оптимума, только валидный (по времени/смене) результат. **Не
  исправлено** — нужно либо доказать/ограничить достаточность текущей
  эвристики для этого конкретного случая (авария как отдельный "нулевой"
  слой перед остальными), либо явно перейти на одну из пяти эвристических
  стратегий для инженеров с широкими/пересекающимися окнами.
- **Приоритизация исправлена** (сессия 2026-09-21): раньше приоритет во
  всех шести стратегиях был вторичным тай-брейком (`route_key`) после
  числа заявок — маршрут с двумя заявками приоритета 3 обгонял маршрут с
  одной заявкой приоритета 1. Теперь `engine_priority`
  (`shared/context.py`) переводит приоритет БД в степенную шкалу
  (`_PRIORITY_TIER_WEIGHT ** (тир - 1)`, тир авариии всегда перевешивает
  любое реалистичное (≤100) количество заявок более низких тиров), а
  `route_key` (`shared/comparison.py`) и финальный выбор в
  `layered_exact_state_graph.py` сравнивают сначала по приоритету, потом
  по числу заявок. Проверено сценарием: авария на 100 минут корректно
  предпочитается трём обычным заявкам по 30 минут, конфликтующим с ней по
  времени. Изменение затронуло общий движок (`shared/`) и подключённую в
  проде стратегию; у `beam_anneal.py`/остальных неподключённых стратегий
  остались собственные локальные сравнения `(count, priority, ...)` в
  внутреннем поиске (не через `route_key`) — не тронуты, так как не
  участвуют в реальном планировании, но при подключении любой из них
  потребуют того же приведения к порядку `(priority, count, ...)`.
