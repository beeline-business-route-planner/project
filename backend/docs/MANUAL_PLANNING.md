# Ручное планирование

Диспетчер может собрать первичный план из XLSX без запуска оптимизатора или изменить
`pending`-кандидата, построенного алгоритмом. Оба сценария используют одинаковые
проверки квалификации, транспорта, доступности, временных окон, смен, дороги и
неизменяемой истории. Время остановок и метрики рассчитывает backend.

## API

| Метод | Назначение |
|---|---|
| `POST /api/planning/manual/import` | Пара XLSX одного округа; импортирует и геокодирует заявки и инженеров, возвращает `upload_id` и данные для редактора. План ещё не создаётся. |
| `GET /api/planning/manual/imports/{upload_id}` | Повторно читает импортированные данные. |
| `POST /api/planning/manual/preview` | Проверяет полные списки будущих заявок по инженерам, возвращает остановки и метрики без сохранения. |
| `POST /api/planning/manual` | Повторно проверяет и сохраняет новую версию со статусом `pending`, возвращает `plan_id`. |

Тело `preview` и `save`:

```json
{
  "upload_id": "<uuid>",
  "routes": [
    {"engineer_id": "<uuid>", "request_ids": ["<uuid>"]}
  ]
}
```

Для правки кандидата вместо `upload_id` передаётся `source_plan_id`. В `routes`
передаётся весь редактируемый будущий хвост каждого инженера в нужном порядке.
Неуказанные заявки становятся неназначенными с причиной `manual_decision`;
закреплённые остановки передавать нельзя — они переносятся из текущего плана.

Новая версия сохраняет `kind` сценария (`initial`, `replan`, `event_replan`),
получает `strategy=manual` и `edited_from_plan_id` исходного кандидата. Исходный
кандидат становится `rejected`, новый нужно отдельно утвердить. При правке
event-кандидата событие остаётся `pending` до утверждения или отклонения новой версии.
`based_on_plan_id` по-прежнему указывает на текущий утверждённый план для diff.

`preview` возвращает `compared_to_plan_id` и разницы по назначениям, числу
инженеров и пробегу относительно текущего плана округа. Пока утверждённого
плана нет, ID и разницы равны `null`; интерфейс скрывает сравнение.

Если ручной маршрут нарушает ограничения, `preview` и `save` отвечают `422` с
`details.issues`: у каждого нарушения есть `request_id`, `engineer_id`, `code`,
а для просроченного окна и конца смены — `at` и `limit`. Редактор подсвечивает
соответствующие заявки красным и показывает причины при наведении. После
перемещения заявки подсветка сбрасывается до новой проверки.

Ручной план из XLSX можно собрать в любой момент дня, в том числе после утверждённого
первичного плана: импорт, расчёт, сохранение и утверждение не проверяют «initial уже
утверждён». Утверждённый ручной план становится текущим; алгоритмический initial
по-прежнему однократный. Утверждённый план вручную не редактируется — только кандидат на
рассмотрении или новый план из файлов.

Ручной initial сохраняет baseline для дневного отчёта. После утверждения ручного
плана обычный алгоритмический replan или event replan по умолчанию использует LNS.
