# PLANS_API.md

Дизайн чтения плана — эндпоинты `GET /api/plans/*`, экраны, куда они ложатся
(«Главный экран» и «Экран планирования» из
[`../../docs/team_discussions/SUMMARY.md`](../../docs/team_discussions/SUMMARY.md)).

**Статус: код написан (сессия 2026-09-21), `make check` чист, миграция
для `PlanStop.planned_start`/`planned_finish` — НЕ сгенерирована** (нужен
живой Postgres, автогенерация Alembic сама подключается к БД — оставлено
пользователю, см. `alembic/versions/`, `.claude/skills/add-migration`).
Без нанесённой миграции эндпоинты `/api/plans/*` упадут на реальной БД
(колонок физически нет) — до `make migrate`/`make upgrade` работоспособны
только статические проверки (`make check`) и сборка DI-контейнера,
проверено smoke-тестом. Реализовано: `src/api/plans/`, `src/api/requests/`
(`GET /api/requests/{id}`), `src/api/engineers/` (`GET /api/engineers/{id}`),
read-методы в `PlanRepository`/`PlanStopRepository`/
`PlanUnassignedRequestRepository`/`EngineerRepository`, DTO-проекции
`RequestDTO`/`EngineerDTO` (`src/core/db/dto/`, через `BaseDTO.from_orm` —
попутно почитал и почитал баг: `BaseDTO` был объявлен НЕ `frozen`, хотя все
остальные DTO проекта — `frozen=True`; наследование frozen-датакласса от
не-frozen физически падает `TypeError` в рантайме Python, не только у
mypy — никто раньше не наследовал `BaseDTO`, поэтому баг был скрыт;
исправлено в `src/core/db/dto/base.py`).

## Откуда берутся даты

`Request.window_start`/`window_end` — обещанное клиенту окно, как пришло из
Excel, не меняется планированием.

`PlanStop` хранит три штампа времени по остановке, все — заморожены на
момент построения плана (та же причина, что и для `travel_minutes`/
`distance_km`, см. `DATABASE.md`):

| Поле | Что значит |
|---|---|
| `planned_arrival` | когда инженер физически приехал на точку |
| `planned_start` | когда он реально **начал работу** — `max(planned_arrival, window_start)`: раньше окна начать нельзя, но приехать раньше и ждать можно |
| `planned_finish` | когда закончил — `planned_start + Request.norm_minutes_without_travel` |

`planned_arrival` и `planned_start` совпадают, только если инженер приехал
**после** открытия окна (ждать не пришлось); если приехал раньше — ждёт, и
`planned_start > planned_arrival`. UI показывает диспетчеру `planned_start`
(момент начала работы) — это то, что реально имеет значение, не факт
физического приезда.

Все три поля уже вычислялись алгоритмом (`Stop.arrival`/`.start`/`.finish` в
`src/core/algorithm/dto.py`, `materialize_route` в `shared/evaluate.py`) —
раньше при сохранении в БД `start`/`finish` терялись, сохранялся только
`arrival`. Исправлено без изменения логики алгоритма — только маппинг при
записи (`AlgorithmService.plan_initial`, `PlanStopRepository.add_many`).

## Юзеркейс — «Главный экран»

Диспетчер открывает главный экран → видит **текущий план** одного округа
(выбор округа — переключатель, вне скоупа этого документа) — запрос
`GET /api/plans/current?region=<округ>` (см. `DATABASE.md`, «какой план
сейчас актуален» — последний `Plan` этого `region` с `is_baseline=false`).
Один ответ содержит всё, что нужно обеим вкладкам сразу — переключение
Заявки/Инженеры не бьёт по бэку повторно.

### Вкладка «Заявки»

- Список заявок округа, сгруппированный в **8 сворачиваемых боксов**, в
  этом порядке: **авария → 10–12 → 12–14 → 14–16 → 16–18 → 18–20 → 20–22 →
  неназначенные**.
  - Правило попадания в бокс (в порядке проверки): заявка **не
    размещена** → бокс «неназначенные» (даже если это была авария — не
    задваиваем смысл, причина всё равно при ней); иначе `priority == 1`
    (авария) → бокс «авария», независимо от фактического времени; иначе —
    двухчасовой бокс по `planned_start`.
  - Смена по умолчанию — 10:00–22:00 (`cfg.planning`, см. ниже) — ровно
    совпадает с сеткой боксов, отдельный бокс «до 10:00» не нужен.
  - Внутри бокса — сортировка по `planned_start` ↑ (у «неназначенные» —
    такого поля нет, там сразу по адресу), при равенстве времени —
    по адресу (алфавит).
- На карте — точки **всех** заявок округа (флажки), независимо от бокса и
  статуса размещения.
- **Клик по тайлу заявки** → открывает полную карточку заявки (отдельный
  `GET /api/requests/{id}`, вне сегодняшнего скоупа) + на карте
  подсвечивается маршрут инженера, за которым она закреплена (если
  назначена).

### Вкладка «Инженеры»

- Список тайлов — **только инженеры, у которых есть хоть одна остановка в
  этом плане** (не все инженеры округа), отсортированы по `name`
  (фамилия) ↑.
- На карте по умолчанию — те же точки заявок, без маршрутов.
- **Клик по тайлу инженера** → карта перерисовывается на **только его**
  маршрут (полилиния: старт → стопы по `sequence_number`), под тайлом —
  список именно его заявок. Данные уже загружены в исходном ответе
  (`engineers[i].stops`) — фронт просто фильтрует, второго запроса не
  нужно. Маршруты остальных инженеров не показываются вообще (ни серым).

## Юзеркейс — «Экран планирования»

Отдельная страница (не модалка/дашборд, см. `SUMMARY.md`). Слева — список
всех планов округа, отсортированный по дате (`GET /api/plans?region=...`,
только шапки, без содержимого — превью, а не полные данные, чтобы не
тянуть сотни заявок ради списка из дат). Клик по конкретному плану в
списке → `GET /api/plans/{plan_id}` — тот же формат ответа, что и у
`current`, только под конкретный (в т.ч. исторический) план. Основная
область экрана рисуется тем же компонентом, что и главный экран (тот же
формат ответа — Заявки/Инженеры/карта).

## Эндпоинты — читаемые схемы (не JSON)

Общие строительные блоки, переиспользуются во всех трёх ответах.

**Тайл заявки** (`RequestTile`):
```
request_id        UUID
address            строка               адрес заявки
district           строка               район (справочно, для фильтров)
latitude           число                для точки на карте
longitude          число
window_start        дата-время           обещанное клиенту окно — начало
window_end           дата-время           обещанное клиенту окно — конец
priority             целое (1-3)          1 = авария
required_skill       enum                 см. Skill
planned_start        дата-время | null    заполнено, только если заявка назначена
planned_finish        дата-время | null    заполнено, только если заявка назначена
sequence_number        целое | null        номер остановки в маршруте её инженера (1, 2, 3…) —
                                             для нумерации точек на карте; null у неразмещённых
assigned_engineer      {engineer_id, name} | null   мини-карточка, только если назначена
unassigned_reason       enum | null        заполнено, только если НЕ назначена
```
(`planned_start`/`assigned_engineer` и `unassigned_reason` — взаимоисключающие
пары: у назначенной заявки первые два не-null, третье null, и наоборот.)

**Тайл инженера** (`EngineerTile`):
```
engineer_id          UUID
name                 строка               фамилия/имя бригады
vehicle_type          enum
shift_start            дата-время
shift_end               дата-время
start_latitude           число              точка старта (офис/"дом")
start_longitude           число
assigned_requests_count    целое
route_distance_km            число
stops                          RequestTile[]    его маршрут по порядку sequence_number,
                                                  те же поля, что и в общем списке заявок
```

### `GET /api/plans/current?region=<округ>`

Вход: `region` (обязательный query-параметр).

Ответ — один объект «план»:
```
id                      UUID
region                   enum
kind                      enum                initial/manual_replan/event_replan
is_baseline                 bool
created_at                    дата-время
based_on_plan_id                UUID | null
triggered_by_event_id             UUID | null
total_mileage_km                    число
engineers_used_count                  целое

request_groups                          8 групп, в фиксированном порядке — только
                                          ключ (не текст), подписи/иконки знает фронт:
  { group: "emergency",   requests: RequestTile[] }
  { group: "10-12",       requests: RequestTile[] }
  { group: "12-14",       requests: RequestTile[] }
  { group: "14-16",       requests: RequestTile[] }
  { group: "16-18",       requests: RequestTile[] }
  { group: "18-20",       requests: RequestTile[] }
  { group: "20-22",       requests: RequestTile[] }
  { group: "unassigned",  requests: RequestTile[] }

engineers                                  EngineerTile[], отсортированы по name ↑
```

Юзкейс: главный экран, дефолтная загрузка при выборе округа (см. выше).

### `GET /api/plans/{plan_id}`

Вход: `plan_id` (path).

Ответ — **тот же формат**, что у `current`, просто для конкретного
(в т.ч. исторического) плана, не обязательно последнего/актуального.

Юзкейс: экран планирования, клик по конкретному плану в списке слева.

### `GET /api/plans?region=<округ>`

Вход: `region` (обязательный query-параметр).

Ответ — список **шапок** планов (без заявок/инженеров), отсортирован по
`created_at` ↓ (новые сверху):
```
[
  {
    id                    UUID
    kind                   enum
    is_baseline              bool
    created_at                 дата-время
    engineers_used_count         целое
    total_mileage_km               число
  },
  ...
]
```

Юзкейс: экран планирования, левая панель — список планов округа, из
которого диспетчер выбирает, что открыть (см. выше).

## Ограничения текущей реализации

Работа с планами пока имеет следующие известные ограничения:

- **Не определена семантика частичного успеха по округам.** Импорт всех
  округов фиксируется до запуска алгоритма, а каждый успешно рассчитанный
  план коммитится отдельно. Если следующий округ завершится ошибкой, endpoint
  вернёт общий error, хотя данные импорта и планы предыдущих округов уже
  останутся в БД. Нужно явно выбрать атомарную операцию либо контракт
  частичного успеха с результатом по каждому округу.
- **Нет отдельного аудита результата алгоритма перед сохранением.** Рабочий
  поток не проверяет одним инвариантом, что каждая заявка встретилась ровно
  один раз — либо в маршруте, либо среди неназначенных; что все ID принадлежат
  нужной выгрузке; что маршруты не содержат дубликатов и разрывов нумерации.
  Ограничения БД покрывают только часть этих ошибок.
- **Фиксированные группы времени связаны с изменяемым конфигом.** HTTP-
  контракт задаёт интервалы `10-12` … `20-22`, но границы классификации
  вычисляются из `cfg.planning.default_shift_start/default_shift_end`.
  Конфигурация смены, отличная от 10:00–22:00, может породить отсутствующий
  enum-ключ и привести к ошибке чтения плана. Нужна валидация конфигурации
  либо другой контракт группировки.
- **Выбор текущего плана не имеет вторичного порядка.** При одинаковом
  `created_at` нескольких планов запрос не определяет, какой из них будет
  выбран. Нужен детерминированный tie-break.
- **Baseline-поток не реализован.** Модель и API поддерживают
  `is_baseline`, но первичное планирование сохраняет только оптимизированный
  план с `is_baseline = false`. Обязательное сравнение с базовым алгоритмом
  из ТЗ пока отсутствует.

## Открытые вопросы (не решено, не блокирует реализацию первых трёх ручек)

- Нужен ли в `EngineerTile` дополнительный признак/бейдж «этому инженеру
  назначена авария» для быстрого визуального сканирования списка (аварии
  и так видны внутри его `stops`, но не с первого взгляда на список
  тайлов)?
- `GET /api/requests/{id}`/`GET /api/engineers/{id}` реализованы как
  **plan-agnostic** карточки — отдают сырые поля `Request`/`Engineer` без
  привязки к конкретному плану (см. `src/api/requests/schemas.py`,
  `src/api/engineers/schemas.py`). Данные о назначении (кто/когда) уже есть
  в тайле, из которого был клик — не дублируются здесь намеренно, чтобы не
  плодить вопрос «относительно какого плана» при просмотре истории.
