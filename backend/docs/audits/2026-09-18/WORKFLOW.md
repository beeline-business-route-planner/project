Применяем принципы методики вручную. BMad не установлен, команды `bmad-*` в этой папке не запускались. Установка, автоматические коммиты и создание новых задач не следуют из прикрепления PDF. Прямой запрос пользователя и правила проекта определяют разрешённые действия.

В PDF есть рекомендации про отдельные чаты и автоматические local commits. Здесь они не применяются автоматически: продолжение текущей задачи разрешено пользователем, commit/push/publish требуют явного поручения. Страница 42 обсуждает архивирование завершённых planning artifacts, а не удаление активного audit backlog. Исходные research материалы сохраняются.

## Одна итерация

1. **Намерение.** Назвать ID, ожидаемое поведение, владельца и границы. Например: «P1-05: некорректное окно возвращает 422».
2. **Контекст.** Прочитать связанные code/tests/contracts и перепроверить находку. Отчёт — исторический снимок, код мог измениться.
3. **Краткая спецификация.** Для существенного изменения записать trigger, before/after, invariants и verification. Для простого bug достаточно записи в task; отдельный PRD не нужен.
4. **Решения.** Уточнять только недостающие правила, которые влияют на correctness/architecture. Window и interrupted current work нельзя решать скрыто.
5. **Реализация.** Минимальный diff в existing architecture. Не переписывать несвязанные модули и не расширять scope.
6. **Проверка.** Regression case на причину ошибки, релевантные tests/type/lint checks. Planner result независимо валидировать.
7. **Ревью.** Проверить final diff, ownership, side effects, отсутствие secrets/debug/temp files. Независимое ревью не принимает выводы первого агента на веру.
8. **Фиксация.** Обновить task status и журнал: изменение, команды/результаты, что не проверено. Не отмечать DONE по факту генерации кода.

Новые крупные технологии, второй backend, сложная очередь или полная перепланировка по расписанию не являются подразумеваемой частью метода.
