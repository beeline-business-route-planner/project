# Рабочая спецификация алгоритма планирования

## Статус документа

Документ фиксирует состояние обсуждения на 24 сентября 2026 года и нужен для продолжения
проектирования алгоритма в следующих сессиях. Это пока не окончательный технический
контракт.

Пометки:

- **[ПОДТВЕРЖДЕНО]** — правило явно подтверждено владельцем проекта в обсуждении;
- **[ИСТОЧНИК]** — правило уже содержится в ТЗ или актуальном user case;
- **[ИДЕЯ]** — текущая проектная гипотеза, которую ещё можно изменить;
- **[КОНФЛИКТ]** — новое решение расходится с существующим документом или архитектурой;
- **[ОТКРЫТО]** — точная семантика ещё не определена.

Источники:

- [технические ограничения](../../../docs/source_files/TECHNICAL_CONSTRAINTS.md) — выжимка
  официального ТЗ и ответов заказчика;
- [алгоритмический user case](../user-case/ALGORITHM.md) — текущий целевой контракт
  алгоритмической части;

расхождение отмечается явно. Канонические user-case до отдельного согласования не
переписываются.

## 1. Назначение алгоритма

**[ПОДТВЕРЖДЕНО]** Под «алгоритмом» в этом документе понимается не только конкретная
стратегия построения маршрута. Это вся самостоятельная подсистема планирования, которая:

1. получает необходимые данные;
2. рассчитывает или запрашивает матрицу времени и расстояний;
3. определяет допустимые для инженеров заявки;
4. распределяет заявки;
5. передаёт подготовленную задачу выбранной стратегии;
6. получает готовые маршруты;
7. сохраняет новый план;
8. возвращает backend результат, достаточный для формирования ответа frontend.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Пользователю после расчёта должен быть доступен сохранённый полный план,
а для replan — также вычисляемый backend-ом diff. Конкретная внутренняя форма возвращаемого
из алгоритма DTO сейчас не принципиальна, если итоговый API соответствует user case.

Источники: обсуждение 24.09.2026; алгоритмический user case, разделы 8 и 13; полный user
case, разделы 11–14.

## 2. Граница алгоритма и backend

### 2.1 Текущее решение владельца проекта

**[ПОДТВЕРЖДЕНО]** Алгоритмическая подсистема рассматривается как самостоятельный сервис.
Для initial она сама получает из БД обработанные backend-парсером заявки и инженеров. Для
replan и event replan она также сама получает из БД:

- актуальный план нужного округа за сегодняшний рабочий день;
- актуальные заявки и их статусы;
- актуальных инженеров и их доступность;
- остальные данные, необходимые конкретному режиму расчёта.

Во внешний вызов алгоритма не требуется передавать полный snapshot всех этих сущностей.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Алгоритмическая подсистема может обращаться к внешнему routing API,
например 2ГИС, чтобы получить время и расстояние между точками.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Алгоритмическая подсистема сама записывает рассчитанный полный план в БД.
Backend получает идентификатор и/или проекцию результата, читает сохранённый план, строит
API-представление и при необходимости вычисляет diff.

Источник: обсуждение 24.09.2026.

### 2.2 Зафиксированный архитектурный конфликт

**[КОНФЛИКТ]** Текущее решение выше расходится с задачами A01–A05 и актуальным
алгоритмическим user case. В них алгоритм описан как чистый вычислительный facade без ORM,
БД, routing I/O и `commit`, а загрузка, сохранение и lifecycle принадлежат backend
orchestration.

Перед реализацией нужно отдельно выбрать и закрепить одну границу ответственности:

1. самостоятельный алгоритмический сервис с БД, routing и сохранением плана;
2. чистое вычислительное ядро плюс внешняя orchestration-обёртка, которая работает с БД и
   routing;
3. единая публичная алгоритмическая подсистема, внутри которой I/O-обёртка вызывает чистое
   вычислительное ядро.

Вариант 3 сохраняет желаемую самостоятельность внешнего сервиса и одновременно позволяет
стратегиям оставаться чистыми и проверяемыми, но пока это только кандидат на решение.

Источники конфликта: обсуждение 24.09.2026; алгоритмический user case, разделы 1–2;
задачи A01 и A05.

## 3. Виды и режимы планирования

**[ПОДТВЕРЖДЕНО]** Есть три вида планирования:

1. `initial` — первичное планирование дня;
2. `replan` — обычное перепланирование;
3. `event_replan` — перепланирование из-за одного события.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 1.

**[ПОДТВЕРЖДЕНО]** Есть два режима распределения:

1. минимизация количества задействованных инженеров;
2. более равномерная загрузка доступных инженеров.

Источники: обсуждение 24.09.2026; командные решения; текущий `DistributionMode`.

**[ОТКРЫТО]** Для обоих режимов ещё не определена строгая целевая функция и порядок
оптимизационных критериев. Обязательные метрики ТЗ — число задействованных инженеров и
пробег, однако также необходимо учитывать приоритет и число назначенных заявок.

Источники: технические ограничения, раздел 7; обсуждение 24.09.2026.

## 4. Рабочий день, смены и окна

**[ПОДТВЕРЖДЕНО]** Алгоритм работает только с сегодняшним рабочим днём по Москве. Данные и
планы предыдущих дней при текущем планировании не используются.

Источники: обсуждение 24.09.2026; полный user case, разделы 3 и 5.

**[ПОДТВЕРЖДЕНО]** Общие границы операционного дня — с 10:00 до 22:00 по Москве.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Конкретный инженер не обязан работать всю смену 10:00–22:00. Его смена
может быть короче, но всегда находится внутри общих границ 10:00–22:00.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО С ТРАКТОВКОЙ]** Смены образуются двухчасовыми блоками: их границы должны
быть выровнены по двухчасовой сетке, а длительность должна быть кратна двум часам. Смена
10:00–15:00 недопустима.

Источник: обсуждение 24.09.2026.

**[ОТКРЫТО]** Нужно подтвердить допустимые границы явно: только ли это
`10:00, 12:00, 14:00, 16:00, 18:00, 20:00, 22:00`, или разрешено иное начало при чётной
длительности.

**[ПОДТВЕРЖДЕНО]** Обычные заявки имеют строгие двухчасовые окна вида `x — x + 2 часа`.

Источник: обсуждение 24.09.2026.

## 5. Семантика временного окна заявки

**[ПОДТВЕРЖДЕНО]** Инженер может приехать раньше начала окна и ждать.

**[ПОДТВЕРЖДЕНО]** Работы нельзя начать раньше `window_start`.

**[ПОДТВЕРЖДЕНО]** Если инженер приехал внутри окна, работа начинается в момент приезда.
Если инженер приехал раньше окна, работа начинается в `window_start`.

```text
planned_start = max(planned_arrival, window_start)
```

**[ПОДТВЕРЖДЕНО]** Начало работы обязано попасть в окно включительно:

```text
window_start <= planned_start <= window_end
```

**[ПОДТВЕРЖДЕНО]** Работа может закончиться после `window_end`. Клиентское окно ограничивает
время начала работ, а не время их завершения.

**[ПОДТВЕРЖДЕНО]** Работа должна закончиться не позже конца смены инженера.

```text
planned_finish = planned_start + service_minutes
planned_finish <= engineer.shift_end
```

Источники раздела: обсуждение 24.09.2026; технические ограничения, разделы 1 и 3;
алгоритмический user case, раздел 7.

**[ПОДТВЕРЖДЕНО]** Ожидание до открытия окна не считается ни работой, ни дорогой.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 11.

## 6. Время начала расчёта

В существующих user-case используется термин `calculation_cutoff_at`. Его смысл — единый
момент, отделяющий уже наступившее время от будущего, которое ещё разрешено планировать.

**[ПОДТВЕРЖДЕНО]** Во внешний вызов не обязательно передавать это значение. Алгоритм может
сам один раз в начале расчёта получить текущее московское время и использовать его во всех
последующих шагах этого запуска.

Источник: обсуждение 24.09.2026.

Чтобы избежать нескольких разных значений `now()` внутри одного расчёта, в дальнейшем
документе этот момент можно называть `calculation_started_at`. Это внутреннее значение
одного запуска, а не обязательно поле внешнего API.

**[ПОДТВЕРЖДЕНО]** Для расчёта нового будущего маршрута нельзя создавать действия раньше
момента начала расчёта.

**[ПОДТВЕРЖДЕНО]** При initial алгоритм не предполагает, что инженер уже находится в пути.
Начальная позиция инженера — стартовая точка округа, а доступное время начала движения:

```text
max(engineer.shift_start, calculation_started_at)
```

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 3.

**[ОТКРЫТО]** Нужно определить поведение, если initial запускается после начала смены:
считать ли инженера всё равно находящимся в офисе и доступным с текущего времени. Из
обсуждения следует именно это, но правило стоит подтвердить отдельно.

## 7. Заявки и приоритеты

**[ПОДТВЕРЖДЕНО]** Используется одна шкала приоритета от 1 до 3:

1. авария;
2. подключение;
3. ремонт или дозаказ.

Чем меньше число, тем выше приоритет.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 2.

**[ПОДТВЕРЖДЕНО]** Старые категории `urgent/normal` больше не используются и не являются
отдельным полем приоритизации.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Новая неаварийная заявка, пришедшая посреди дня, получает обычный
приоритет 1–3 согласно своему типу и участвует в event replan по общим правилам этого
приоритета.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Время обслуживания заявки берётся без фиксированного времени дороги.
Реальное время пути добавляется отдельно по routing matrix.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 2.

## 8. Аварии

### 8.1 Общие правила

**[ПОДТВЕРЖДЕНО]** Авария имеет высший приоритет.

**[ПОДТВЕРЖДЕНО]** Авария не обязательно должна стать самой ближайшей следующей задачей.
Её начало разрешено сдвинуть вперёд максимум на два часа, если это позволяет построить
более эффективный план.

Источник: обсуждение 24.09.2026; высший приоритет также задан техническими ограничениями.

**[ПОДТВЕРЖДЕНО]** Исходное техническое окно аварии `00:00–23:59` не означает, что её
можно выполнять ночью. Для планирования оно ограничивается операционным днём и сменой
конкретного инженера.

Источник: обсуждение 24.09.2026.

**[ОТКРЫТО]** Требуется формально определить начало двухчасового SLA аварии:

- для утренней аварии с окном `00:00–23:59` вероятный отсчёт начинается в 10:00;
- для аварии, пришедшей в течение дня, вероятный отсчёт начинается во время события;
- для инженера, чья смена начинается позже, возможен отсчёт от начала его смены.

Пока нельзя однозначно записать формулу `latest_start`, не выбрав одно из этих правил.

### 8.2 Авария, возникшая в течение дня

**[ПОДТВЕРЖДЕНО]** Нельзя мгновенно перенаправить на аварию инженера, который:

- уже едет к заявке;
- уже находится на заявке и выполняет работу.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Текущая заявка такого инженера фиксируется. Сначала инженер завершает
уже начатое обязательство, после чего авария может стать его следующей остановкой.

**[ПОДТВЕРЖДЕНО]** Остальной ещё не начатый хвост маршрута после зафиксированной заявки
разрешено перестроить. Поэтому после текущей заявки инженер может поехать на новую аварию,
а не на ранее запланированную следующую заявку.

**[ПОДТВЕРЖДЕНО]** На такую аварию также распространяется допустимый сдвиг до двух часов.

Источник: обсуждение 24.09.2026.

**[ОТКРЫТО]** Нужно решить, может ли алгоритм выбрать для аварии свободного инженера вместо
занятого, если свободный доберётся раньше или даст лучший план. Из обсуждения однозначно
следует запрет прерывать текущий путь/работу, но не следует запрет рассматривать свободных
инженеров.

## 9. Инженеры

**[ПОДТВЕРЖДЕНО]** «Бригада» в исходной терминологии — один инженер. В течение дня в
округе работает множество отдельных инженеров.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 1.

**[ПОДТВЕРЖДЕНО]** Стартовая точка инженера при initial — офис его округа.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Инженер не переключается между округами.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 1.

**[ПОДТВЕРЖДЕНО]** Возвращение в офис после последней заявки не рассчитывается и не нужно.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 5.

**[ПОДТВЕРЖДЕНО]** Учёт оборудования помимо транспортного ограничения пока не реализуется.

Источник: обсуждение 24.09.2026.

### 9.1 Транспорт

В текущем техническом референсе перечислены четыре значения: автомобиль, пешеход,
велосипед и общественный транспорт. В обсуждении отмечено, что исходное ТЗ может
подразумевать три транспорта, а пешеход фактически может пользоваться общественным
транспортом.

**[ОТКРЫТО]** Нужно проверить точный первоисточник и выбрать модель:

1. четыре взаимоисключающих типа;
2. три типа, где пеший инженер использует смешанный профиль
   «пешком + общественный транспорт»;
3. основной транспорт инженера плюс разрешённые способы перемещения;
4. единый приближённый профиль для всех неавтомобильных инженеров.

**[ОТКРЫТО]** Не решено, нужно ли строить две матрицы для пешего и общественного маршрута
и выбирать лучший путь. Это может быть слишком дорого для каждого расчёта.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 2.

## 10. Обязательные ограничения назначения

**[ПОДТВЕРЖДЕНО]** Заявка может быть назначена инженеру, только если требуемый навык входит
в навыки инженера.

**[ПОДТВЕРЖДЕНО]** Если заявка требует конкретный транспорт, транспортные возможности
инженера должны удовлетворять этому ограничению. Точная модель транспорта ещё открыта.

**[ПОДТВЕРЖДЕНО]** Путь до следующей заявки рассчитывается от фактической предыдущей точки
маршрута.

**[ПОДТВЕРЖДЕНО]** Один инженер не может выполнять пересекающиеся заявки.

**[ПОДТВЕРЖДЕНО]** Одна заявка не может быть назначена двум инженерам.

**[ПОДТВЕРЖДЕНО]** Инженер и заявка должны относиться к одному округу и одному рабочему
дню.

Источники: обсуждение 24.09.2026; технические ограничения, раздел 3;
алгоритмический user case, раздел 7.

## 11. Initial

**[ПОДТВЕРЖДЕНО]** Для initial алгоритмическая подсистема получает из БД обработанные
заявки и инженеров одного округа за сегодняшний день.

**[ПОДТВЕРЖДЕНО]** Затем она:

1. фиксирует текущее московское время одного запуска;
2. получает матрицу времени и расстояний;
3. строит допустимые пулы заявок для инженеров;
4. распределяет заявки в выбранном режиме;
5. вызывает выбранную стратегию построения маршрутов;
6. получает и проверяет полный результат;
7. сохраняет план;
8. возвращает backend идентификатор/результат сохранённого плана.

Источник: обсуждение 24.09.2026.

## 12. Replan и фиксация прошлого

**[ПОДТВЕРЖДЕНО]** При replan алгоритмическая подсистема сама получает из БД текущий план,
актуальные заявки, инженеров и статусы.

Источник: обсуждение 24.09.2026.

**[ПОДТВЕРЖДЕНО]** Уже прошедшие остановки не пересчитываются.

**[ПОДТВЕРЖДЕНО]** Не пересчитывается заявка, к которой инженер уже едет.

**[ПОДТВЕРЖДЕНО]** Не пересчитывается заявка, на которой инженер уже находится.

**[ПОДТВЕРЖДЕНО]** При определении зафиксированной части нужно учитывать не только время,
но и актуальный статус заявки.

Источник: обсуждение 24.09.2026.

Существующий user case считает остановку locked, если выполняется хотя бы одно условие:

- `planned_start` раньше времени начала расчёта;
- статус `on_the_way`;
- статус `in_progress`;
- статус `done`.

**[ИСТОЧНИК, ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]** Locked stop должен переноситься без изменения
инженера, заявки, порядка в прожитой части, arrival/start/finish, времени пути и расстояния.

Источник: алгоритмический user case, раздел 5.

**[ПОДТВЕРЖДЕНО]** Если инженер выбыл в течение дня, он не исчезает из нового полного
плана: уже выполненная/зафиксированная часть его маршрута сохраняется, а будущий маршрут
обрывается. Его ещё не начатые заявки возвращаются в общий пул.

Источник: обсуждение 24.09.2026.

**[ОТКРЫТО]** Полный процесс обычного replan владелец проекта опишет отдельно.

## 13. Event replan

**[ПОДТВЕРЖДЕНО]** Event replan является отдельным видом планирования, но использует общие
правила фиксации прошлого и перестройки будущего.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 6.

На данный момент известны события:

- новая авария или другая новая заявка;
- отмена заявки;
- инженер стал недоступен;
- инженер снова доступен.

**[ПОДТВЕРЖДЕНО]** Новое событие не позволяет изменить уже прошедшую, начатую или
находящуюся в пути часть плана.

**[ОТКРЫТО]** Детальный процесс event replan, кроме правил аварии и недоступного инженера,
будет описан владельцем проекта позже.

## 14. Текущая идея распределения заявок

### 14.1 Предварительные пулы

**[ИДЕЯ]** Сначала для каждого инженера строится собственный пул совместимых заявок.
Совместимость на этом этапе определяется как минимум по:

- округу и рабочему дню;
- навыку;
- транспортному ограничению;
- потенциальному пересечению смены и окна.

Одна заявка может одновременно находиться в пулах нескольких инженеров. Фактическое
назначение появляется только на следующем этапе.

Источник: обсуждение 24.09.2026; похожий подход используется текущим
`DistributionPlanner`.

**[ОТКРЫТО]** Владелец проекта допускает, что разбиение на независимые пулы на первом шаге
может оказаться тупиковым. Нужно сравнить его с глобальным распределением, которое
одновременно выбирает инженера и позицию заявки.

### 14.2 Порядок инженеров

**[ИДЕЯ]** Для режима минимального числа инженеров сначала рассматриваются инженеры с
наибольшим количеством совместимых заявок.

**[ИДЕЯ]** Для режима балансировки сначала рассматриваются инженеры с наименьшим
количеством совместимых заявок.

Источник: обсуждение 24.09.2026; именно такое приближение частично используется текущей
реализацией.

**[ОТКРЫТО]** Простая сортировка по размеру пула может не обеспечивать ни минимум
инженеров, ни реальный баланс. Возможные улучшения нужно обсуждать после полного описания
послойного графа и целевой функции.

### 14.3 Основная стратегия

**[ИДЕЯ]** Основное дальнейшее проектирование будет сосредоточено на послойном графе.

Источник: обсуждение 24.09.2026.

**[ОТКРЫТО]** Владелец проекта позже опишет ожидаемые слои, состояния, переходы, критерий
выбора пути и взаимодействие графа с распределением заявок между инженерами.

## 15. Результат и сохранение

**[ПОДТВЕРЖДЕНО]** После успешного расчёта полный план должен находиться в БД.

**[ПОДТВЕРЖДЕНО]** Backend должен иметь возможность вернуть frontend:

- карточку/summary плана;
- полную структуру плана;
- маршруты инженеров;
- назначенные и неназначенные заявки;
- метрики;
- для replan/event replan — diff с базовым планом;
- действия подтверждения или отклонения согласно lifecycle.

Источники: обсуждение 24.09.2026; полный user case, разделы 9–14.

**[ПОДТВЕРЖДЕНО]** Diff вычисляет backend, а не стратегия планирования.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 13.

**[ОТКРЫТО]** Точный DTO между алгоритмом и backend пока не определяется. Сначала нужно
зафиксировать поведение и границу ответственности.

**[ОТКРЫТО]** В обсуждении прозвучало, что план подтверждает «инженер», однако актуальный
user case задаёт единственного пользователя — диспетчера. До отдельного изменения
считается, что approve/reject выполняет диспетчер.

## 16. Причины неназначения

Текущий user case задаёт причины:

- `no_matching_skill`;
- `no_matching_vehicle`;
- `no_time_slot`;
- `no_available_engineer`.

**[ПОДТВЕРЖДЕНО]** Этот набор пока принимается.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 10.

**[ОТКРЫТО]** Не определена отдельная причина для недостижимой пары точек routing matrix.

## 17. Метрики

**[ПОДТВЕРЖДЕНО]** Загрузка без дороги:

```text
sum(service_minutes) / shift_minutes
```

**[ПОДТВЕРЖДЕНО]** Загрузка с дорогой:

```text
(sum(service_minutes) + sum(travel_minutes)) / shift_minutes
```

**[ПОДТВЕРЖДЕНО]** Ожидание окна в загрузку не входит.

Источники: обсуждение 24.09.2026; алгоритмический user case, раздел 11.

**[ОТКРЫТО]** Не подтверждён точный набор агрегатов округа: среднее по всем доступным,
среднее по задействованным, минимум, максимум и другие показатели.

## 18. Инварианты, которые пока сохраняются

Следующие правила уже содержатся в актуальном user case и не были опровергнуты в
обсуждении:

1. одна заявка назначается не более чем одному инженеру;
2. один инженер не выполняет пересекающиеся работы;
3. время пути считается от предыдущей фактической точки;
4. последовательность остановок инженера упорядочена;
5. назначенная заявка не должна одновременно присутствовать среди неназначенных;
6. новый replan хранит полный снимок дня, включая зафиксированную историю;
7. недоступный инженер не получает новые остановки;
8. результат должен быть детерминирован при одинаковых данных и routing matrix;
9. результат не должен нарушать навык, транспорт, окно и смену.

Источники: алгоритмический user case, разделы 7–9 и 16; обсуждение 24.09.2026.

## 19. Не включать без нового решения

**[ПОДТВЕРЖДЕНО]** Пока не реализуются:

- оборудование помимо транспорта;
- возврат инженера в офис;
- отдельные категории приоритета `urgent/normal`;
- ручное редактирование маршрута;
- работа с планами предыдущих дней в расчёте сегодняшнего дня.

Источники: обсуждение 24.09.2026; актуальные user-case.

## 21. Текущее состояние реализации

На момент создания документа код ещё не соответствует всем решениям выше:

- `AlgorithmService` уже читает БД, вызывает routing и сохраняет план;
- внутри него жёстко выбрана `LayeredExactStateGraph`;
- `DistributionPlanner` строит пересекающиеся пулы и обрабатывает инженеров
  последовательно;
- режимы отличаются в основном направлением сортировки инженеров по размеру пула;
- стратегия строит маршрут одного инженера, а не глобальный план округа;
- время initial начинается от начала смены и не фиксирует единое текущее московское время;
- полноценные replan и event replan отсутствуют;
- отдельный baseline отсутствует;
- общего аудита полного плана нет;
- послойный граф не гарантирует оптимальность при пересекающихся окнах.

Источник: текущий код `src/core/algorithm/` и `agents-docs/PROJECT_CONTEXT.md`. Последний
файл агентами не изменяется.
