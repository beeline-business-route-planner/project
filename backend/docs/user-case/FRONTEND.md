# Frontend-сценарии планирования

## 1. Цель

Frontend даёт диспетчеру понятную границу между рабочим утверждённым планом и любым
количеством рассчитанных предложений. Pending-план никогда не должен визуально выглядеть
как уже применённый.

## 2. Основная навигация

Сохраняются два основных контекста:

- **Главный экран** — только текущий approved-план выбранного округа и дня.
- **Экран планирования** — импорт, генерация, история, просмотр кандидатов, дифф,
  approve/reject и экспорты.

Экран планирования является отдельной страницей, а не модальным окном. При отсутствии
current главный экран показывает баннер с переходом, без автоматического редиректа.

## 3. Визуальный язык статусов

Каждая карточка плана явно показывает:

- `pending` — ожидает решения;
- `approved` — утверждён;
- `rejected` — отклонён/вытеснен/протух;
- отдельный бейдж `Текущий`, если approved является current.

Цвет не должен быть единственным носителем смысла: статус сопровождается текстом и/или
иконкой.

Pending-карточка содержит время расчёта. Правило актуальности initial ещё должно быть
спроектировано. Если для MVP останется временный TTL-fallback, карточка дополнительно
показывает полученный от backend дедлайн и обратный отсчёт; клиент не вычисляет 10 минут
самостоятельно. Истечение таймера на клиенте не заменяет серверную проверку.

## 4. Пустое состояние дня

Если `GET current` не находит approved-план:

- карта/рабочий список не подменяются pending-кандидатом;
- показывается сообщение «Рабочий план на сегодня не утверждён»;
- доступна кнопка перехода на планирование;
- replan и event replan недоступны;
- доступен initial upload.

## 5. Первичное планирование

### 5.1 Загрузка

Диспетчер выбирает пары Excel: отдельную книгу заявок и отдельную книгу доступных инженеров
для каждого округа. UI до отправки проверяет расширение и число файлов, но сервер остаётся
источником истины по роли и округу файла. `Синтетические данные.xlsx` — штатный реальный
источник заявок. UI и backend не определяют назначение книги по исходному имени файла:
backend классифицирует её по обязательным колонкам и игнорирует лишние поля. Книги
контрольного распределения не подходят под схему книги инженеров: это справочные примеры
ручного плана, а не входные данные.

После запуска показывается единый progress для запроса. HTTP остаётся открытым до
завершения расчёта.

### 5.2 Частичный результат

Ответ может содержать успехи и ошибки разных округов. UI создаёт вкладки/карточки:

- успешный округ — summary pending initial;
- неуспешный — сообщение с серверным error detail и возможность повторить действие;
- успешные результаты не скрываются из-за ошибки соседнего округа.

### 5.3 Просмотр и решение

Клик по успешному округу вызывает `GET /plans/{id}` и открывает полный план. У initial нет
диффа. Доступны:

- `Утвердить`;
- `Отклонить`;
- `Скачать Excel`.

После approve/reject фронт повторно загружает список планов округа, потому что статусы
остальных pending могли автоматически измениться на rejected.

Если initial протух локально или сервер вернул expiry conflict, кнопка approve скрывается,
план перечитывается, пользователю предлагается новый расчёт.

## 6. Обычный replan нескольких округов

Диспетчер выбирает произвольный непустой набор округов с current-планами и запускает
пересчёт.

После ответа:

- показываются кнопки/вкладки только запрошенных округов;
- каждая вкладка имеет собственный success/error;
- выбор успешной вкладки лениво загружает detail + diff;
- переход между вкладками вызывает чтение соответствующего plan ID или использует
  безопасный клиентский cache последнего GET;
- approve/reject действует только на текущую открытую вкладку;
- решение по одному округу не меняет решения соседних округов.

## 7. Event replan

Форма события меняется по типу:

- urgent request — полный набор полей новой заявки;
- request cancelled — выбор существующей активной заявки;
- engineer unavailable — выбор доступного инженера;
- engineer available — выбор недоступного инженера.

Время события не редактируется и не показывается как пользовательский input: сервер
фиксирует его при создании.

Пока у округа есть pending-событие:

- создание другого события для округа заблокировано;
- UI предлагает открыть существующий pending event plan;
- обычные карточки истории продолжают быть доступны.

Если расчёт события упал, event/plan на сервере отсутствуют; UI возвращает заполненную форму
и позволяет повторить отправку.

## 8. Экран истории

Список планов выбранного округа:

- сортируется по `created_at DESC`;
- показывает все статусы;
- показывает вид `initial/replan/event_replan`;
- показывает рабочую дату и время расчёта;
- для approved показывает время утверждения;
- для rejected показывает время отклонения;
- current выделяется отдельно;
- карточка содержит основные метрики и counts.

Фильтры по статусу/виду не обязательны в MVP. Округ — обязательный переключатель.

Pending-план можно оставить без действия: это и есть «отложить». Специальной кнопки и
четвёртого статуса нет.

## 9. Полная карточка плана

Компонент основной области переиспользуется для current и исторических планов.

### 9.1 Заявки

Группы в фиксированном порядке:

1. авария;
2. 10–12;
3. 12–14;
4. 14–16;
5. 16–18;
6. 18–20;
7. 20–22;
8. неназначенные.

Неназначенная авария находится только в `unassigned`. Назначенные сортируются по
`planned_start`, затем адресу; неназначенные — по адресу.

Показываются минимум:

- адрес и район;
- окно;
- приоритет и навык;
- planned start/finish;
- инженер;
- номер остановки;
- причина неназначения.

### 9.2 Инженеры

В списке только инженеры с остановками в плане. Для каждого:

- имя и транспорт;
- смена;
- число заявок;
- пробег;
- загрузка с дорогой и без неё;
- упорядоченные stops.

### 9.3 Карта

- По умолчанию видны точки всех заявок без всех маршрутов одновременно.
- Выбор заявки рисует маршрут назначенного инженера.
- Выбор инженера рисует только его маршрут.
- Полилиния начинается со стартовой точки и идёт по `sequence_number`.
- Кластеризация близких заявок выполняется на frontend.

## 10. Дифф

Дифф показывается только у replan/event replan.

### 10.1 Сводка

Верхняя часть сравнивает before/after/delta:

- назначенные/неназначенные заявки;
- задействованные инженеры;
- общий пробег;
- загрузку с дорогой и без неё.

### 10.2 Инженеры

Список содержит всех инженеров диффа:

- добавлен;
- удалён;
- изменён;
- без изменений.

Карточка инженера раскрывается и показывает список заявок. Фронт не вычисляет бизнес-дифф
самостоятельно, а отображает серверные `change/changes/before/after`.

### 10.3 Заявки

Для заявки одновременно возможны несколько бейджей:

- добавлена;
- удалена;
- переназначена;
- изменён порядок;
- изменено время;
- изменились дорога/километраж;
- изменилась причина неназначения;
- без изменений.

Для изменённых значений UI показывает две колонки «Было» и «Стало». У добавленной заявки
нет before, у удалённой нет after. Неизменённые заявки не скрываются: диспетчер должен
видеть целостный маршрут и понимать, что часть осталась прежней.

### 10.4 Карта диффа

Минимальный MVP может отображать карту нового плана и подсветку изменённых точек. Нельзя
рисовать все старые и новые маршруты одновременно без управления слоями: это создаёт
визуальный шум. Полный двухслойный map diff является улучшением, а не обязательным
условием первого релиза.

## 11. Approve/reject UX

### Approve

- Требуется подтверждение действия.
- Во время запроса обе кнопки блокируются.
- После успеха показывается новый current и перечитывается список.
- При 409 detail перечитывается; UI объясняет, что план устарел, протух или разошёлся с
  фактическим состоянием.
- Клиент не предлагает «повторить approve» без перечитывания.

### Reject

- Причина не запрашивается.
- После подтверждения plan становится rejected.
- Для event replan событие также исчезает из pending-состояния.
- Рабочий current не меняется.

Approved нельзя отклонить, rejected нельзя утвердить. Frontend скрывает невозможные
действия, но backend всё равно валидирует состояние.

## 12. Главный экран после approve

После утверждения:

1. экран планирования обновляет history;
2. при переходе на главный экран вызывается `GET current`;
3. отображается новый approved-план;
4. pending/rejected варианты не влияют на карту и рабочие списки.

## 13. Экспорт Excel

Кнопка доступна для любого плана, включая pending/rejected/исторический approved.

Frontend вызывает export endpoint, получает presigned URL и инициирует скачивание. Во
время генерации показывается отдельный progress. Дифф в книге отсутствует.

## 14. Дневной отчёт

Форма содержит рабочую дату. Отчёт можно запросить в середине дня.

Backend возвращает ссылку на ZIP, внутри которого:

- `summary.pdf`;
- по одному PDF на каждый округ, имеющий утверждённый план за дату.

UI сообщает, что это плановый отчёт. Если дата сегодняшняя и день не завершён, показывает
предупреждение «Отчёт сформирован на текущий момент».

Pending и rejected варианты в отчёт не попадают.

## 15. Ошибки и восстановление

| Ситуация | Поведение UI |
|---|---|
| Partial success | Показать успешные вкладки и локальные ошибки соседних округов. |
| Initial уже утверждён | Запретить новый upload округа, обновить history/current. |
| Initial протух | Обновить статус, предложить новый расчёт. |
| База replan сменилась | Обновить history/current, предложить новый replan. |
| План разошёлся с фактом | Показать конфликт и предложить пересчитать. |
| Уже есть pending event | Дать ссылку на существующий event plan. |
| Неверный переход события | Обновить доступные цели формы. |
| Routing/geocoding unavailable | Сохранить введённые данные формы, позволить повторить. |
| Export unavailable | Не менять состояние плана, позволить повторить экспорт. |

## 16. Клиентское состояние

Frontend не должен самостоятельно решать, какой план current, вычислять статус события,
просрочку initial или применимость approve. Сервер возвращает готовые признаки и является
источником истины.

Допустимый cache detail привязан к `plan_id`. После approve/reject перечитываются history и
current, потому что несколько summaries могли сменить статус одной транзакцией.

## 17. Доступность и форматирование

- Время показывается в московском часовом поясе.
- Decimal не преобразуется с неконтролируемой потерей точности.
- Before/after доступны не только через цвет.
- Pending/approved/rejected имеют текстовые подписи.
- Большие списки сворачиваются по инженерам/группам, но при масштабе до 100 заявок серверная
  пагинация detail/diff не требуется.

## 18. Вне MVP

- Ручное перетаскивание заявок между инженерами.
- Force approve устаревшего плана.
- Отдельная страница журнала событий.
- Пользовательское время события.
- Одновременная очередь нескольких событий округа.
- Фактический dashboard исполнения и история статусов.
- Повторный Excel-import после approved initial.
