# Алгоритмический контракт initial, replan и baseline

## 1. Роль алгоритмической подсистемы

Алгоритм получает подготовленный снимок одного округа и возвращает полный проверяемый
план. Он не утверждает план, не выбирает current, не меняет approval status и не управляет
HTTP. Жизненным циклом владеют API-доменные сервисы.

Основной алгоритм решает три задачи:

- initial — построить первый план дня;
- replan — сохранить прожитое прошлое и пересчитать допустимое будущее;
- event replan — сделать то же с учётом одного pending-события.

Baseline реализуется отдельно и не является стратегией рабочего планирования.

## 2. Общие входные данные

Для одного вызова передаются:

- `region` и `planning_date`;
- `calculation_cutoff_at` — серверное время, относительно которого определяется прошлое;
- заявки округа;
- инженеры округа;
- навыки и транспорт;
- смены и стартовые точки;
- актуальная матрица времени/расстояний;
- режим распределения;
- для replan — полный утверждённый базовый план;
- для event replan — одно событие и его payload;
- текущие статусы заявок;
- утверждённое состояние доступности инженеров.

Все даты относятся к одному московскому рабочему дню.

## 3. Временной срез

Алгоритм не планирует новые действия раньше `calculation_cutoff_at`.

Для initial:

- инженер считается способным начать путь не раньше cutoff;
- ранняя часть смены до cutoff недоступна;
- заявка, окно которой уже нельзя соблюсти после cutoff, становится неназначенной с
  подходящей причиной;
- результат не может содержать остановку в прошлом.

Для replan/event replan cutoff делит день на:

- заблокированную историю;
- пересчитываемый будущий хвост.

Временной срез фиксируется один раз на use-case и передаётся явно. Стратегия не вызывает
`now()` самостоятельно в разных местах.

## 4. Initial

Initial работает только с одной версией upload одного округа.

Этапы:

1. загрузить заявки и инженеров версии;
2. исключить заведомо недопустимые сочетания по навыку и транспорту;
3. построить матрицу;
4. распределить заявки;
5. секвенировать маршрут каждого инженера;
6. материализовать arrival/start/finish/travel/distance;
7. классифицировать каждую неназначенную заявку;
8. рассчитать плановые метрики;
9. выполнить аудит результата;
10. вернуть полный результат без изменения lifecycle.

Initial считается рассчитанным для текущего cutoff. Актуальность кандидата при позднем
approval проверяет сервис жизненного цикла, а не стратегия. Фиксированный TTL 10 минут —
только временная MVP-эвристика: окончательное правило должно быть спроектировано отдельно
и учитывать, остаётся ли маршрут выполнимым на момент утверждения.

## 5. Replan

### 5.1 Определение locked stops

Stop блокируется, если выполняется хотя бы одно:

- `planned_start < calculation_cutoff_at`;
- заявка имеет статус `on_the_way`;
- заявка имеет статус `in_progress`;
- заявка имеет статус `done`.

Заявки со статусом `cancelled` не возвращаются в будущую часть. Если отмена относится к уже
прожитой остановке, историческая строка сохраняется как часть полного снимка дня, а её
статус показывается отдельно.

### 5.2 Копирование истории

Locked stops копируются без изменений. Запрещено пересчитывать для них:

- инженера;
- порядок в прожитой части;
- arrival/start/finish;
- travel minutes;
- distance;
- факт назначения.

Новый план остаётся полным: locked history + новый future tail.

### 5.3 Начальная позиция будущего хвоста

Для каждого инженера пересчитываемый хвост начинается:

- после его последнего locked stop — из координат этой заявки и после её finish;
- из исходной стартовой точки и не раньше cutoff, если locked stops нет.

Алгоритм не предполагает телепортацию инженера в офис при replan.

### 5.4 Кандидаты на пересчёт

В future pool входят:

- ещё не начатые stops базового плана;
- ранее неназначенные активные заявки;
- заявки, добавленные допустимым event;
- остальные активные заявки дня, которые должны присутствовать в полном покрытии.

Не входят:

- done;
- cancelled;
- заявки locked history как повторные кандидаты;
- заявки/инженеры другого округа или дня.

## 6. Event replan

Event replan использует тот же механизм replan, затем применяет временный вход события к
расчётному снимку.

### `urgent_request`

- Добавить новую заявку в future pool.
- Приоритет/норматив/окно берутся из валидированного payload.
- Она не может появиться в locked history.

### `request_cancelled`

- Удалить отменённую заявку из future pool.
- Если она уже locked, историю не переписывать.

### `engineer_unavailable`

- Инженер не получает новые future stops.
- Его незаблокированные заявки возвращаются в общий pool.
- Locked history сохраняется.

### `engineer_available`

- Инженер снова участвует в распределении будущего хвоста.
- Его стартовая позиция/время определяются подтверждённой историей дня и cutoff.

Событие становится операционным фактом только после approve плана. До этого алгоритм
использует его как вход кандидата, но не меняет постоянное состояние инженера/заявки.

## 7. Обязательные ограничения

Для каждого нового назначения:

1. навык заявки входит в навыки инженера;
2. требуемый транспорт совпадает, если ограничение задано;
3. начало работы не раньше `window_start` и не позже `window_end`;
4. finish не выходит за смену;
5. путь считается от фактической предыдущей точки маршрута;
6. инженер не назначается в два пересекающихся места;
7. одна заявка не назначается двум инженерам;
8. округ и рабочий день совпадают.

Инженер может приехать раньше окна и ждать. В UI главным временем остаётся planned start.

## 8. Результат основного алгоритма

Результат содержит:

- маршруты всех задействованных инженеров;
- упорядоченные stops;
- locked marker;
- assigned request IDs;
- unassigned request IDs и причины;
- общий пробег;
- число задействованных инженеров;
- counts assigned/unassigned;
- загрузку с дорогой и без неё;
- диагностические безопасные агрегаты для аудита.

Стратегия не возвращает ORM и HTTP schemas.

## 9. Аудит перед сохранением

Отдельная проверка результата обязательна. Она доказывает минимум:

- каждая активная заявка встретилась ровно один раз: assigned xor unassigned;
- нет неизвестных request/engineer IDs;
- все ID принадлежат нужному округу/дню;
- sequence numbers каждого маршрута уникальны и непрерывны;
- времена stop монотонны и согласованы с travel/service;
- соблюдены окна и смены;
- соблюдены навыки/транспорт;
- locked stops равны базовому плану;
- отсутствуют назначения недоступным инженерам;
- агрегаты совпадают с суммой stops/routes;
- нет stop и unassigned для одной заявки одновременно.

При провале аудита план не сохраняется.

## 10. Причины неназначения

Сохраняются согласованные причины:

- `no_matching_skill`;
- `no_matching_vehicle`;
- `no_time_slot`;
- `no_available_engineer`.

Классификация должна быть детерминированной. Replan не должен менять причину locked
истории, но может изменить причину активной неназначенной заявки в новом снимке.

## 11. Плановая загрузка

Для инженера:

```text
without_travel = sum(service_minutes) / shift_minutes
with_travel    = (sum(service_minutes) + sum(travel_minutes)) / shift_minutes
```

Ожидание окна не считается работой или дорогой. Метрики возвращаются как доля/Decimal с
однозначным последующим форматированием процентов.

Агрегаты округа считаются:

- по всем доступным инженерам;
- отдельно по задействованным;
- min/max;
- used/available counts.

## 12. Baseline-алгоритм

### 12.1 Назначение

Baseline нужен исключительно для контрольного сравнения, требуемого официальным ТЗ. Это
отдельная реализация, а не флаг рабочего алгоритма и не одна из оптимизационных стратегий.

### 12.2 Правила

1. Заявки идут в стабильном входном порядке.
2. Инженеры идут в стабильном входном порядке.
3. Для заявки выбирается первый инженер, который проходит статические ограничения и может
   вставить заявку в конец уже набранного маршрута без нарушения времени.
4. Порядок маршрута равен порядку назначения.
5. Нет глобального поиска, перестановок, балансировки, ruin/recreate и сравнения вариантов.
6. Неназначение классифицируется теми же публичными причинами.

### 12.3 Сопоставимость

Baseline initial и основной initial получают:

- одну версию заявок/инженеров;
- один region/day;
- одинаковый cutoff;
- одну матрицу маршрутизации или эквивалентный зафиксированный снимок;
- одинаковые нормативы и обязательные ограничения.

Иначе сравнение метрик нечестно.

### 12.4 Сохранение

Полные baseline routes нужны во время расчёта и аудита, но рабочие Plan/PlanStop не
создаются. В `BaselineResult` сохраняются агрегаты сравнения и версия реализации.

Baseline запускается только для initial. Replan/event replan его не используют.

## 13. Дифф не является задачей оптимизатора

Алгоритм возвращает новый полный план. Дифф строит отдельный чистый presenter по двум
сохранённым планам. Стратегии не должны маркировать `added/removed/reassigned` и не должны
знать API-форму диффа.

## 14. Поздний approve

Алгоритм не выполняет approve-check, но обязан сохранить достаточно данных:

- cutoff;
- locked flags;
- полный снимок;
- frozen stop values;
- base plan ID через вызывающий сервис.

Сервис затем может определить, ушло ли изменение в прошлое и совпадает ли locked history.

## 15. Несколько округов

Один алгоритмический вызов обрабатывает один округ. Мультиокружный planning service вызывает
его независимо и собирает региональные результаты. Ошибка одного вызова не должна портить
уже проверенный результат другого.

Не использовать один `AsyncSession/UnitOfWork` конкурентно в нескольких корутинах.

## 16. Производительность и детерминизм

При одинаковом входе, cutoff и матрице результат должен быть воспроизводимым. Все
tie-breakers задаются явно. Нельзя полагаться на неупорядоченный set/dict или случайный seed
без фиксации.

Масштаб MVP: до 100 заявок и примерно 10–15 инженеров. Отсутствие пагинации API не снимает
требование ограничивать бюджет алгоритма.

## 17. Известные алгоритмические ограничения

Сохраняются ограничения существующей подсистемы:

- текущая рабочая стратегия не гарантирует оптимум при пересекающихся окнах;
- транспортные профили требуют отдельной корректной политики;
- недостижимая пара точек требует согласованной причины неназначения;
- manual force-edit отсутствует;
- фактические GPS-позиции инженеров не собираются, поэтому replan исходит из подтверждённой
  плановой истории.

Эти ограничения не разрешают нарушать locked history или сохранять неаудированный план.

## 18. Обязательные сценарии проверки

1. Initial в 10:12 не содержит stop раньше 10:12.
2. Initial и baseline получают одинаковый cutoff/input.
3. Replan в 16:00 копирует всё прошлое и пересчитывает только будущее.
4. On-the-way/in-progress/done остаются locked независимо от planned time.
5. Выбывший инженер теряет future tail, но сохраняет history.
6. Вернувшийся инженер участвует только в будущем.
7. Отмена future request удаляет её из маршрута.
8. Срочная заявка участвует с корректным приоритетом.
9. Каждая заявка assigned xor unassigned.
10. Итоговый новый plan полностью описывает день.
11. Метрики совпадают с маршрутами.
12. Audit отклоняет дубликаты, разрывы порядка и изменение locked stop.
