# Алгоритмический контракт и поведение планирования

## 1. Граница подсистемы

Алгоритм — чистая вычислительная подсистема `src/core/algorithm`. Он получает неизменяемый
snapshot одного округа и возвращает полный проверенный результат. Внутри алгоритма запрещены:

- чтение и запись БД, `commit` и ORM-модели;
- HTTP-вызовы геокодера и routing-провайдеров;
- получение текущего времени;
- approval/current/lifecycle-решения;
- построение HTTP-схем.

Зависимости пакета — только стандартная библиотека, `cfg` и закрытые перечисления
`src.core.db.enums`.

API-domain orchestration фиксирует `calculation_cutoff_at`, передаёт алгоритму сырой
snapshot, получает у routing-провайдера запрошенные алгоритмом матрицы, вызывает расчёт и
сохраняет результат одной транзакцией. Нормализация окон и аварий, фиксация прожитой
истории, применение события, разбиение на слои и выбор точек матриц принадлежат алгоритму,
чтобы orchestration не повторяла алгоритмическую логику.

Публичный контракт `AlgorithmService`:

```text
prepare_initial(InitialPlanningSnapshot)            -> InitialPlanningDraft
build_initial_input(draft, [LayerMatrix, ...])      -> InitialPlanningInput
plan_initial(InitialPlanningInput, variant)         -> InitialPlanningResult
plan_baseline(InitialPlanningInput)                 -> InitialPlanningResult
plan_initial_diagnosed(InitialPlanningInput, variant)

prepare_replan(ReplanSnapshot)                      -> ReplanDraft
prepare_event_replan(ReplanSnapshot, ReplanEvent)   -> ReplanDraft
build_replan_input(draft, [LayerMatrix, ...])       -> ReplanInput
plan_replan(ReplanInput, variant)                   -> ReplanResult
```

`prepare_*` возвращает черновик с эффективными окнами и списком `LayerMatrixRequest`.
Orchestration не интерпретирует запрос: передаёт провайдеру `traffic_reference_at`, тип
транспорта, `source_ids` и `target_ids` и возвращает матрицу вместе с исходным запросом.
Replan и event replan отличаются только подготовкой: `prepare_event_replan` сначала
применяет событие к snapshot, дальше расчёт общий.

Backend вызывает один фасад и не знает внутреннего устройства стратегии. Стратегия
выбирается значением `AlgorithmVariant`, которое совпадает с сохраняемым `PlanStrategy`.

## 2. Цели и жёсткие ограничения

План обязан соблюдать:

1. округ и рабочий день;
2. доступность, смену, навык и транспорт инженера;
3. эффективное окно начала заявки;
4. завершение работы до конца смены;
5. физическую последовательность пути без пересечений и телепортации;
6. назначение заявки максимум одному инженеру;
7. SLA аварии;
8. неизменность прожитой истории при replan.

После hard constraints решения сравниваются лексикографически:

1. суммарный score приоритета назначенных заявок (авария весит больше любого реалистичного
   числа обычных заявок, см. §6.1);
2. число назначенных заявок;
3. цель режима распределения (§8);
4. суммарная дорога;
5. детерминированный tie-breaker по UUID.

Это иерархия целей, а не сумма случайных коэффициентов. Минуты, километры и приоритет не
складываются в одну величину. Эвристическая реализация не объявляет найденное решение
математически оптимальным, но каждый кандидат проходит одинаковую материализацию и
независимый аудит.

Альтернативное правило «аварии → покрытие → приоритет» измерено (отчёт сессии 25.09,
вопрос 5.2), но не принято: код использует порядок выше.

## 3. Вход initial

Вход содержит:

- `region`, `planning_date`, единый `calculation_cutoff_at`;
- нормализованные заявки;
- инженеров и их стартовое состояние;
- режим `min_engineers` или `balanced`;
- временные слои и отдельные routing matrix слоя для используемых типов транспорта;
- известные решения (`known_solutions`) — только у хвоста replan.

У заявки отдельно хранятся:

- исходные `source_window_start/source_window_end` для аудита;
- эффективные `release_at/latest_start_at`, ограничивающие начало работ;
- норматив чистой работы без фиксированного времени дороги;
- приоритет, навык, транспорт и признак аварии.

У инженера кроме смены, навыков и транспорта хранятся `available_from` (не раньше cutoff и
конца прожитой истории) и `history_service_minutes` — работа в прожитой истории дня.

## 4. SLA аварии

Для аварии два часа (`emergency_response_minutes = 120`) — время реагирования: работу нужно
начать не позже дедлайна, закончить можно позже, но в пределах смены. Правило одно для
initial, replan и события:

```text
received     = момент поступления заявки (RequestSnapshot.received_at, иначе cutoff)
sla_start    = max(window_start, received, начало операционного дня 10:00)
если sla_start + 120 < cutoff:        # SLA истёк, а авария всё ещё в пересчитываемом пуле
    sla_start = cutoff                 # выполнить как можно раньше, а не отбросить
если sla_start <= window_end:
    release_at      = sla_start
    latest_start_at = min(window_end, sla_start + 120)
иначе:
    окно остаётся исходным, и авария честно не назначается
```

Следствия:

| Ситуация | Окно начала работ |
|---|---|
| авария «на весь день» (`00:01–23:59`), initial до 10:00 | `10:00–12:00` |
| то же, initial в 11:05 | `11:05–13:05` |
| авария с клиентским окном 15–17, initial утром | `15:00–17:00` |
| срочная авария-событие в 13:45, окно «на весь день» | `13:45–15:45` |
| запланированная авария при replan | исходный дедлайн от момента поступления |
| незапланированная авария, SLA истёк к replan | `cutoff … cutoff+120` в пределах клиентского окна |

Момент поступления задаёт orchestration: для заявок из загрузки — cutoff утверждённого
initial, для срочной заявки — `occurred_at` её события. При initial он равен cutoff.

Авария имеет высший приоритет, но не обязана быть первой в маршруте: до неё допустимы
обычные заявки, если материализация даёт её начало в SLA. Отдельной причины «SLA истёк» нет:
такая авария получает `no_time_slot`.

## 5. Временные слои и routing matrix

Слой объединяет заявки с одним эффективным окном `(release_at, latest_start_at)`. Сетка
10–12, 12–14… не требуется: окно аварии `13:45–15:45` образует собственный слой. Порядок
слоёв в маршруте — по началу окна; заявку более позднего слоя нельзя поставить перед
заявкой более раннего. Внутри слоя порядок свободный.

Для окна `10:00–12:00` провайдеру передаётся `departure_at = 11:00` — опорное время прогноза
пробок, а не плановый выезд инженера. У каждого слоя собственная матрица на каждый
используемый тип транспорта. Переход в заявку оценивается по матрице слоя этой заявки и
транспорта назначенного инженера.

Матрица слоя не квадратная матрица округа: `targets` — заявки слоя, `sources` — стартовые
точки инженеров этого транспорта и заявки всех слоёв, начинающихся не позже текущего
(включая соседние слои с тем же началом окна: переход между ними допустим в обе стороны).
Слои с более поздним началом не включаются. Сокращать `sources` до заранее выбранных хвостов
нельзя: до запуска графа неизвестно, какие точки останутся во frontier.

Недостижимая пара (`None` в матрице) делает переход невыполнимым; заявка без единого
достижимого перехода получает причину `no_route`, округ при этом не падает.

Провайдер матриц выбирается `cfg.travel_matrix.provider`: `osrm` (без пробок, одна матрица
«все со всеми» на тип транспорта; общественный транспорт оценивается по дорожному расстоянию,
средней скорости и ожиданию) или `dgis` (матрица на каждый запрос с прогнозом пробок).

## 6. Построение плана

### 6.1 Распределение и порядок

Стратегии (`AlgorithmVariant` = `PlanStrategy` для рабочих планов):

- `lns` — стратегия по умолчанию в API;
- `layered_graph` — точный послойный граф с глобальным selector;
- `greedy` — быстрая последовательная вставка без графа;
- `baseline` — официальный контрольный алгоритм, только для сравнения, не `Plan`.

Все стратегии используют одни DTO, hard constraints, материализацию и аудит. Результат
детерминирован: при одинаковом snapshot и матрицах он не зависит от порядка входных
коллекций (кроме `baseline`, который по ТЗ зависит от входного порядка).

**`layered_graph`.** Для каждого доступного инженера по его совместимому пулу строится
точный граф достижимых состояний по слоям. Состояние — маска посещённых заявок слоя,
последняя точка, время завершения, дорога, score приоритета и порядок. Ребро существует,
только если начало не позже `latest_start_at` и окончание не выходит за смену. Внутри слоя
состояния с одинаковой маской, последней точкой, числом заявок и score сравниваются по
`(finish, travel)`; после слоя — доминирование по `(priority_score, assigned_count, finish,
travel)` для каждой последней точки. Граф отдаёт ограниченный набор недоминируемых
`RouteCandidate` (`route_candidates_per_engineer = 48`), дополненный маршрутами baseline,
greedy, priority-aware append seed и известных решений. Branch-and-bound selector
(`selection_node_budget`) выбирает не больше одного кандидата на инженера без повторов
заявок, затем `route_candidate_improvement_rounds = 2` best-response раунда добавляют новые
колонки и selector запускается снова. Граф точен для одного инженера при заданном пуле;
выбор по округу точен только относительно сгенерированных колонок.

**`lns`.** Старт — лучший из greedy, точной фазы аварий и допустимых известных решений.
Точная фаза аварий (`EmergencyPlanner`) находит максимальное число аварий, выполнимых в SLA:
динамика по наборам аварий на бригаду плюс branch-and-bound с отсечением симметрии
(`emergency_phase_state_budget`). Далее `lns_iterations = 95` итераций: оператор разрушения
(`random`, `related`, `route`, `time_window`, `string`, `worst`) снимает часть заявок,
regret-вставка возвращает снятые и свободные, маршрут каждого изменённого инженера
переоптимизируется точным графом. План принимается, если приоритет, покрытие и цель режима не
хуже, а дорога хуже не более чем на убывающий порог. В конце — межмаршрутный спуск (relocate,
swap в пределах окна, 2-opt*) по лучшему решению с повторной полировкой графом. Случайность
идёт от фиксированного `lns_random_seed`.

**`greedy`.** Последовательная вставка с проверкой всех позиций у всех подходящих инженеров.
Известные решения не использует; защита от ухудшения в replan обеспечивается общей
страховкой (§13.4).

Вес приоритета — степенная шкала:

```text
request_priority_score = priority_tier_weight ** (3 - priority)   # 1_000_000 / 1_000 / 1
```

### 6.2 Материализация времени

Для выбранной последовательности время рассчитывается строго слева направо:

```text
arrival = previous_finish + travel_minutes
start   = max(arrival, release_at, calculation_cutoff_at)
finish  = start + service_minutes
```

Для первой заявки `previous_finish` — `available_from` инженера, предыдущая точка — его
стартовая точка (у хвоста replan — точка последней зафиксированной остановки, §13.2).
Начать работу нужно внутри эффективного окна; окончание может выйти за окно, но не за
смену.

Расстояние перехода округляется до 0,01 км (`PlanningRules.stop_distance`) — точности
хранения остановки. Пробег маршрута и плана поэтому точная сумма сохранённых остановок, и
сохранённые агрегаты сходятся с маршрутами (на этом держится проверка дневного отчёта).

## 7. Greedy-вставка

Вставка заявки проверяет все допустимые позиции у всех подходящих инженеров; принимается
только позиция, при которой повторная материализация всего затронутого хвоста сохраняет
hard constraints. Используется как самостоятельная стратегия `greedy`, как стартовое решение
LNS и как seed колонок графа.

## 8. Режимы распределения

Оба режима используют одинаковые hard constraints и стратегии. После приоритета и покрытия:

- `min_engineers` — минимизировать число инженеров с непустым маршрутом за день, затем
  дорогу;
- `balanced` — минимизировать разброс полезной загрузки в минутах работы за день, затем
  дорогу.

В replan цель считается за весь день: инженер с прожитой историей уже задействован, а его
утренние минуты работы входят в загрузку (`history_service_minutes`).

`min_engineers` не может сократить число бригад ценой потери заявок: сначала покрытие.
Поэтому при избыточной книге инженеров и неравномерных окнах средняя загрузка остаётся около
50 % — это потолок данных (сумма работы / сумма смен), а не недоработка стратегии.

## 9. Загрузка и метрики

Для инженера:

```text
without_travel = sum(service_minutes) / shift_minutes
with_travel    = (sum(service_minutes) + sum(travel_minutes)) / shift_minutes
```

Полезная загрузка — `without_travel`. Ожидание окна не входит ни в работу, ни в дорогу.

Агрегаты плана одинаковы для initial, replan и event replan и считаются по маршрутам
полного дня (с прожитой историей):

- назначенные и неназначенные заявки, инженеры доступные и с маршрутом;
- минуты работы и дороги, пробег (точная сумма остановок);
- средняя загрузка с дорогой и без — по всем, кто мог работать или работал за день
  (доступен либо имеет маршрут). Выбывший после утренней истории инженер остаётся в
  знаменателе.

## 10. Неназначенные заявки

Результат содержит каждую заявку ровно один раз: в stop, в `unassigned` либо (только replan)
в `cancelled_request_ids`. Причины проверяются по порядку:

1. `no_available_engineer` — в округе нет ни одного доступного инженера;
2. `no_matching_skill`;
3. `no_matching_vehicle`;
4. `no_available_engineer` — подходящие есть, но все недоступны;
5. `no_route` — нет ни одного достижимого перехода в заявку;
6. `no_time_slot` — ни один подходящий инженер не успевает даже с одной заявкой;
7. `no_available_engineer` — время есть, но инженеры заняты другими заявками.

Заявка без координат (адрес не найден геокодером) в алгоритм не передаётся; orchestration
сохраняет её неназначенной с причиной `no_route`. Авария, которую невозможно назначить
физически, остаётся только в `unassigned`; её нельзя скрывать нарушением SLA.

## 11. Независимый аудит

До возврата результата `ResultAuditor` проверяет:

- полное и взаимоисключающее покрытие пула;
- существование всех request/engineer IDs и доступность инженеров маршрутов;
- непрерывную последовательность и точное равенство arrival/start/finish/дороги/пробега
  повторному расчёту;
- окно, смену, cutoff, навык и транспорт;
- агрегаты каждого маршрута и плана (одна общая проверка для initial и replan).

Для replan дополнительно:

- зафиксированные остановки — точные копии базы и префикс маршрута;
- будущие остановки только у доступных инженеров и не раньше cutoff;
- каждая заявка дня ровно один раз среди назначенных, неназначенных и отменённых.

Для event replan дополнительно — событие применено ровно один раз: срочная заявка есть в
snapshot, отменённая не осталась в будущем плана, доступность инженера соответствует
событию.

При ошибке аудита результат не может быть сохранён.

## 12. Диагностический прогон

`plan_initial_diagnosed` запускает тот же расчёт и аудит и дополнительно возвращает
неперсистентный отчёт: время распределения, сборки результата, аудита и полного вызова;
время генерации route columns и агрегаты selector (запуски, кандидаты, узлы, отсечения); для
LNS — итерации, принятые и улучшающие шаги, частоту операторов; для каждого сочетания
инженера и слоя — размеры frontier, переходы, отказы и длительность. Диагностика не входит в
`Plan` и не меняет решение.

## 13. Baseline и replan

### 13.1 Baseline

Baseline буквально повторяет п. 2.3 ТЗ: заявки обходятся во входном порядке, каждая
добавляется в конец маршрута первого во входном порядке подходящего инженера. Сортировки,
перестановок и графа нет. Orchestration вызывает `plan_baseline` на том же
`InitialPlanningInput` и сохраняет только метрики в `BaselineResult`. ORM-записи перед
сборкой snapshot сортируются по UUIDv7 последовательного импорта.

### 13.2 Фиксация прожитой истории

Остановка прожита, если:

- заявка `in_progress` или `done`;
- заявка `on_the_way` у доступного инженера;
- иначе — её `planned_start` раньше cutoff (FULL_USER_CASE §7.2).

Отменённая заявка и заявка `on_the_way` у выбывшего инженера сами прожитыми не считаются.
Фиксируется префикс маршрута до последней прожитой остановки: в конце истории такие заявки
снимаются с маршрута (отменённая исчезает, «в пути» уходит в пересчёт), в середине истории
остаются как есть. Зафиксированные остановки копируются без изменений с `is_locked = true`.

Ограничение §7.2: если инженер по плану уже выехал к заявке, а статус «в пути» не выставлен,
остановка не фиксируется, хвост выпускает инженера из предыдущей точки в момент cutoff, и
такая заявка может не поместиться. Корректные статусы диспетчера устраняют это полностью.

### 13.3 Старт будущего хвоста

- инженер без истории — из стартовой точки не раньше cutoff;
- с историей — из точки последней зафиксированной остановки не раньше её окончания и cutoff;
- вернувшийся в строй после своей последней зафиксированной остановки
  (`EngineerSnapshot.returned_at`) — из своей стартовой точки не раньше момента возвращения;
- недоступный инженер сохраняет историю и не получает будущих остановок.

Хвост считается как самостоятельный initial по незафиксированным и неотменённым заявкам с
теми же правилами SLA (§4), затем склеивается с историей; sequence продолжает историю.

### 13.4 Не хуже текущего плана

Будущая часть утверждённого плана передаётся хвосту как известное решение — без заявок,
которых больше нет в пуле, и без маршрутов недоступных инженеров. Маршрут известного решения,
ставший невыполнимым, отбрасывается один, остальные остаются. Графу и LNS известное решение
служит стартом; кроме того, для любой стратегии `plan_replan` сравнивает найденный хвост с
допустимым известным решением по ключу `(score приоритета, покрытие)` и возвращает лучший.
Поэтому replan без изменений не хуже текущего плана, если текущий хвост физически выполним.

Отменённые незафиксированные заявки возвращаются в `cancelled_request_ids` и не считаются
неназначенными.

## 14. Event replan

`ReplanEvent` — одно валидированное событие: тип, `occurred_at` (не позже cutoff) и ровно
одна цель. `prepare_event_replan` применяет его к snapshot и готовит обычный replan:

| Событие | Применение |
|---|---|
| `urgent_request` | новая заявка добавляется в пул с `received_at = occurred_at`; назначается либо попадает в `unassigned` с причиной |
| `request_cancelled` | заявка получает статус `cancelled`; `in_progress`/`done` отменить нельзя; «в пути» снимается с маршрута, инженер пересчитывается с последней зафиксированной точки |
| `engineer_unavailable` | инженер исключается из будущего; `in_progress`/`done` остаются его историей, «в пути» уходит другим или в неназначенные |
| `engineer_available` | инженер возвращается в пул и стартует из своей стартовой точки не раньше события |

Некорректное событие (цель не найдена, повтор, недопустимый переход, время позже cutoff) —
`AlgorithmInputError`. Проверку переходов по утверждённой цепочке событий, хранение события
и его lifecycle выполняет backend.

Контракт с orchestration, зависящий от алгоритма:

- при следующих replan backend передаёт `received_at` срочной заявки и `returned_at`
  инженера из утверждённых событий дня;
- утверждение плана по событию допускает, что отменённая заявка и снятые с выбывшего
  инженера заявки «в пути» исчезли из уже начавшейся части маршрута; статус таких заявок
  «в пути» сбрасывается в «не отправлена».

## 15. Проверенное состояние

Версии реализаций: `layered_graph-v3`, `lns-v3`, `greedy-v3`, `baseline-v3`; replan —
`replan-<стратегия>-v3`.

Юнит-тесты покрывают граничные случаи на всех стратегиях (нет заявок, нет инженеров, один
инженер, несовпадение навыка/транспорта, cutoff в конце смены, все инженеры недоступны,
полностью прожитый день, все выбыли), детерминизм initial и replan, все четыре события,
правила SLA и точность пробега.

Стенд на реальных книгах трёх округов (66/83/56 заявок, 12/15/11 бригад, синтетическая
матрица по расстоянию, строгая к непокрытым переходам):

- initial на `layered_graph`, `lns`, `greedy` детерминирован, все аварии назначены в SLA;
- цепочка replan 11:00–20:00 при корректных статусах «в пути» — ноль нарушений
  (неизменная история, полное покрытие, не хуже текущего плана);
- все четыре события в 11:00, 14:00, 17:00 — ноль нарушений инвариантов.

Полный HTTP-прогон дня (реальный DaData, локальная матрица, подменённые часы 09:10–18:10):
initial трёх округов, повторная загрузка и истечение утверждения, replan с утверждением,
отклонением, конкурирующими кандидатами и поздним approve, все события, Excel всех планов и
дневной PDF-отчёт — без нарушений инвариантов; пробег каждого плана совпадает с суммой
остановок.

Не проверено на реальных матрицах: публичный OSRM блокирует по трафику уже на одном initial
крупного округа; для работы нужен собственный OSRM или другой провайдер.
