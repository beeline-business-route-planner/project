# Полный пользовательский сценарий планирования рабочего дня

## 1. Назначение документа

Документ описывает единый жизненный цикл планирования одного рабочего дня:

1. загрузка исходных Excel-файлов и первичное планирование;
2. просмотр, утверждение или отклонение предложенного плана;
3. обычное перепланирование одного или нескольких округов;
4. перепланирование одного округа по внештатному событию;
5. просмотр полного нового плана и его отличий от рабочего;
6. выгрузка любого плана в Excel;
7. формирование планового отчёта о дне в PDF.

Документ является канонической версией сценария. Подробные совместимые правила
представления карточек заявок и инженеров, группировки, карты, history/current/detail и
ленивого чтения закреплены в [`PLANS_API.md`](./PLANS_API.md).

## 2. Пользователь и термины

Единственный пользователь системы — **диспетчер**. Инженеры не входят в систему и не
утверждают планы.

| Термин | Значение |
|---|---|
| Рабочий день | Дата планирования в московском часовом поясе. Планы разных дней независимы. |
| Округ | Независимый пул заявок и инженеров. Один план всегда относится ровно к одному округу. |
| Кандидат | Полностью рассчитанный, сохранённый, но ещё не утверждённый план со статусом `pending`. |
| Рабочий план | Последний утверждённый план округа за выбранный рабочий день. |
| Initial | Первичный план, построенный из пары Excel-файлов округа. |
| Replan | Пересчёт будущей части дня по инициативе диспетчера без нового события. |
| Event replan | Пересчёт будущей части дня как реакция на одно внештатное событие. |
| Дифф | Детерминированное сравнение кандидата с утверждённым планом, указанным в `based_on_plan_id`. |
| Baseline | Отдельный примитивный контрольный алгоритм из официального ТЗ, используемый только для сравнения метрик initial. |

## 3. Главные инварианты

1. План неизменяем после успешного расчёта и сохранения. Решение диспетчера меняет только
   его статус и время решения.
2. План относится к одной паре `region + planning_date`.
3. Рабочим является только `approved`-план. `pending` не влияет на работу, а `rejected`
   никогда не может стать рабочим.
4. Текущий план определяется по времени утверждения `approved_at`, а не по времени
   расчёта `created_at`.
5. Initial не имеет родительского плана и диффа.
6. Replan и event replan всегда имеют `based_on_plan_id`, который указывает на текущий
   утверждённый план в момент запуска расчёта.
7. Перепланирование никогда не основывается на другом `pending` или `rejected` плане.
8. Дифф всегда строится относительно сохранённого `based_on_plan_id`; база сравнения не
   подменяется более новым планом при позднем чтении.
9. После утверждения нового плана все остальные `pending`-планы того же округа и дня
   становятся `rejected`.
10. Предыдущие утверждённые планы сохраняют статус `approved`, но перестают быть current.
11. Каждый округ рассчитывается, утверждается и отклоняется независимо.
12. Новый план содержит полный снимок дня. Уже прошедшие или фактически начатые остановки
    переносятся из рабочего плана без изменений; пересчитывается только допустимая будущая
    часть.
13. Одну заявку в одном плане можно встретить ровно один раз: либо в назначенных
    остановках, либо среди неназначенных.
14. После утверждения initial повторная загрузка Excel для **алгоритмического** расчёта
    того же округа и рабочего дня запрещена в MVP. Ручное планирование — исключение:
    диспетчер может в любой момент дня загрузить пару XLSX и собрать план сам; такой план
    (`kind = initial`, `strategy = manual`) после утверждения становится текущим.
15. Планы разных рабочих дней не наследуются друг от друга.

## 4. Виды и состояния планов

### 4.1 Виды

| Значение | Смысл |
|---|---|
| `initial` | Первый план рабочего дня, построенный по загруженным Excel-файлам. |
| `replan` | Запрошенный диспетчером пересчёт будущей части рабочего дня. |
| `event_replan` | Пересчёт будущей части рабочего дня в ответ на внештатное событие. |

Ранее использовавшееся имя `manual_replan` заменяется на `replan`: маршрут всё равно
строит алгоритм, диспетчер лишь вручную запускает пересчёт.

### 4.2 Статусы

| Статус | Смысл |
|---|---|
| `pending` | План рассчитан и сохранён, но ещё не влияет на работу. |
| `approved` | Диспетчер утвердил план. Он является или являлся рабочим. |
| `rejected` | План явно отклонён, автоматически вытеснен другим утверждением либо протух. |

Переходы:

```text
pending ──approve──> approved
pending ──reject───> rejected
pending ──expiry───> rejected
pending ──другой план approved──> rejected
```

Обратных переходов нет. Повторный approve, approve отклонённого плана и reject
утверждённого плана завершаются конфликтом. Причина отклонения в MVP не вводится.

## 5. Рабочий день и выбор current

- `planning_date` обязателен в доменной модели.
- Дата определяется и интерпретируется в часовом поясе Москвы.
- `GET current` без явной даты использует текущую московскую дату.
- Вчерашний план не является текущим сегодня.
- Вчерашний `pending` нельзя утвердить сегодня.
- Если сегодня нет `approved`-плана выбранного округа, главный экран показывает пустое
  состояние и переход на экран планирования.
- История по округу сортируется по `created_at DESC` и показывает статус каждой версии.

## 6. Первичное планирование

### 6.1 Вход

Диспетчер загружает ненулевое чётное число `.xlsx`: для каждого переданного округа — одну
книгу с заявками и одну отдельную книгу со списком доступных инженеров этого округа. Книги
`Синтетические данные.xlsx` являются штатными реальными входными данными заявок: именно в
таком табличном формате заявки поступают в систему.

Backend определяет роль книги по набору обязательных колонок, извлекает только необходимые
для планирования поля и игнорирует остальные колонки. Исходное имя файла и слова
`Синтетические данные`, `Контрольное распределение` или `Инженеры` в имени не участвуют в
определении роли и не валидируются. Округ определяется по содержимому книги.

Книги `Контрольное распределение.xlsx` не являются входными данными системы. Это только
справочные примеры того, как диспетчер вручную распределил заявки в прошлом. Они не подходят
под обязательную схему книги инженеров, поэтому backend не выводит из них состав, навыки,
смены или транспорт инженеров. Это определяется содержимым, а не именем файла.

Один запрос может содержать один, два, три или больше округов. Результат каждого округа
независим.

### 6.2 Время начала планирования

Алгоритм обязан получить фактический временной срез расчёта. Ни одна новая остановка не
может начинаться раньше этого времени.

Если расчёт initial выполняется в 10:12, рабочий график строится так, будто инженеры могут
начать движение и работу не раньше 10:12. Нельзя построить в 10:12 маршрут с первой
остановкой в 10:00 и затем считать его выполнимым.

### 6.3 Жизненный цикл initial

1. Файлы валидируются, геокодируются и сохраняются.
2. Для каждого округа создаётся отдельная выгрузка данных.
3. Основной алгоритм строит полный initial-кандидат.
4. Отдельный baseline-алгоритм строит контрольный результат на тех же данных и с тем же
   временным срезом.
5. Кандидат сохраняется как `pending`.
6. Генерационный endpoint возвращает карточку-заголовок по каждому округу.
7. Полная карточка загружается отдельным запросом по ID.
8. Диспетчер утверждает или отклоняет каждый округ отдельно.

Ранее для initial был выбран фиксированный срок утверждения в 10 минут, однако это не
считается окончательным доменным правилом. До реализации approval необходимо отдельно
спроектировать более корректную проверку того, что рассчитанный маршрут всё ещё актуален
и выполним на момент утверждения. Конкретный критерий пока не согласован; фиксированные
10 минут можно рассматривать только как временную MVP-эвристику, если более точное
решение не будет принято к началу реализации. См. раздел 11 в
[`FUTURE_FUNCTIONALITY.md`](./FUTURE_FUNCTIONALITY.md).

До первого утверждения диспетчер может повторно загрузить Excel и получить другие
initial-кандидаты. Каждая загрузка является независимой версией данных. После утверждения
одного initial:

- все остальные `pending` этого округа и дня становятся `rejected`;
- исходные файлы утверждённой версии считаются входными данными рабочего дня;
- новые Excel для этого округа и дня больше не принимаются;
- дальнейшие изменения выполняются только через replan или event replan.

Если initial ещё не утверждён:

- current отсутствует;
- replan запрещён;
- event replan запрещён;
- дифф отсутствует, потому что нет рабочей базы сравнения.

## 7. Обычное перепланирование

### 7.1 Запуск

Диспетчер выбирает один или несколько округов и запускает пересчёт. Для каждого округа
система:

1. находит current `approved` за текущий рабочий день;
2. фиксирует временной срез расчёта;
3. переносит недоступную для изменения часть current без изменений;
4. пересчитывает разрешённую будущую часть;
5. сохраняет новый полный план `pending` с `kind = replan`;
6. записывает `based_on_plan_id = current.id`.

Если у округа нет утверждённого initial/current, этот округ возвращает ошибку и не
создаёт кандидат.

### 7.2 Что нельзя менять

Алгоритм не меняет:

- остановки с `planned_start` раньше временного среза расчёта;
- заявки в состояниях `on_the_way`, `in_progress`, `done`;
- фактически отменённые заявки не возвращаются в будущий маршрут;
- принадлежность, порядок и временные значения уже зафиксированной части истории.

Такие остановки копируются в новый план с `is_locked = true`. Их наличие делает новый
план полным снимком всего дня, а не только будущим «хвостом».

### 7.3 Частичный успех

Ошибки одного округа не откатывают успешно рассчитанные округа. Валидный запрос получает
общий ответ с результатом по каждому округу:

- успешный округ — `pending`-план и карточка-заголовок;
- неуспешный округ — стабильный код и безопасное описание ошибки.

Успешные планы сохраняются. Ошибки уровня формы всего запроса возвращаются обычным HTTP
error и не создают результаты.

## 8. Внештатные события

### 8.1 Типы MVP

| Тип | Смысл |
|---|---|
| `urgent_request` | Появилась новая срочная заявка с полным набором данных заявки. |
| `request_cancelled` | Существующая заявка отменена. |
| `engineer_unavailable` | Инженер выбыл до конца рабочего дня. |
| `engineer_available` | Ранее выбывший инженер снова доступен. |

### 8.2 Общие правила

- Event replan всегда относится ровно к одному округу.
- Время события задаёт сервер в момент создания. Пользователь не может поставить событие
  задним числом или в будущем.
- Пользовательское `occurred_at` оставлено как будущее расширение.
- На округ и рабочий день одновременно допускается только одно `pending`-событие.
- Пока оно не approved/rejected, попытка создать другое событие возвращает конфликт.
- Событие и рассчитанный по нему план создаются одной транзакцией.
- Если парсинг, геокодирование, маршрутизация, алгоритм или сохранение плана завершаются
  ошибкой, откатываются и событие, и план.
- План события получает `kind = event_replan`, текущий `based_on_plan_id` и
  `triggered_by_event_id`.
- Событие и его план имеют одинаковый статус: `pending`, `approved` или `rejected`.
- Явное отклонение плана отклоняет событие той же транзакцией.
- Утверждение плана утверждает событие и применяет соответствующее изменение состояния.
- Только `approved`-события считаются состоявшимися для рабочего состояния и отчёта.

### 8.3 Валидность переходов

- Нельзя создать/утвердить `engineer_unavailable`, если инженер уже недоступен по последней
  утверждённой цепочке событий.
- Нельзя создать/утвердить `engineer_available`, если инженер уже доступен.
- Нельзя повторно отменить отменённую заявку.
- Нельзя повторно создать ту же срочную заявку с тем же внешним ID.
- После утверждённого `engineer_available` новое `engineer_unavailable` считается новым
  самостоятельным событием.

Поскольку события становятся фактом только после утверждения связанного плана, отклонённая
попытка не входит в отчёт. Диспетчер может заново создать семантически такое же событие и
получить новый расчёт.

## 9. Утверждение плана

Approve выполняется одной транзакцией и должен защищаться от конкурентных решений.

### 9.1 Общие проверки

Перед утверждением система проверяет:

1. план существует и имеет статус `pending`;
2. рабочий день плана совпадает с текущим рабочим днём;
3. для replan/event replan `based_on_plan_id` всё ещё является current;
4. initial всё ещё актуален и выполним по согласованному правилу проверки; временный
   fallback — не прошло 10 минут после завершения расчёта;
5. после расчёта не было утверждено новое событие округа;
6. не изменилась затрагиваемая заявка;
7. не изменился статус затрагиваемой заявки;
8. изменяемая кандидатом остановка не оказалась в прошлом;
9. не изменился статус доступности затрагиваемого инженера.

Неизменившиеся остановки, уже оказавшиеся в прошлом, не запрещают approve: они должны быть
точной заблокированной копией рабочего плана.

### 9.2 Успешное утверждение

При успехе:

- кандидат получает `approved` и `approved_at`;
- event replan той же транзакцией утверждает и применяет событие;
- кандидат становится current округа и дня;
- все другие `pending`-планы округа и дня получают `rejected` и `rejected_at`;
- фронт после ответа обновляет список планов округа.

Принудительное утверждение устаревшего плана с переписыванием истории в MVP отсутствует.

## 10. Отклонение плана

- Отклоняется только `pending`.
- Причина/комментарий не запрашивается.
- План получает `rejected` и `rejected_at`.
- Если это event replan, событие также получает `rejected`.
- Рабочий план не меняется.
- Отклонённый план остаётся доступен в истории для просмотра, но не входит в дневной
  отчёт и не может быть базой следующего расчёта.
- Фронт после ответа повторно получает список планов округа.

«Отложить решение» не является отдельным действием: диспетчер просто оставляет план в
`pending` и возвращается к нему позже.

## 11. История и карточка плана

### 11.1 Список

История округа содержит карточки-заголовки всех планов и сортируется по времени расчёта по
убыванию. Карточка показывает:

- ID;
- округ и рабочую дату;
- вид плана;
- статус;
- время расчёта, утверждения или отклонения;
- ID базового плана;
- число назначенных и неназначенных заявок;
- количество задействованных инженеров;
- общий пробег;
- является ли план current.

В MVP единственный обязательный фильтр списка — округ. Статусы отображаются, но отдельные
фильтры по ним необязательны.

### 11.2 Полная карточка

Полная карточка следует контракту [`PLANS_API.md`](./PLANS_API.md):

- метаданные плана;
- группы заявок: авария, интервалы времени, неназначенные;
- тайлы всех заявок;
- только задействованные инженеры;
- остановки каждого инженера по `sequence_number`;
- координаты для карты;
- метрики плана.

Для initial поле `diff` равно `null`. Для replan/event replan полный ответ также содержит
вычисленный дифф.

## 12. Дифф планов

Дифф не хранится. Он строится при чтении кандидата по паре:

```text
before = based_on_plan_id
after  = candidate plan
```

Изменяемость статуса кандидата не меняет содержимое диффа.

### 12.1 Структура

Дифф содержит:

1. `base_plan_id` и `candidate_plan_id`;
2. сводное изменение метрик;
3. список всех инженеров, включая неизменившихся;
4. `before` и `after` по каждому инженеру;
5. список всех заявок инженера, включая неизменившиеся;
6. набор признаков изменения и `before`/`after` по каждой заявке.

Изменение инженера:

- `added`;
- `removed`;
- `changed`;
- `unchanged`.

Изменения заявки не являются взаимоисключающими и возвращаются массивом:

- `added`;
- `removed`;
- `reassigned`;
- `reordered`;
- `rescheduled`;
- `travel_changed`;
- `assignment_changed`;
- `unassigned_reason_changed`;
- `unchanged`.

Для добавленного элемента `before = null`, для удалённого `after = null`. Если изменились
время прибытия, начала, завершения, время дороги или километраж, API показывает старое и
новое значения.

### 12.2 Сводные метрики

Показываются before/after/delta минимум для:

- назначенных и неназначенных заявок;
- числа задействованных инженеров;
- общего пробега;
- плановой загрузки с дорогой и без дороги.

## 13. Представление главного экрана

Главный экран всегда использует current `approved` выбранного округа за текущую дату.
Pending-кандидаты не подменяют рабочий план.

Применяются правила [`PLANS_API.md`](./PLANS_API.md):

- вкладка заявок показывает все заявки и группы в фиксированном порядке;
- неназначенная заявка не дублируется в аварийной группе;
- UI использует `planned_start`, а не `planned_arrival`, как основное время;
- карта показывает точки всех заявок;
- выбор заявки подсвечивает маршрут назначенного инженера;
- вкладка инженеров показывает только задействованных;
- до выбора инженера маршруты не рисуются;
- после выбора рисуется только его маршрут;
- plan-agnostic карточки заявки и инженера открываются отдельными endpoint.

## 14. Ленивое чтение результатов

Генерационный endpoint не возвращает все маршруты и диффы нескольких округов одним
огромным телом. Он возвращает региональные карточки-заголовки или региональные ошибки.

Фронт строит вкладки округов по результату. При выборе вкладки он вызывает чтение
конкретного плана и получает:

- полную карточку;
- дифф, если он существует;
- актуальный статус;
- доступность действий approve/reject.

Отдельный endpoint только для диффа в MVP не нужен.

## 15. Плановые метрики загрузки

Для каждого инженера:

```text
workload_without_travel =
    sum(service_minutes) / shift_minutes * 100%

workload_with_travel =
    (sum(service_minutes) + sum(travel_minutes)) / shift_minutes * 100%
```

Ожидание до открытия окна не включается ни в одну из двух метрик.

Для округа показываются:

- средняя загрузка всех доступных инженеров, включая незадействованных;
- средняя загрузка только задействованных;
- минимальная и максимальная загрузка;
- число доступных и задействованных инженеров;
- назначенные и неназначенные заявки;
- пробег по каждому инженеру и общий пробег.

Метрики являются плановыми. Без истории фактических статусов и времён нельзя называть их
фактической производительностью.

## 16. Baseline

Baseline задан разделом 2.3 официального ТЗ:

1. заявки обрабатываются по входному порядку;
2. заявка назначается первому по входному порядку доступному инженеру, проходящему
   обязательные ограничения;
3. порядок посещения равен порядку назначения;
4. глобальная оптимизация отсутствует.

Для baseline требуется отдельная реализация алгоритма. Она рассчитывает полноценные
маршруты в памяти, чтобы получить корректные времена, пробег и причины неназначения.

Baseline не является `Plan`:

- поле `Plan.is_baseline` удаляется;
- baseline не имеет approval status;
- его нельзя открыть как рабочий вариант, утвердить, отклонить или использовать в replan;
- он не участвует в истории и диффах.

Для каждого initial-кандидата создаётся отдельный результат baseline на тех же входных
данных и с тем же временным срезом. Результат хранится в отдельной таблице сравнения,
связанной один-к-одному с initial-планом. Если initial отклонён, его baseline не попадает
в отчёт. Для replan/event replan baseline не запускается.

## 17. Excel-выгрузка плана

Выгрузить можно любой сохранённый план независимо от статуса. Один план всегда относится к
одному округу, поэтому один XLSX не смешивает округа.

Листы:

- `Заявки` — все заявки и их назначения/причины неназначения;
- `Инженеры` — инженеры и агрегированные метрики;
- отдельный лист на каждого задействованного инженера с маршрутом по порядку;
- `Неназначенные`;
- `Метрики`.

Дифф в Excel не включается.

## 18. Дневной PDF-отчёт

### 18.1 Назначение

Отчёт предназначен для руководства и показывает, как был спланирован рабочий день,
какие утверждённые изменения происходили и какие плановые показатели получены.

Это плановый управленческий отчёт. Он не утверждает, что заявки фактически выполнены в
запланированное время.

### 18.2 Состав

Для каждого округа создаётся отдельный PDF:

1. дата и округ;
2. сведения об утверждённой исходной загрузке;
3. первоначальный утверждённый план;
4. сравнение initial с baseline;
5. хронология утверждённых событий;
6. хронология утверждённых перепланирований;
7. краткие диффы между последовательными утверждёнными версиями;
8. последний утверждённый полный план;
9. маршруты и метрики инженеров;
10. назначенные и неназначенные заявки;
11. плановая загрузка с дорогой и без неё;
12. итоговые метрики округа.

Дополнительно формируется `summary.pdf` со сводкой всех округов.

Pending и rejected планы/события в отчёт не входят.

### 18.3 Формирование в середине дня

Отчёт строится по запросу и может быть сформирован до окончания дня. В нём обязательно
указываются:

- момент формирования;
- признак, что рабочий день ещё продолжается;
- текущий на этот момент последний approved-план.

Итоговые метрики берутся из последнего approved-плана, потому что он обязан содержать
точную заблокированную историю предыдущих версий и актуальный будущий хвост.

### 18.4 Пакет скачивания

Региональные PDF и `summary.pdf` упаковываются в один ZIP. Количество файлов зависит от
числа округов:

```text
daily-report-YYYY-MM-DD/
├── summary.pdf
├── <region-1>.pdf
├── <region-2>.pdf
└── ...
```

## 19. S3 для экспортов

XLSX и ZIP/PDF:

1. формируются в памяти;
2. не сохраняются на локальном диске backend;
3. загружаются в выделенный префикс S3 `exports/`;
4. не получают отдельную запись в PostgreSQL;
5. возвращаются клиенту как presigned URL;
6. ссылка имеет настраиваемое короткое время жизни (целевое значение — 15 минут);
7. объект удаляется lifecycle policy S3 (целевое значение — через 24 часа);
8. повторный запрос создаёт новый экспорт.

Сроки являются конфигурацией, а не литералами в коде.

## 20. Частичный успех по округам

Для initial и replan результат имеет общий статус:

- `success` — все переданные округа рассчитаны;
- `partial_success` — часть рассчитана, часть завершилась ошибкой;
- `error` — ни один округ не рассчитан, но форма запроса была корректна.

Каждый региональный элемент содержит `region`, `status`, а затем либо `plan_summary`, либо
`error {code, detail}`. HTTP 200 используется для корректно принятого мультиокружного
запроса с региональными результатами. Ошибка формы всего запроса использует подходящий
4xx/5xx и не маскируется как региональный результат.

Event replan относится к одному округу и использует обычную HTTP-ошибку при неуспехе.

## 21. Ошибочные сценарии

Конфликтом считаются минимум:

- попытка replan/event replan без approved initial;
- повторный initial upload после утверждения initial;
- approve не-pending плана;
- reject не-pending плана;
- approve replan, база которого перестала быть current;
- approve протухшего initial;
- approve кандидата, разошедшегося с фактическим состоянием;
- создание второго pending-события округа;
- недопустимый переход доступности инженера;
- повторная отмена заявки;
- повторное создание срочной заявки;
- approve плана другого рабочего дня.

## 22. Будущие расширения

Отложены и не должны незаметно попасть в MVP:

- пользовательское время события и события задним числом;
- несколько одновременно ожидающих событий одного округа;
- повторная загрузка Excel после утверждённого initial и правила слияния;
- принудительный approve устаревшего кандидата с переписыванием истории;
- отдельный read-only журнал событий;
- фактические времена начала/завершения и полноценный отчёт исполнения;
- история переходов статусов заявок;
- постоянное хранение сформированных экспортов и каталог отчётов;
- фильтры истории планов по статусу, виду и диапазону дат.

Ручное составление initial и изменение pending-кандидата реализованы как расширение;
действующий контракт — [MANUAL_PLANNING.md](../MANUAL_PLANNING.md).
