# ROUTING.md

Как считается время в пути и расстояние между точками (матрица для
`src/core/algorithm/`) — что именно возвращает провайдер, как это
оптимизировано под число запросов и скорость, и план перехода на
самостоятельный инстанс OSRM (не сделан, задокументирован заранее). Про
слои/стиль кода — [../agents-docs/ARCHITECTURE.md](../agents-docs/ARCHITECTURE.md).
Где матрица используется дальше — [ALGORITHM.md](./ALGORITHM.md).

**Статус на сейчас**: `src/core/routing/` реализован (`client.py` +
`service.py`, см. `RoutingService.build_matrix`), подключён в
`AlgorithmService` (`docs/ALGORITHM.md`). **Кэш сознательно не делаем** —
см. раздел "Почему без кэша" ниже.

---

## Что именно считается

**Реальный маршрут по дорожной сети, не расстояние по прямой.** Источник —
OSRM `Table API` (`/table/v1/{profile}/{coordinates}?annotations=duration,distance`):
движок строит граф дорог из данных OpenStreetMap (перекрёстки, разрешённые
повороты, односторонние улицы, типы дорог со своими скоростными профилями) и
для каждой пары точек ищет путь **по этому графу**, не по воздуху.
`distance` — метры вдоль реального маршрута, `duration` — секунды, оценённые
по скоростным характеристикам дорог профиля (не "расстояние / средняя
скорость по прямой"). Это важно, потому что реальный объезд (река без
моста рядом, МКАД без съезда) даёт совсем другое число, чем формула
расстояния — а по `SUMMARY.md` пробег обязан считаться "по дорогам, не по
прямой".

Профиль `driving` покрывает транспорт `car`. Для `pedestrian`/`bicycle`/
`public_transport` по ТЗ (`TECHNICAL_CONSTRAINTS.md`, §4) допустим
усреднённый расчёт "от точки до точки" без честного маршрута — то есть для
не-`car` транспорта можно(и по объёму работы проще) взять расстояние по
прямой с усреднённым коэффициентом скорости, а не гонять отдельный
OSRM-профиль на каждый вид транспорта.

## Как оптимизировано

1. **Один batched-запрос на всю NxN-матрицу**, не попарные вызовы — `Table
   API` отдаёт сразу все `durations`/`distances` одним HTTP-запросом
   (`RoutingService.build_matrix`, `src/core/routing/service.py`).
2. **Матрица строится per-region**, не глобально — округа независимы
   (`SUMMARY.md`), на округ ≤100 заявок + 10-15 инженеров, то есть ≤~115
   узлов за раз — тривиальный размер для одного запроса. `AlgorithmService`
   строит ровно одну матрицу на округ: точки инженеров (старты) + точки
   заявок пула, за один вызов `build_matrix`.
3. **Параллелизация независимых округов** — `PlanningService.import_initial_data`
   вызывает `AlgorithmService.plan_initial` для всех округов через
   `asyncio.gather` (`planning.py`), то есть их `build_matrix`-запросы к
   OSRM уходят параллельно.

## Почему без кэша

Изначально рассматривался in-memory кэш по координатам точки (переживающий
процесс, как у `GeocodingService`) — **сознательно отказались**: реальное
время в пути меняется (пробки, дорожные работы, время суток), а `Plan`
хранит `PlanStop.travel_minutes`/`distance_km` как результат **конкретного
расчёта на момент построения именно этого плана** (см. `DATABASE.md`,
обоснование там же для `PlanUnassignedRequest.reason`). Закэшированное
значение с прошлого расчёта могло бы незаметно разойтись с реальностью и
исказить план так, что диспетчер увидел бы не то решение, которое реально
стоило принять на момент пересчёта. Поэтому каждый вызов `build_matrix` —
всегда свежий HTTP-запрос к провайдеру, без переиспользования между
вызовами (в том числе между `initial`/`manual_replan`/`event_replan` одного
дня). Единственная "оптимизация под число запросов", которая при этом
остаётся — batched-запрос на всю матрицу сразу (п. 1 выше), а не отказ от
актуальности данных ради экономии запросов.

## Провайдер сейчас: публичный demo-сервер OSRM

`router.project-osrm.org` — общий бесплатный демо-инстанс, без ключа, но:

- негласный рейт-лимит (по опыту — около 1 запроса/сек с одного IP),
  возможна временная блокировка IP при частых запросах;
- нет SLA/гарантии доступности — сторонний сервис вне нашего контроля;
- версия данных/профиля дорог может обновляться без предупреждения.

Для хакатон-масштаба (единичные прогоны, не продакшен-нагрузка) это
приемлемо **при условии** соблюдения пп. 3-4 выше — не пересчитывать то, что
уже посчитано.

## План на будущее (НЕ делаем сейчас): свой OSRM в `docker-compose.yml`

Убирает рейт-лимит и внешнюю сеть полностью — матрица считается локально за
миллисекунды. Откладывается сознательно — время хакатона важнее, публичный
демо-сервер закрывает MVP. Фиксируется здесь, чтобы решение не потерялось и
было ясно, что это осознанный выбор, а не забытая доработка.

### Что нужно будет сделать

1. **Достать extract дорожной сети** под нужный регион (Москва и область —
   весь датасет укладывается туда) с [Geofabrik](https://download.geofabrik.de/)
   (`.osm.pbf`), а не весь OSM-мир — extract умеренного размера.
2. **Препроцессинг OSRM** (одноразово, через `osrm-backend` Docker-образ,
   профиль `car.lua`):
   ```bash
   docker run -t -v "${PWD}/osrm-data:/data" ghcr.io/project-osrm/osrm-backend \
     osrm-extract -p /opt/car.lua /data/moscow.osm.pbf
   docker run -t -v "${PWD}/osrm-data:/data" ghcr.io/project-osrm/osrm-backend \
     osrm-partition /data/moscow.osrm
   docker run -t -v "${PWD}/osrm-data:/data" ghcr.io/project-osrm/osrm-backend \
     osrm-customize /data/moscow.osrm
   ```
   Результат — набор `.osrm*`-файлов, кладётся в volume, переиспользуется
   между запусками (препроцессинг не гоняется при каждом старте контейнера).
3. **Сервис в `docker-compose.yml`** (рядом с Postgres/мониторингом):
   ```yaml
   osrm:
     image: ghcr.io/project-osrm/osrm-backend
     command: osrm-routed --algorithm mld /data/moscow.osrm
     volumes:
       - ./osrm-data:/data
     ports:
       - "5000:5000"
   ```
4. **Единственное изменение в коде** — `cfg.routing.base_url` в конфиге
   (`config.toml`/env) с публичного демо-сервера на `http://osrm:5000` — сам
   `RoutingClient`/`RoutingService` не меняется, так как оба используют один
   и тот же протокол OSRM Table API. Это и есть смысл вынесения клиента в
   отдельный пакет `src/core/routing/` по конвенции `ARCHITECTURE.md` — смена
   инфраструктуры провайдера не трогает бизнес-логику алгоритма.

### Когда стоит вернуться к этому пункту

- если публичный демо-сервер реально забанит IP во время демонстрации/тестов;
- если понадобится профиль `pedestrian`/`bicycle` с честным маршрутом (не
  усреднённой скоростью по прямой) — самостоятельный OSRM это позволяет
  через отдельные `.lua`-профили при том же препроцессинге.
