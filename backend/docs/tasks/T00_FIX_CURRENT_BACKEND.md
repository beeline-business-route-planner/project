# T00. Починить существующий backend

**Статус: выполнена.**

## Цель

Получить воспроизводимую рабочую точку, от которой безопасно одновременно ответвляются
две backend-дорожки и независимая алгоритмическая дорожка. Эта задача не внедряет новый
lifecycle и не должна смешиваться с продуктовым рефакторингом.

## Исполнитель и зависимость

- Исполнитель: один backend-разработчик.
- Второй backend-разработчик: обязательное ревью и повтор smoke-проверки.
- Algorithm: начинает работу только после слияния T00.
- Зависимости: отсутствуют.

## Подтверждённая проблема

ORM `PlanStop` содержит `planned_start` и `planned_finish`, а начальная Alembic-миграция
этих колонок не создаёт. База с чистой историей миграций несовместима с текущим кодом
сохранения и чтения плана.

## Объём работ

1. Сопоставить все ORM-модели с фактической схемой единственной миграции.
2. Устранить рассинхронизацию `PlanStop` корректной новой миграцией; старую применённую
   миграцию не переписывать.
3. Проверить создание чистой БД и применение всех миграций.
4. Проверить текущий сценарий:
   - приложение запускается;
   - initial принимает валидные файлы;
   - план, остановки и неназначенные заявки сохраняются;
   - `GET /api/plans/{id}` читает созданный план;
   - `GET /api/plans/current` работает по старой семантике до T01/T04.
5. Исправить только найденные runtime/schema-дефекты, которые мешают этому сценарию.
6. Устранить ошибочное использование книги контрольного распределения как источника
   инженеров: initial принимает отдельную книгу инженеров того же округа. Книга
   `Синтетические данные.xlsx` является штатным реальным источником заявок. Роль книги
   определяется только по обязательным колонкам; имя файла не валидируется, дополнительные
   колонки игнорируются. Контрольный файл не соответствует схеме входной книги инженеров и
   не используется как источник данных.
7. Зафиксировать для алгоритмической дорожки рабочий публичный фасад
   `src/core/algorithm`: текущий import path и базовые DTO не ломаются последующими
   backend-ветками без интеграционной задачи.

## Не входит

- статусы plan/event;
- approve/reject;
- replan;
- baseline;
- diff;
- изменение HTTP-контрактов;
- добавление тестового фреймворка;
- рефакторинг алгоритма ради стиля.

## Зоны файлов

- `alembic/versions/*` — новая корректирующая миграция;
- `src/api/planning/{dto,parser,service,utils}.py` — отдельный входной формат инженеров;
- `docs/user-case/*` — только синхронизация согласованного входного контракта initial;
- при доказанной необходимости — минимальные исправления текущих моделей/репозиториев;
- `AGENTS.md` и `agents-docs/*` не меняются.

## Критерии приёмки

1. Чистая БД поднимается всеми миграциями без ручного SQL.
2. Таблица `planstop` соответствует ORM минимум по `planned_arrival`, `planned_start`,
   `planned_finish`, travel, distance и lock.
3. Текущий initial физически сохраняет и затем читает план.
4. Initial принимает книгу заявок в формате `Синтетические данные.xlsx` и отдельную книгу
   инженеров одного округа, классифицирует их по обязательным колонкам независимо от имён и
   игнорирует дополнительные колонки; книга контрольного распределения не принимается как
   источник инженеров из-за несоответствия обязательной схеме.
5. Повторный запуск миграций идемпотентно сообщает отсутствие новых миграций.
6. `make check` проходит.
7. В PR нет реализации будущего lifecycle.

## Выходной контракт

После merge все три исполнителя создают ветки от одного commit T00. Если smoke выявил
дополнительный дефект, он перечислен в PR и либо исправлен в границах задачи, либо вынесен
в конкретную следующую задачу — не оставлен неявным.
