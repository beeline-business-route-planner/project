# A05. Финальная стабилизация алгоритмической дорожки

## Владелец и зависимости

- Владелец: Algorithm.
- Требует: A01–A04.
- Не ждёт G04, но предоставляет результат для G05.

## Цель

Стабилизировать единый algorithm facade, аудит и метрики для всех трёх сценариев без
расширения продуктового scope.

## Объём работ

1. Унифицировать input/output initial/replan/event replan.
2. Устранить временные adapters и старые методы, которые сохраняют Plan.
3. Проверить детерминизм при фиксированных входах и matrix.
4. Унифицировать audit errors и причины unassigned.
5. Проверить метрики:
   - total/route mileage;
   - work minutes;
   - travel minutes;
   - utilization относительно смены с дорогой и без неё;
   - assigned/unassigned;
   - engineers used.
6. Проверить граничные случаи MVP: ноль назначений, один инженер, все заявки
   неназначены, cutoff в конце смены, unreachable point, пустой future tail.
7. Зафиксировать version идентификаторы optimized и baseline реализаций.
8. Не оптимизировать производительность ценой нарушения hard constraints; бюджет и
   fallback должны возвращать аудируемый полный результат.
9. Контролировать цикломатическую сложность через Ruff `C901`; общий порог проекта — 13.
   Вычислительную сложность графа оценивать отдельно по времени и размерам frontier, потому
   что McCabe измеряет ветвление исходного кода, а не число состояний алгоритма.
10. Поддерживать отдельный диагностический вызов без записи в БД: длительность стратегии и
    её стадий, а для графа — агрегаты переходов, отсечений и frontier по каждому слою.
11. Сравнивать рабочую стратегию с baseline на одинаковом snapshot. Найденное ухудшение
    покрытия или маршрута считается входом для следующей гипотезы, а не скрывается общей
    успешностью аудита hard constraints.
12. Для глобального selector измерять отдельно число route columns, запуски, посещённые
    узлы, конфликтные и bound-отсечения; повторные графы различать по `graph_run_id`.
13. Для экспериментального ALNS отдельно фиксировать single-ejection attempts и новые
    колонки, число итераций и улучшений, сгенерированные кандидаты, cache hit/miss и частоту
    destroy-операторов. Диагностика остаётся неперсистентной.

## Критерии приёмки

1. Backend использует один facade без знания конкретной стратегии.
2. Нет SQLAlchemy/FastAPI/S3 зависимостей внутри вычислительного слоя.
3. Все результаты проходят общий аудит.
4. Метрики одинаково определены во всех сценариях.
5. `make check` проходит.
