# T03. Backend orchestration первичного планирования

## Цель

Переделать initial из «импортировать и сразу сделать текущим» в генерацию независимых
pending-кандидатов по округам с полным региональным результатом.

## Исполнитель и зависимости

- Исполнитель: Backend A.
- Требует: G01.
- Параллельно: T04 и алгоритмическая дорожка.
- Блокирует: G02.

## Объём работ

1. Оставить входом пары Excel по одному или нескольким округам.
2. Валидировать правило: после approved initial для `(region, planning_date)` новая
   Excel-загрузка запрещена; до него повторные версии разрешены.
3. Один раз зафиксировать server-side `calculation_cutoff_at` для регионального расчёта и
   передать его алгоритму явно.
4. Для каждого округа выполнить независимый pipeline:
   - parse/validate;
   - geocode;
   - сохранить versioned upload;
   - вызвать optimized initial;
   - вызвать отдельный baseline;
   - аудит результата;
   - атомарно сохранить pending Plan, stops, unassigned и BaselineResult.
5. Ошибка округа полностью откатывает его DB/S3-изменения, но не уничтожает успешно
   рассчитанные соседние округа.
6. Вернуть `success`, `partial_success` или `error` и массив региональных summary/error.
7. Summary содержит минимум plan id, region, kind, status, planning date, created time и
   ключевые метрики. Полный plan загружается отдельно.
8. Initial никогда не назначается current до approve.
9. Исходные Excel после успешного сохранения остаются в S3 как входная версия дня.

## Транзакционная граница

Единица атомарности — один округ. S3 cleanup обязателен при его неуспехе. Нельзя сначала
закоммитить imports всех округов, а потом упасть общей ошибкой на алгоритме.

## Контракт с алгоритмом

Backend передаёт нормализованный snapshot и cutoff, получает pure result. Backend владеет
транзакцией и status; алгоритм не коммитит Plan самостоятельно.

## Не входит

- approve/reject;
- diff initial;
- повторная загрузка после approved initial;
- фоновая очередь;
- окончательная замена временного initial TTL.

## Критерии приёмки

1. Pending initial не появляется в `current`.
2. Можно создать несколько pending initial до первого approve.
3. После approved initial новый upload того же региона/дня получает conflict.
4. Один сломанный округ даёт partial success, успешные возвращаются в ответе.
5. Неуспешный округ не оставляет event/plan/upload/файлы частично.
6. Cutoff сохранён в Plan и совпадает с переданным алгоритму.
7. `make check` проходит.
