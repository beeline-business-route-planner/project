# T07. Backend внештатных событий и event replan

## Цель

Реализовать атомарное создание одного внештатного события и связанного pending event plan
для одного региона.

## Исполнитель и зависимости

- Исполнитель: Backend A.
- Требует: G03.
- Параллельно: T08/T09 и A04.
- Блокирует: G04.

## HTTP API

`POST /api/planning/events`

Один запрос содержит ровно одно событие одного региона. Сервер сам фиксирует время
создания/возникновения события для MVP.

## Поддерживаемые события

- `urgent_request`;
- `request_cancelled`;
- `engineer_unavailable`;
- `engineer_available`.

## Валидация

1. У региона есть approved initial/current текущего дня.
2. Нет другого pending event региона/дня.
3. Целевая сущность принадлежит региону и рабочему дню.
4. Нельзя повторно отменить отменённую заявку.
5. Нельзя повторно сделать недоступным недоступного инженера.
6. Нельзя вернуть уже доступного инженера.
7. Urgent request валидна и создаётся без upload.
8. Пользователь не задаёт прошлое/будущее `occurred_at`.

## Атомарный pipeline

1. Зафиксировать cutoff и current.
2. Создать pending event в текущей транзакции.
3. Применить event к вычислительному snapshot, не меняя утверждённый current.
4. Вызвать A04.
5. Выполнить аудит результата.
6. Создать pending Plan с `kind = event_replan`, base=current и event ID.
7. Сохранить stops/unassigned.
8. Commit event + payload + plan как единое целое.

При любой ошибке алгоритма, routing, БД или S3 событие и его payload не сохраняются.

## Lifecycle

- событие pending, пока pending связанный plan;
- approve/reject выполняет T04 в одной транзакции с plan;
- только approved events входят в дневной отчёт;
- rejected событие не влияет на следующие планы;
- новое повторное фактическое выбытие после возвращения является новым событием.

## Не входит

- CRUD/журнал событий;
- несколько pending events;
- пользовательское время;
- редактирование/удаление события;
- объединение нескольких событий в один plan.

## Критерии приёмки

1. Event и Plan либо сохранены вместе, либо отсутствуют вместе.
2. Все четыре перехода валидируются.
3. Второй pending event региона отклоняется.
4. Reject не меняет фактическое состояние; approve применяет согласованное изменение.
5. Urgent request видна в detail/diff/экспорте.
6. `make check` проходит.
