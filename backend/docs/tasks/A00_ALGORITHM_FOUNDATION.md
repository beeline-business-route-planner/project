# A00. Новый фундамент алгоритмической подсистемы

## Владелец

Algorithm. Задача предшествует A01 и не зависит от backend lifecycle-задач.

## Причина

Старый пакет строил маршрут каждого инженера отдельно, использовал одну матрицу округа,
смешивал поиск с точным временем и самостоятельно читал/сохранял ORM. Он не может быть
расширен до нового поведения локальными исправлениями.

## Цель

Полностью заменить пакет `src/core/algorithm` чистым каркасом, соответствующим
`docs/user-case/ALGORITHM.md`.

## Объём работ

1. Ввести immutable DTO snapshot/result без ORM и HTTP schemas.
2. Сделать `AlgorithmService` чистой точкой входа без UoW, routing-клиента и часов.
3. Ввести явный единый `calculation_cutoff_at`.
4. Представить traffic forecast как набор матриц по временным слоям и типам транспорта.
5. Разделить порядок заявок и материализацию точных времён.
6. Ввести оба режима как разные вторичные цели.
7. Добавить отдельный greedy completion и независимый result audit.
8. Перенести вызов routing и persistence в API-domain orchestration.
9. Удалить старый registry и стратегии, не соответствующие контракту.

## Критерии приёмки

1. Импорт `src.core.algorithm` не подтягивает UoW, ORM или routing service.
2. Одинаковый snapshot и матрицы дают детерминированный результат.
3. Матрица выбирается по слою целевой заявки и транспорту инженера; orchestration не
   запрашивает полную квадратную матрицу округа для каждого слоя.
4. `AlgorithmService.plan_initial` ничего не сохраняет.
5. `make check` проходит.
