# G03. Интеграционный барьер replan end-to-end

## Цель

Соединить T05 и A03, проверить replan, вычисляемый diff и позднее решение диспетчера.

## Входы и исполнитель

- Требует: T05 и A03; T06 может продолжаться независимо.
- Исполнитель: Backend B.
- Backend A: ревью orchestration/transactions.
- Algorithm: ревью adapter и locked semantics.
- Блокирует: T07 и T08.

## Объём работ

1. Подключить pure replan contract без ORM внутри алгоритма.
2. Устранить временные adapters и дублирование cutoff/locked rules.
3. Проверить полный detail кандидата и diff строго с зафиксированной base.
4. Проверить approve при неизменившемся фактическом состоянии.
5. Проверить conflicts:
   - после кандидата approved другой plan;
   - изменилась затрагиваемая заявка/status;
   - mutable stop стала прошлой;
   - изменилась доступность инженера;
   - approved новое событие.
6. Проверить reject и повторный replan: новый кандидат строится от последнего approved,
   никогда от rejected.

## Обязательные сценарии

- replan одного региона;
- replan трёх регионов с одной ошибкой;
- несколько pending от одного current;
- approve одного автоматически rejects остальные pending;
- reject кандидата не меняет current;
- поздний безопасный approve;
- поздний конфликтующий approve;
- past/started stops идентичны base;
- Excel T06 выгружает replan при готовности T06, но не блокирует сам G03.

## Критерии приёмки

1. User case обычного replan проходит целиком.
2. Diff соответствует base ID, а не текущему плану на момент чтения.
3. Lifecycle и транзакции не находятся внутри алгоритма.
4. `make check` проходит.
