# A04. Алгоритм event replan

## Владелец и зависимости

- Владелец: Algorithm.
- Требует: A03.
- Не зависит от backend T07.
- Нужен для G04.

## Цель

Расширить replan чистым применением одного валидированного event payload и вернуть полный
план с неизменяемой историей.

## Общая семантика

Backend гарантирует валидность перехода и передаёт один event. Алгоритм применяет его к
расчётному snapshot и оптимизирует будущий хвост по правилам A03.

## Типы

### Urgent request

- добавить новую заявку в mutable pool;
- учитывать приоритет, навык, транспорт и окно;
- если назначить нельзя — вернуть unassigned с причиной.

### Request cancelled

- убрать заявку из mutable future;
- locked past не переписывать;
- освободившееся будущее время доступно оптимизации.

### Engineer unavailable

- сохранить его locked history;
- исключить из будущего распределения;
- перераспределить будущие заявки либо вернуть unassigned.

### Engineer available

- сохранить общую locked history;
- добавить инженера в будущий доступный pool с корректной позицией/временем старта;
- не восстанавливать старый отклонённый кандидат.

## Аудит

- событие применено ровно один раз;
- locked stops идентичны base;
- отменённая mutable request не назначена;
- unavailable engineer не имеет новых future stops;
- urgent request присутствует assigned или unassigned;
- полный набор заявок согласован с event snapshot.

## Не входит

- хранение/status события;
- проверка повторных переходов;
- несколько events;
- время события от пользователя;
- diff.

## Критерии приёмки

1. Все четыре типа дают полный валидный snapshot.
2. Event применяется только к будущей части.
3. Неизменяемая история не меняется.
4. Output совместим с A03 и backend persistence.
5. `make check` проходит.
