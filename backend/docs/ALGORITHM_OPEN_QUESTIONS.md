## 1. Что исправлено в этой сессии (с доказательствами)

### 1.1 Лимит точек в одном запросе к OSRM Table API

Публичный demo-сервер `router.project-osrm.org` жёстко ограничивает число
координат в одном `Table`-запросе. Измерено бинарным поиском вживую:

| Точек | Статус |
|---|---|
| 100 | `200 OK` |
| 101 | `400 {"message":"Too many table coordinates","code":"TooBig"}` |

При максимуме по ТЗ (до 100 заявок + до 15 инженеров = до 115 точек в
одной матрице на округ) старый код падал бы **гарантированно** на любом
округе, где суммарно набирается больше 100 точек.

**Исправлено**: `RoutingService._iter_blocks` (`src/core/routing/service.py`)
разбивает точки на куски ≤ `cfg.routing.max_table_coordinates // 2` и
запрашивает попарные объединения кусков — несколько HTTP-запросов вместо
одного, матрица собирается полностью. Лимит вынесен в конфиг
(`cfg.routing.max_table_coordinates = 100`), не захардкожен — при переходе
на self-hosted OSRM (там лимита обычно нет) или другого провайдера
достаточно поменять число в конфиге.

**Проверено вживую** (не только юнит-тестом): 115 случайных точек в
Москве/области → 3 HTTP-запроса, матрица собралась за 1.6 сек, случайные
пары (включая пары из разных "кусков") дают согласованные симметричные по
структуре (не по значению — `driving` асимметричен) результаты.

Дальше — сквозной прогон на реалистичном объёме (12 инженеров, 100 заявок,
112 точек): матрица через реальный OSRM — 1.1 сек, `DistributionPlanner` +
`LayeredExactStateGraph` — 0.67 сек, 84/100 заявок размещено, 11/12
инженеров задействовано, 16 неразмещённых — все с корректной причиной
`no_available_engineer`. Без единого падения.

### 1.2 Неверный маппинг ошибок провайдера

`400 Bad Request` от OSRM (наша проблема — некорректный запрос, например
та же "слишком много точек") раньше ловился тем же `except httpx.HTTPError`,
что и реальные сетевые сбои, и превращался в `RoutingUnavailableError`
("сервис недоступен") — вводя в заблуждение: проблема была на нашей
стороне, не у провайдера.

**Исправлено**: `_fetch_block` отдельно ловит `httpx.HTTPStatusError`
(4xx/5xx с ответом от сервера — это провайдер **ответил**, просто отклонил
запрос) и маппит в `InvalidRoutingResponseError`, а `RoutingUnavailableError`
остаётся только для реальной недоступности (таймаут, обрыв соединения —
`httpx.HTTPError`, не `HTTPStatusError`).

## 2. Найдено, но НЕ исправлено — ждёт решения

### 2.1 Все виды транспорта считаются как `car`

`RoutingService`/`AlgorithmService` строят одну общую матрицу через
`cfg.routing.profile` (`"driving"`) для всех точек округа, **независимо от
`Engineer.vehicle_type`** конкретного инженера. Это касается не только
гипотетических данных: `cfg.planning.default_vehicle_type` (`src/config/config.py`)
по умолчанию — **`"public_transport"`**, не `"car"`, и именно этот дефолт
получают синтетические инженеры при импорте (транспорт в датасете не
указан, см. `SUMMARY.md`). То есть при дефолтном конфиге все инженеры
сейчас планируются по скорости автомобиля, хотя формально считаются
пользователями общественного транспорта — заниженное время в пути,
нарушение даже упрощённого требования ТЗ (см. п. 4 ниже — усреднённая
скорость должна быть скоростью **этого** вида транспорта).

**Не исправлено.** Нужное решение: `car` — через OSRM `driving`
(как сейчас), `pedestrian`/`bicycle`/`public_transport` — расстояние по
прямой (`geopy`/формула гаверсинуса, координаты уже есть) с усреднённым
коэффициентом скорости на вид транспорта (константы завести в
`cfg.routing` — например `pedestrian_kmh`/`bicycle_kmh`/`public_transport_kmh`).
Правило и коэффициенты уже подтверждены ТЗ как допустимые (`SUMMARY.md`,
`TECHNICAL_CONSTRAINTS.md` §4 — см. цитату в п. 4).

### 2.2 Недостижимая пара точек роняет весь план округа

Если провайдер вернёт `null` для конкретной пары (адрес не примыкает к
дороге — редко, но случается при неточном геокодировании), `TravelMatrix.minutes`/
`.kilometers` бросают `UnreachablePointsError` (`src/core/routing/service.py`).
Стратегии (`shared/context.py`, все 6 `strategies/*.py`) вызывают эти
методы без `try/except` — исключение всплывает необработанным через
`DistributionPlanner.assign` до `AlgorithmService.plan_initial`, обрывая
построение плана **для всего округа**, хотя проблема — в одной точке.

**Не исправлено.** Хочет отдельного решения о семантике: скорее всего
правильно — на уровне `AlgorithmService` (до вызова `DistributionPlanner`)
проверить пары "старт инженера → заявка" на достижимость и заранее
выкинуть недостижимые заявки из соответствующих пулов с причиной
`no_time_slot` (простой вариант) или завести новый `UnassignedReason`
(например, `no_route`, потребует миграции enum — более честный вариант, но
дороже). Внутри маршрута (заявка → заявка) недостижимость сложнее — там
уже нужно либо ловить исключение внутри каждой из 6 стратегий (дорого,
дублирование в 6 местах), либо `TravelMatrix` отдавать "бесконечность"
вместо исключения и полагаться на то, что окно/смена сами отбросят такой
вариант (тише, но неявно, точки без реального пути будут молча
"невыгодны", а не явно исключены).

### 2.3 Время выезда для трафик-зависимого провайдера

Обсуждали: если переходим на 2ГИС/Яндекс (умеют учитывать пробки по
времени выезда), нужен `departure_time` — предложена эвристика "середина
окна заявки" (окно 18-20 → 19:00). Технически у обоих API `departure_time`
— **один параметр на весь запрос матрицы**, не индивидуальный на пару
точек. Честная реализация идеи требует группировки точек по времени
(бакеты по середине окна) и отдельного вызова матрицы на каждый бакет —
это отдельная ось чанкинга поверх уже существующей (по числу точек,
`_iter_blocks`), увеличивает число HTTP-вызовов и (для 2ГИС, где
тарификация идёт по элементу матрицы) стоимость. Для OSRM `departure_time`
не существует как параметр вообще — там эта идея нереализуема независимо
от решения.

**Не реализовано, ждёт решения по п. 3** (выбор провайдера) — теряет
смысл, если остаёмся на OSRM.

## 3. Прогуглено по провайдерам (2026-09-21)

### Яндекс Карты — Distance Matrix API

- **Бесплатного тарифа нет вообще** — только коммерческая лицензия
  (помесячная/годовая подписка).
- Тарификация — за **каждый элемент матрицы** (матрица 5×5 = 25
  тарифицируемых единиц, не 1 запрос).
- Два вида лицензии: стандартная (нельзя сохранять/изменять полученные
  данные) и расширенная (можно) — нам как минимум нужно сохранять
  `PlanStop.travel_minutes`/`distance_km` в БД, то есть годится только
  расширенная лицензия.
- Отдельно существует старый JS API 1.x "Маршрутизатор" с лимитом
  "25 000 запросов/сутки" в условно-бесплатном режиме — но это
  клиентский browser-side JS API для одной пары точек за раз (не матрица,
  не серверный REST), для backend-планирования не подходит напрямую.

Источники: [Матрица расстояний — API Яндекс Карты](https://yandex.ru/maps-api/products/distancematrix-api),
[Тарифы — API Яндекс Карты](https://yandex.ru/maps-api/tariffs),
[Введение — API Матрицы расстояний](https://yandex.ru/dev/distance_matrix/doc/ru/).

### 2ГИС — Distance Matrix API

- Бесплатный **demo-ключ** доступен через личный кабинет
  [platform.2gis.ru](https://platform.2gis.ru/ru) — тестовый период
  ограничен по времени (порядка месяца), для регулярного продакшена нужен
  платный ключ.
- Синхронный режим ограничен **25 точек** на старты/финиши за запрос
  (меньше, чем измеренный лимит OSRM в 100) — но у нас уже есть
  chunking-инфраструктура (`_iter_blocks`), переиспользуется под новый
  лимит через `cfg.routing.max_table_coordinates = 25`.
- Тарификация — за каждую комбинацию старт×финиш (аналогично Яндексу).
- **Поддерживает учёт текущих и статистических пробок** — то, чего нет у
  OSRM ни в каком виде.

Источники: [Distance Matrix API — Обзор — 2ГИС Документация](https://docs.2gis.com/en/api/navigation/distance-matrix/overview),
[Тарифы и правила тарификации — 2ГИС](https://docs.2gis.com/platform-manager/subscription/pricing),
[Создание ключей доступа — 2ГИС](https://docs.2gis.com/en/platform-manager/subscription/keys).

### Вывод (не решение — вводные для решения)

- Бесплатно и без пробок — OSRM (сейчас).
- Бесплатно (на время хакатона) и с пробками — 2ГИС demo-ключ, но нужно
  самостоятельно завести ключ на `platform.2gis.ru` (агент это сделать не
  может).
- С пробками и без ограничения по времени демо — только платно (Яндекс с
  первого запроса, 2ГИС после истечения демо-периода).

## 4. Уточнения по домену (из ТЗ, не домыслы)

### 4.1 Пеший инженер и общественный транспорт — не одно и то же

`VehicleType` (`src/core/db/enums.py`) — четыре взаимоисключающих
значения: `CAR`, `PEDESTRIAN`, `BICYCLE`, `PUBLIC_TRANSPORT`. У инженера
ровно одно значение. "Пеший" инженер в нашей модели по определению не
пользуется автобусом — если по факту он комбинирует ходьбу и транспорт,
это либо отдельная категория `PUBLIC_TRANSPORT` целиком, либо
"комбинированный транспорт", который ТЗ явно называет необязательным
бонусом:

> Для пешехода/велосипеда/общественного транспорта время в пути
> **допустимо** считать по усреднённой скорости/времени "от точки до
> точки" — расчёт реальных маршрутов общественного транспорта **не
> обязателен**. Решение, которое всё же умеет реалистично считать маршрут
> для бригад без авто (в т.ч. комбинированный транспорт) —
> **дополнительный плюс** при оценке, не победная фича сама по себе.
> (`TECHNICAL_CONSTRAINTS.md`, §4; дословно повторено в `SUMMARY.md`)

Смешивание режимов внутри одной поездки требует отдельного мультимодального
роутера (GTFS-фид или транзитный API) — это не мелкая правка, откладывается
как бонус, не требование.

### 4.2 Self-hosted OSRM не решает вопрос пробок

Важная поправка к `docs/ROUTING.md`: self-hosted OSRM **не добавляет**
точности по пробкам относительно публичного demo-сервера — это то же
самое ядро без учёта трафика, разница только в надёжности/скорости/лимитах
запросов, не в качестве прогноза времени. У OSRM `Table`/`Route API`
физически нет параметра "время выезда" — время в пути всегда статично,
посчитано по профилю скоростей дорог (`car.lua`), не по факту загруженности.
Учитывать пробки в OSRM технически можно только вручную скормив внешние
данные о скорости сегментов (`osrm-contract --segment-speed-file`) — а
источника таких данных у нас нет (это и есть то, что продают Яндекс/2ГИС).

  синтетике и на реалистичном объёме — валидные маршруты, корректные
  причины отказа.

- DI-контейнер (`src/main.py::container`) собирается без конфликтов типов.

**НЕ проверено**:
- Полный HTTP-прогон через настоящий `POST /planning/initial` с живой
  Postgres/S3/геокодированием — `make up` в этой сессии не поднимался.
  Репозитории `Plan`/`PlanStop`/`PlanUnassignedRequest` написаны по тому
  же паттерну, что уже рабочие `Request`/`Engineer`, но вживую не
  выполнялись.
- Поведение при реальных "грязных" геокодированных адресах (риск п. 2.2).
