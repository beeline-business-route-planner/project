# CODE_STYLE.md

Как пишется код внутри файла — импорты, переменные/функции на уровне
модуля, наименование по слоям, ошибки, логирование, комментарии. Про то,
какой слой (`api`/`services`/`db`) за что отвечает — см.
[ARCHITECTURE.md](./ARCHITECTURE.md).

---

## 1. Инструменты — обязательны перед каждым коммитом

```bash
make check   # ruff format --check + ruff check + mypy
# или при необходимости поправить:
make lint-fix
```

- **ruff** — форматирование и линт. Конфиг в `pyproject.toml`:
  - `line-length = 100`
  - `target-version = "py314"`
  - кавычки — **только двойные** (`quote-style = "double"`)
  - активные правила: `E, F, I, W, B, C4, UP, SIM` (pycodestyle, pyflakes,
    isort, warnings, bugbear, comprehensions, pyupgrade, simplify)
- **mypy** — строгая типизация: `check_untyped_defs`, `warn_unused_ignores`,
  `warn_redundant_casts`, `ignore_missing_imports` (для нетипизированных
  сторонних либ).

Если `ruff` или `mypy` ругаются — правим код, а не подавляем правило
точечным `# noqa`/`# type: ignore` без крайней необходимости. Если
подавление всё же нужно — обязательно с конкретным кодом правила
(`# noqa: E501`, `# type: ignore[arg-type]`), не голым.

## 2. Импорты

Все `import`/`from ... import ...` — единым блоком в начале файла, сразу
после docstring модуля (если есть). Порядок сортируется автоматически ruff
(`I`, isort-совместимо) на 3 группы, разделённые пустой строкой: стандартная
библиотека → сторонние пакеты → `src.*`:

```python
import logging
from contextlib import asynccontextmanager

import uvicorn
from dishka import make_async_container
from fastapi import FastAPI, Request

from src.api import router
from src.config import cfg
from src.core.di import DbProvider
```

Внутри пакетов `src` — **только абсолютные импорты**
(`from src.core.db.models.base import Base`), относительные
(`from .base import Base`) не используются.

**Запрещено**: импорт внутри функции/метода (единственное исключение —
разрыв циклического импорта, как временная мера с комментарием, а не по
умолчанию), отложенный/условный импорт «по месту использования» ради
удобства.

**`from __future__ import annotations`** — не добавлять по умолчанию/по
привычке. Добавляется только когда без него реально не обойтись (конкретная
причина, которую можно назвать), и тогда рядом — комментарий, почему.

## 3. Состояние модуля, атрибуты класса и функции

### 3.1 Module-level присваивания: запрещены по умолчанию

Обычный файл с поведением (`router.py`, `service.py`, `presenter.py`,
`utils.py`, репозиторий, клиент, стратегия алгоритма) после импортов должен
переходить к объявлениям классов и функций. Данные вида `NAME = ...` /
`_NAME = ...` в начале такого файла запрещены — независимо от регистра,
ведущего `_`, неизменяемости и количества использований.

Фраза «используется несколько раз» **не является основанием** для
module-level константы. Значению сначала определяется смысл, затем место:

- настройка окружения или параметр алгоритма → типизированная секция
  `Config`, доступ исключительно через единый `cfg`;
- закрытый набор значений API/домена → `Enum`/`StrEnum` в доменном
  `enums.py`; порядок закрытого набора — порядок объявления enum, а не
  отдельный tuple рядом с сервисом;
- структура входа/выхода → `@dataclass(frozen=True)` в `dto.py`;
- значение нужно одному методу → локальная переменная этого метода;
- таблица соответствий — явный метод/`match` в отвечающем за правило
  классе; большой справочник → отдельный декларативный модуль, согласованный
  с пользователем, а не случайный словарь в `service.py`;
- технический реестр/метаданные фреймворка → специализированный registry,
  wiring- или declarative-файл.

**Исчерпывающий список обычных исключений:**

- `log = logging.getLogger(__name__)`;
- `router = APIRouter(...)` и аналогичный объект регистрации фреймворка;
- Prometheus-метрики в выделенном модуле метрик;
- `__all__` в `__init__.py`;
- декларативные/wiring-модули, назначение которых именно в объявлении
  объектов: `config.py`, `enums.py`, `src/core/db/db.py`, DI-провайдеры,
  ORM-модели и реестр HTTP-исключений.

Любое новое исключение к этому списку сначала согласуется с пользователем и
документируется здесь. Нельзя маскировать данные под `Final`,
`MappingProxyType`, property-фабрику или функцию без аргументов только ради
обхода правила.

Module-level инстанс класса ради удобства вызова запрещён. Stateless-класс
вызывается через `ClassName.method(...)`; stateful-класс создаётся DI.

### 3.2 Атрибуты класса

Сервис не является контейнером констант. В `Service`/`Presenter` запрещены
`ClassVar`, справочники, списки ключей, regex и настройки алгоритма на уровне
класса. Атрибуты экземпляра создаются только из зависимостей/состояния,
полученных через `__init__`.

Если сервису понадобился `ClassVar` со списком ключей ответа, он смешал
словарь API, порядок представления и оркестрацию use-case. Правильная
декомпозиция:

1. ключи групп — доменный `StrEnum` в `src/api/<domain>/enums.py`;
2. тип поля `group` в DTO/Pydantic-схеме — этот enum, не свободный `str`;
3. классификация и сборка read-model — `<Domain>Presenter` в
   `src/api/<domain>/presenter.py`;
4. `<Domain>Service` только загружает данные через UoW и передаёт их
   presenter'у.

Допустимый атрибут класса — только часть контракта типа, которую требует
библиотека/ORM/ABC (`model` репозитория, `name`/`slug` стратегии и т.п.).
Не добавлять атрибут класса просто потому, что к нему удобно обращаться из
`@classmethod`; для stateless-логики использовать `@staticmethod`.

### 3.3 Module-level функция с `_`

Модульная (не метод класса) функция с `_` в начале имени — всегда сигнал
остановиться и определить, какой из случаев:

1. **Используется один раз** → не выносится вообще, инлайнится в месте
   вызова.
2. **Нужны объекты уровня приложения** (`UoW`, репозиторий, `Request`,
   другой атрибут `self`) и функция специфична одному домену → приватный
   **метод** класса-сервиса (`self._метод`), не кандидат в `utils` ни при
   каком раскладе, сколько бы раз ни переиспользовалась.
3. **Работает только с голыми значениями** (без `UoW`/репозитория/
   HTTP-объекта на входе) **и используется 2+ раз, но только внутри одного
   домена** — не важно, только внутри одного класса или ещё и в
   роутере/другом сервисе того же домена → `src/api/<domain>/utils.py`.
4. **Работает только с голыми значениями и используется в 2+ доменах** →
   `src/core/utils/` (см. `ARCHITECTURE.md`, раздел Utils). В обоих случаях
   3 и 4 функции — **без ведущего `_`** (это уже переиспользуемый хелпер, не
   приватная деталь одного файла).

Пограничный случай: функция на голых значениях, используемая 2+ раз, но
**строго внутри одного класса** и оставленная там ради читаемости, остаётся
методом этого класса; если она не трогает `self`, это `@staticmethod`, не
обычный метод экземпляра. Если таких преобразований несколько и вместе они
собирают API read-model, это уже отдельный presenter, а не пачка staticmethod
в сервисе (см. `ARCHITECTURE.md`).

### 3.4 Методы класса

- `@staticmethod` — метод относится к ответственности класса, но не читает
  `self`/`cls`.
- `@classmethod` — только альтернативный конструктор либо настоящий
  полиморфизм по классу. Доступ к `ClassVar` ради справочника не причина для
  `classmethod`.
- Обычный приватный метод — шаг use-case, использующий зависимости/состояние
  экземпляра.
- Порядок в классе: `__init__` → публичные методы → приватные методы.
  Вспомогательный метод располагается рядом с ответственностью, а не в
  произвольном порядке по мере написания.
- Если метод принимает больше четырёх связанных значений одного понятия,
  сначала проверить, не является ли этот набор отдельным frozen DTO. Не
  вводить DTO ради случайной пары аргументов.
- Boolean-флаг, полностью меняющий сценарий метода (`do(..., special=True)`),
  обычно означает два публичных use-case или enum режима. Флаг допустим,
  только когда обе ветки остаются одной операцией и различие названо в
  контракте.

## 4. Типизация

- Типизируем **всё**: сигнатуры функций и методов, возвращаемые значения,
  атрибуты классов. `-> None` пишем явно, даже когда функция ничего не
  возвращает.
- Generics через новый синтаксис Python 3.12+ (PEP 695), без `TypeVar`:
  ```python
  class BaseRepository[ModelType: Base]:
      model: type[ModelType]
  ```
- Современные типы из `X | Y`, `list[...]`, `dict[...]` — не `Optional[X]`,
  `List[...]` (за это отвечает правило `UP`).
- Для датаклассов с `from_orm` — `typing.Self` как тип возврата
  classmethod'а.
- Не использовать `Any` как способ закончить рефакторинг типов. На границе
  нетипизированной библиотеки значение один раз проверяется/преобразуется в
  известный тип; дальше `Any` не распространяется.
- Публичный type alias объявляется современным `type Alias = ...` в
  `dto.py`/узком `types.py`, если он действительно является частью
  контракта. Не создавать `Alias = ...` среди данных behavior-модуля.
- Если tuple/dict имеет именованные поля и доменный смысл, это frozen
  dataclass, а не усложняющийся type alias.

## 5. Наименование

- **Файлы и модули** — `snake_case`, в единственном числе для одной
  сущности (`config.py`, `middleware.py`), множественное — для пакета с
  несколькими похожими сущностями (`models/`, `repositories/`, `dto/`).
- **Классы** — `PascalCase` (`UnitOfWork`, `BaseRepository`).
- **Функции, методы, переменные** — `snake_case`.
- **Разрешённые декларативные константы** — `UPPER_SNAKE_CASE`; только в
  файлах из whitelist §3.1. Регистр имени не разрешает константу в
  behavior-файле.
- **Приватные атрибуты класса** — один подчёркивающий префикс
  (`self._session`), не двойной.
- **Модели БД** (`src/core/db/models/`) — один файл = одна модель,
  `snake_case` от имени класса в единственном числе:
  `user.py` → `User`, таблица генерируется автоматически как
  `cls.__name__.lower()` — руками `__tablename__` не переопределяем без
  явной причины.
- **DTO из `src/core/db/dto/`** — обычные `@dataclass`, наследники `BaseDTO`,
  не содержат ORM-логики, получаются из модели через
  `SomeDTO.from_orm(model_instance)`. DTO никогда не импортируют SQLAlchemy.
  Не путать с локальными датаклассами в `src/api/<domain>/dto.py` /
  `src/core/<system>/dto.py` (см. `ARCHITECTURE.md`, разделы «API-слой» и
  «Клиенты внешних API...») — те не наследуют `BaseDTO` и никак не связаны
  с ORM, это просто входные/выходные формы конкретного сервиса.
- **Все DTO** — `@dataclass(frozen=True)`, если библиотечный контракт явно
  не требует мутабельности. Коллекции в публичном DTO по умолчанию
  неизменяемые (`tuple`, `frozenset`), если вызывающему не нужна мутация.
- **Репозитории** (`src/core/db/repositories/`) — по одному на модель,
  наследуют `BaseRepository[ModelType]`, только методы доступа к данным.
  Бизнес-правила и оркестрация нескольких репозиториев — в сервисном слое.
- **DI-провайдеры** (`src/core/di/`) — файл называется по домену, который
  собирает (`payments.py`), не по классу. Добавляется, когда у сущности
  есть жизненный цикл, который нужно собрать.
- **Pydantic-схемы API** — отдельные `pydantic.BaseModel`, не переиспользуем
  DTO/ORM-модели напрямую как `response_model`. Название:
  `<Entity><Action>Request` / `<Entity>Response`
  (`PlanGenerateRequest`, `RequestItemResponse`).
  Мутабельные defaults задаются через `Field(default_factory=...)`, не
  литералом `[]`/`{}`.
- **Модуль-логгер** — создаётся только если файл реально логирует; всегда
  называется `log` и объявляется сразу после импортов:
  `log = logging.getLogger(__name__)`.

## 6. Docstring и комментарии

- По умолчанию **без комментариев** — код должен быть понятен через
  именование.
- Docstring пишем только там, где поведение метода не очевидно из сигнатуры
  или содержит тонкости, которые не следует передавать только именованием
  параметров.
- Формат — **Google-style**. Заголовки секций (`Args`, `Returns`, `Raises`,
  `Yields`, `Note`, `Example`) — **на английском**, ровно как в стандарте,
  без перевода: это фиксированные ключевые слова, которые понимают IDE и
  генераторы документации. Всё остальное — на русском.
  Простой однострочный docstring без секций — тоже целиком на русском:
  ```python
  def to_dict(self) -> dict[str, object]:
      """Преобразует объект модели в словарь по колонкам."""
  ```
- Полный Google-style с секциями — когда у метода есть параметры, есть что
  сказать про возврат, или он бросает исключения, которые вызывающему важно
  знать:
  ```python
  def build_route(self, engineer: Engineer, requests: list[Request]) -> Route:
      """Строит маршрут инженера с учётом временных окон заявок.

      Args:
          engineer: инженер, для которого строится маршрут.
          requests: заявки, уже отфильтрованные по квалификации и транспорту.

      Returns:
          Маршрут с упорядоченным списком заявок и суммарным пробегом.

      Raises:
          NoFeasibleRouteError: если ни одна заявка не помещается во
              временные окна инженера с учётом его смены.
      """
  ```
- Комментарий внутри кода — только если объясняет неочевидное
  решение/ограничение, не пересказывает код построчно. Максимум — короткая
  пара строк; длиннее — повод для docstring'а функции.

## 7. Ошибки и исключения

- **Один слой исключений на домен**, не два: `src/api/exc/<domain>.py` —
  единственное место, где домен объявляет свои исключения. Никакого
  параллельного `service_exc.py` в проекте нет и не заводится — исключение
  и его HTTP-интерпретация объявляются вместе, декоратором
  `http_error` (`src/api/exc/base.py`):
  ```python
  from src.api.exc.base import http_error

  @http_error(status_code=404, detail="Заявка не найдена")
  class EntityNotFoundError(Exception):
      pass
  ```
  `service.py` импортирует и райзит `EntityNotFoundError` как обычный
  `Exception` — **не импортирует FastAPI**, декоратор не превращает класс в
  `HTTPException`-наследника, просто запоминает пару
  (класс, `status_code`, `detail`) в общем реестре. `src/main.py` при
  старте один раз вызывает `register_all(app)` — Starlette сам ловит это
  исключение где угодно в цепочке вызова (сервис, репозиторий) и переводит
  в HTTP-ответ; **роутер не пишет `try/except`**, только
  `return await service.do_something(...)`.
- **Исключения core-сервисов** (`src/core/<system>/exc.py`) декоратором
  `http_error` не
  украшаются в месте определения — `core`-сервис не должен знать про HTTP
  (и физически не может импортировать что-либо из `src/api/`, зависимости
  идут только вниз, см. `ARCHITECTURE.md`), а разные домены, вызывающие
  один и тот же core-сервис, могут захотеть разную интерпретацию одной и
  той же ошибки. Вместо этого домен, вызывающий core-сервис, сам ловит его
  исключение в своём `service.py` и перевыбрасывает **свой** — уже
  задекорированный, объявленный в его же `exc/<domain>.py` — эквивалент:
  После перевыброса API-исключение проходит через тот же реестр и
  автоматически переводится в HTTP без `try/except` в роутере.
- Кастомное исключение заводится, только если вызывающему коду важно
  различать причину (разные HTTP-статусы, разные логи, ретраить/не
  ретраить). Если разницы нет — не ловить и не переупаковывать исходное
  исключение. Намеренно поднимать голый `Exception` запрещено: использовать
  подходящий built-in для ошибки программиста/значения либо осмысленный
  доменный тип для ожидаемого отказа.
- Непойманные исключения (никогда не декорированные `http_error`) ловятся
  глобальным `@app.exception_handler(Exception)` в `src/main.py`.
- `except Exception as exc:` — допустимо только на настоящей границе
  процесса/глобальном обработчике. При переводе core-ошибки в API-ошибку и
  во внутренней бизнес-логике ловится конкретный тип.
- `raise` без обработки внутри `except` — осознанный проброс наверх. Если
  ловишь и проглатываешь — рядом лог с объяснением, почему это безопасно.

## 8. Асинхронность

- Весь I/O (БД, внешние HTTP-вызовы) — только `async`/`await`, синхронных
  блокирующих вызовов в обработчиках запросов быть не должно.
- Асинхронные генераторы для ресурсов с жизненным циклом (сессия БД, UoW) —
  через `AsyncIterator[...]` + `yield`, как в `src/core/di/session.py`.
- Не использовать `asyncio.gather` с одним `UnitOfWork`/`AsyncSession`.
  Параллелить можно независимые внешние вызовы или операции с отдельными
  сессиями и явно определённой семантикой частичного сбоя.

## 9. Логирование

- Только `logging`, без `print()`.
- Сообщение — стабильный идентификатор события `<domain>.<event>` в
  lowercase snake_case (`"planning.import_completed"`), не человеческое
  предложение и не динамическая f-строка.
- Формат — структурные JSON-логи (`StructuredJsonFormatter`), дополнительные
  поля передаются через `extra={...}`, не форматированием в строку
  сообщения:
  ```python
  log.info("http.request_completed", extra={"http": {"method": ..., "status_code": ...}})
  ```
- `request_id` берётся из контекстной переменной автоматически форматтером —
  вручную его прокидывать в каждый лог не нужно.
- Контекст — именованные безопасные поля: ID, enum, количество, длительность.
  Не логировать содержимое xlsx, секреты и полные пользовательские адреса.
- Исключение логируется один раз на границе, которая принимает решение о
  retry/HTTP 500/компенсации. Каждый промежуточный слой не дублирует один и
  тот же traceback.
- Уровни: `info` — штатная веха, `warning` — ожидаемая нештатная ситуация,
  которую код сам обрабатывает, `error` — реальный сбой, требующий
  внимания.

## 10. Конфигурация

- Все настройки — через `pydantic-settings`-модель `Config`
  (`src/config/config.py`), никаких `os.environ[...]` россыпью по коду.
- Секции конфига — вложенные `BaseModel` (`Database`, `Logging`, `CORS`), а
  не плоский список полей.
- Единственная точка доступа во всём приложении —
  `from src.config import cfg`. Используется привычная иерархия
  `cfg.<section>.<field>` (`cfg.s3.bucket_uploads`,
  `cfg.routing.timeout_seconds`). Секции конфигурации не инжектятся через
  DI и не передаются параметрами по цепочке вызовов.
- Импортировать классы секций напрямую из `config.py` вне самого config-
  модуля запрещено. Это внутренняя схема `cfg`, не публичные зависимости.
- Presenter по возможности получает вычисленный параметр явно от сервиса,
  чтобы сборка read-model оставалась детерминированной. Service/client/
  router могут читать необходимые значения через `cfg` напрямую.
- Секретное значение не имеет fallback, похожий на рабочий секрет. Для
  обязательного секрета используется пустое/обязательное поле и валидация
  на старте соответствующей интеграции.

## 11. Общее

- Ничего не оставляем закомментированным "на всякий случай" — либо код
  нужен, либо удаляется.
- `TODO` допустим только для реально отложенной работы с конкретной причиной
  и ссылкой на документ/задачу. `TODO: refactor`, `FIXME later` и заглушка
  вместо части согласованного scope запрещены.
- Один файл — одна зона ответственности (не смешиваем модели и роутеры в
  одном модуле).
- Явные, длинные и понятные имена важнее сокращений (`get_sessionmaker`, а
  не `get_sm`).
- Не писать «универсальный» base/mixin/protocol до второго реального
  использования. Два похожих фрагмента сначала сравниваются по семантике:
  одинаковая форма кода ещё не означает одну ответственность.
