# CODE_STYLE.md

Как пишется код внутри файла — импорты, переменные/функции на уровне
модуля, наименование по слоям, ошибки, логирование, комментарии. Про то,
какой слой (`api`/`services`/`db`) за что отвечает — см.
[ARCHITECTURE.md](./ARCHITECTURE.md).

---

## 1. Инструменты — обязательны перед каждым коммитом

```bash
make check   # ruff format --check + ruff check + mypy
# или при необходимости поправить:
make lint-fix
```

- **ruff** — форматирование и линт. Конфиг в `pyproject.toml`:
  - `line-length = 100`
  - `target-version = "py314"`
  - кавычки — **только двойные** (`quote-style = "double"`)
  - активные правила: `E, F, I, W, B, C4, UP, SIM` (pycodestyle, pyflakes,
    isort, warnings, bugbear, comprehensions, pyupgrade, simplify)
- **mypy** — строгая типизация: `check_untyped_defs`, `warn_unused_ignores`,
  `warn_redundant_casts`, `ignore_missing_imports` (для нетипизированных
  сторонних либ).

Если `ruff` или `mypy` ругаются — правим код, а не подавляем правило
точечным `# noqa`/`# type: ignore` без крайней необходимости. Если
подавление всё же нужно — обязательно с конкретным кодом правила
(`# noqa: E501`, `# type: ignore[arg-type]`), не голым.

---

## 2. Импорты

Все `import`/`from ... import ...` — единым блоком в начале файла, сразу
после docstring модуля (если есть). Порядок сортируется автоматически ruff
(`I`, isort-совместимо) на 3 группы, разделённые пустой строкой: стандартная
библиотека → сторонние пакеты → `src.*`. Пример (`src/main.py`):

```python
import logging
from contextlib import asynccontextmanager

import uvicorn
from dishka import make_async_container
from fastapi import FastAPI, Request

from src.api import router
from src.config import cfg
from src.core.di import DbProvider
```

Внутри пакетов `src` — **только абсолютные импорты**
(`from src.core.db.models.base import Base`), относительные
(`from .base import Base`) не используются.

**Запрещено**: импорт внутри функции/метода (единственное исключение —
разрыв циклического импорта, как временная мера с комментарием, а не по
умолчанию), отложенный/условный импорт «по месту использования» ради
удобства.

**`from __future__ import annotations`** — не добавлять по умолчанию/по
привычке. Добавляется только когда без него реально не обойтись (конкретная
причина, которую можно назвать), и тогда рядом — комментарий, почему.

## 3. Переменные и функции на уровне модуля

### 3.1 Module-level переменная

Не заводить `имя = значение` в начале файла ради «покрасивее подставить чуть
ниже» — если значение используется **один раз**, подставляется прямо в
место использования литералом, без переменной вообще.

Если значение вычисляется один раз при импорте и **переиспользуется
несколько раз внутри этого же файла** — не проблема с самим наличием
модульной константы: `UPPER_SNAKE_CASE` (см. §5).

**Разрешённые исключения** (не «одноразовые», но и не бизнес-константы):
- **Логгер модуля**: `log = logging.getLogger(__name__)` — всегда, сразу
  после импортов.
- **Framework-обязательные объекты**: `router = APIRouter(prefix="/api")` —
  без него эндпоинтам буквально не на что регистрироваться.
- **Путь к файлу/директории и его инициализация** (склейка сегментов без
  условной логики). Как только к пути добавляется условная логика выбора —
  выносится в `config.py`.
- **Файлы-реестры** (`config.py`, `enums.py`, выделенный `constants.py`) и
  **wiring-файлы**, целиком состоящие из инициализации module-level
  объектов (движок БД, sessionmaker) — не подпадают под запрет, это их
  прямое назначение.

**Не разрешено**: module-level инстанс класса ради удобства вызова его
методов. Если методы класса не используют `self` для состояния — методы
становятся `@staticmethod`, вызов — `ИмяКласса.method(...)` напрямую, без
инстанцирования.

### 3.2 Module-level функция с `_`

Модульная (не метод класса) функция с `_` в начале имени — всегда сигнал
остановиться и определить, какой из трёх случаев:

1. **Используется один раз** → не выносится вообще, инлайнится в месте
   вызова.
2. **Используется 2+ раз, но только внутри одного сервиса/роутера** →
   становится приватным **методом** класса-сервиса (`self._метод`) — не
   нарушение, обычная инкапсуляция.
3. **Используется 2+ раз и не привязана к одному домену** (голые значения,
   без `UoW`/репозитория/HTTP-объекта на входе) → `src/core/utils/` (см.
   `ARCHITECTURE.md`, раздел Utils). В `utils` функции — **без ведущего
   `_`** (это уже переиспользуемый публичный хелпер, не приватная деталь
   одного файла).

Функция, которой для работы нужны объекты уровня приложения (`UoW`,
`Request`) и которая специфична одному домену — не кандидат в `utils` ни при
каком раскладе, она по пункту 2 становится методом сервиса.

## 4. Типизация

- Типизируем **всё**: сигнатуры функций и методов, возвращаемые значения,
  атрибуты классов. `-> None` пишем явно, даже когда функция ничего не
  возвращает.
- Generics через новый синтаксис Python 3.12+ (PEP 695), без `TypeVar`:
  ```python
  class BaseRepository[ModelType: Base]:
      model: type[ModelType]
  ```
- Современные типы из `X | Y`, `list[...]`, `dict[...]` — не `Optional[X]`,
  `List[...]` (за это отвечает правило `UP`).
- Для датаклассов с `from_orm` — `typing.Self` как тип возврата
  classmethod'а.

## 5. Наименование

- **Файлы и модули** — `snake_case`, в единственном числе для одной
  сущности (`config.py`, `middleware.py`), множественное — для пакета с
  несколькими похожими сущностями (`models/`, `repositories/`, `dto/`).
- **Классы** — `PascalCase` (`UnitOfWork`, `BaseRepository`).
- **Функции, методы, переменные** — `snake_case`.
- **Константы модуля** — `UPPER_SNAKE_CASE` (`BASE_DIR`,
  `TOML_SETTINGS_PATH`).
- **Приватные атрибуты класса** — один подчёркивающий префикс
  (`self._session`), не двойной.
- **Модели БД** (`src/core/db/models/`) — один файл = одна модель,
  `snake_case` от имени класса в единственном числе:
  `user.py` → `User`, таблица генерируется автоматически как
  `cls.__name__.lower()` — руками `__tablename__` не переопределяем без
  явной причины.
- **DTO** — обычные `@dataclass`, наследники `BaseDTO`, не содержат
  ORM-логики, получаются из модели через `SomeDTO.from_orm(model_instance)`.
  DTO никогда не импортируют SQLAlchemy.
- **Репозитории** (`src/core/db/repositories/`) — по одному на модель,
  наследуют `BaseRepository[ModelType]`, только методы доступа к данным.
  Бизнес-правила и оркестрация нескольких репозиториев — в сервисном слое.
- **DI-провайдеры** (`src/core/di/`) — файл называется по домену, который
  собирает (`payments.py`), не по классу. Добавляется, когда у сущности
  есть жизненный цикл, который нужно собрать.
- **Pydantic-схемы API** — отдельные `pydantic.BaseModel`, не переиспользуем
  DTO/ORM-модели напрямую как `response_model`. Название:
  `<Entity><Action>Request` / `<Entity>Response`
  (`PlanGenerateRequest`, `RequestItemResponse`).
- **Модуль-логгер** — всегда называется `log`, объявляется сразу после
  импортов: `log = logging.getLogger(__name__)`.

## 6. Docstring и комментарии

- По умолчанию **без комментариев** — код должен быть понятен через
  именование.
- Docstring пишем только там, где поведение метода не очевидно из сигнатуры
  или содержит тонкости, которые не следует передавать только именованием
  параметров.
- Формат — **Google-style**. Заголовки секций (`Args`, `Returns`, `Raises`,
  `Yields`, `Note`, `Example`) — **на английском**, ровно как в стандарте,
  без перевода: это фиксированные ключевые слова, которые понимают IDE и
  генераторы документации. Всё остальное — на русском.
  Простой однострочный docstring без секций — тоже целиком на русском:
  ```python
  def to_dict(self) -> dict[str, object]:
      """Преобразует объект модели в словарь по колонкам."""
  ```
- Полный Google-style с секциями — когда у метода есть параметры, есть что
  сказать про возврат, или он бросает исключения, которые вызывающему важно
  знать:
  ```python
  def build_route(self, engineer: Engineer, requests: list[Request]) -> Route:
      """Строит маршрут инженера с учётом временных окон заявок.

      Args:
          engineer: инженер, для которого строится маршрут.
          requests: заявки, уже отфильтрованные по квалификации и транспорту.

      Returns:
          Маршрут с упорядоченным списком заявок и суммарным пробегом.

      Raises:
          NoFeasibleRouteError: если ни одна заявка не помещается во
              временные окна инженера с учётом его смены.
      """
  ```
- Комментарий внутри кода — только если объясняет неочевидное
  решение/ограничение, не пересказывает код построчно. Максимум — короткая
  пара строк; длиннее — повод для docstring'а функции.

## 7. Ошибки и исключения

- Доменные HTTP-исключения — `src/api/exc/<domain>.py`, наследники
  `src.api.exc.base.Base` (сам он — `fastapi.HTTPException`), задают
  `status_code` и `detail` как **атрибуты класса**, не в `__init__`:
  ```python
  class RequestNotFound(Base):
      status_code = 404
      detail = "Заявка не найдена"
  ```
  Новый файл `src/api/exc/<domain>.py` заводится, когда у домена появляется
  первое собственное исключение — не валить всё в один файл.
- Кастомное исключение заводится, только если вызывающему коду важно
  различать причину (разные HTTP-статусы, разные логи, ретраить/не
  ретраить). Если разницы нет — обычный `Exception` + структурированный лог
  с деталями, не плодить иерархию ради иерархии.
- Непойманные исключения ловятся глобальным
  `@app.exception_handler(Exception)` в `src/main.py` — не оборачиваем
  каждый роут в `try/except Exception`, только точечные бизнес-исключения
  там, где нужно вернуть осознанный HTTP-статус.
- `except Exception as e:` — нормально на границах (точка входа, глобальный
  обработчик); во внутренней бизнес-логике — ловить конкретный тип.
- `raise` без обработки внутри `except` — осознанный проброс наверх. Если
  ловишь и проглатываешь — рядом лог с объяснением, почему это безопасно.

## 8. Асинхронность

- Весь I/O (БД, внешние HTTP-вызовы) — только `async`/`await`, синхронных
  блокирующих вызовов в обработчиках запросов быть не должно.
- Асинхронные генераторы для ресурсов с жизненным циклом (сессия БД, UoW) —
  через `AsyncIterator[...]` + `yield`, как в `src/core/di/session.py`.

---

## 9. Логирование

- Только `logging`, без `print()`.
- Формат — структурные JSON-логи (`StructuredJsonFormatter`), дополнительные
  поля передаются через `extra={...}`, не форматированием в строку
  сообщения:
  ```python
  log.info("HTTP request completed", extra={"http": {"method": ..., "status_code": ...}})
  ```
- `request_id` берётся из контекстной переменной автоматически форматтером —
  вручную его прокидывать в каждый лог не нужно.
- Уровни: `info` — штатная веха, `warning` — ожидаемая нештатная ситуация,
  которую код сам обрабатывает, `error` — реальный сбой, требующий
  внимания.

---

## 10. Конфигурация

- Все настройки — через `pydantic-settings`-модель `Config`
  (`src/config/config.py`), никаких `os.environ[...]` россыпью по коду.
- Секции конфига — вложенные `BaseModel` (`Database`, `Logging`, `CORS`), а
  не плоский список полей.
- Единая точка входа — `from src.config import cfg`, читаем
  `cfg.database.postgres_host` и т.п., глобальный `cfg` создаётся один раз
  на модуле.

---

## 11. Общее

- Ничего не оставляем закомментированным "на всякий случай" — либо код
  нужен, либо удаляется.
- Один файл — одна зона ответственности (не смешиваем модели и роутеры в
  одном модуле).
- Явные, длинные и понятные имена важнее сокращений (`get_sessionmaker`, а
  не `get_sm`).
