# ARCHITECTURE.md

Кто где живёт и что кому разрешено делать — слои `src/api/<domain>`
(router/schemas/service/presenter) → `src/core/db`
(models/dto/repositories/uow), плюс переиспользуемые core-сервисы и клиенты
внешних API в `src/core/<system>/`. Про наименование, импорты, ошибки,
логирование — [CODE_STYLE.md](./CODE_STYLE.md).
Техническая карта (какие модели/эндпоинты реально существуют) —
[PROJECT_CONTEXT.md](./PROJECT_CONTEXT.md), обновляется при каждом
архитектурном изменении.

## Стек

FastAPI + uvicorn · dishka (DI) · SQLAlchemy 2.0 (async) + asyncpg + Alembic ·
pydantic-settings · prometheus-client · структурные JSON-логи.

## Слои и поток запроса

```
Request
  │
  ▼
src/api/<domain>/router.py     HTTP-слой: маршрут и schema ↔ DTO.
  │
  ▼
src/api/<domain>/service.py    Бизнес-логика эндпоинта: оркестрирует репозитории через UoW,
  │                            валидирует бизнес-правила, зовёт внешние клиенты/core-сервисы.
  ├── presenter.py             Опционально: собирает сложный read-model без I/O.
  ▼
src/core/db/
  ├── models/…             SQLAlchemy ORM-модели (таблицы БД).
  ├── dto/…                Датаклассы для передачи данных между слоями без ORM.
  ├── repositories/…       Доступ к данным конкретной модели, без бизнес-логики.
  └── uow.py                UnitOfWork — сессия, репозитории, commit/rollback.
  ▼
PostgreSQL
```

**Правило: зависимости идут только вниз.** Роутер знает про сервис, сервис —
про UoW и репозитории, репозиторий — только про свою модель. Модель не
знает ни про DTO, ни про сервис. DTO не знает про SQLAlchemy.

API-домены изолированы друг от друга: `src/api/<domain_a>/` не импортирует
router/service/schema/presenter из `src/api/<domain_b>/`. Общая логика
опускается на подходящий нижний уровень (`src/core/<system>/`, DB-слой или
`src/core/utils/`), а не связывает два HTTP-домена боковым импортом.

Сервис домена может использовать другие сервисы, привязанные не к
HTTP-эндпоинту, а к конкретной системе/подсистеме (алгоритм, внешний API) —
см. «Клиенты внешних API и внутренние core-сервисы» ниже. Такие сервисы
живут в `src/core/<system>/`, а не в `src/api/<domain>/`, потому что не
привязаны к одному эндпоинту и переиспользуются несколькими доменами.

### Матрица зависимостей

| Слой | Может импортировать | Не может импортировать |
|---|---|---|
| router | свои schemas/DTO/service, FastAPI/Dishka | repository, ORM session, client внешней системы, чужой API-домен |
| schemas | Pydantic, stdlib, публичные enum | service, repository, ORM-модели, DI |
| domain service | свои DTO/presenter/API exceptions, UoW, core-сервисы | FastAPI, Pydantic schemas, router, чужой API-домен |
| presenter | свои DTO/enums, входные модели/DB DTO | UoW, repository, config singleton, client/service, FastAPI |
| parser | свои DTO/enums/utils, библиотеку формата, `cfg` | UoW, repository, client/service, FastAPI |
| core service | свой client/DTO/enums/exceptions, нижележащие библиотеки | любой `src/api.*` |
| repository | SQLAlchemy, своя модель, DB DTO | API, core service, HTTP schema, commit/rollback |
| ORM model | SQLAlchemy base/enums/связанные модели | DTO, repository, service, API |
| DTO | stdlib types и публичные enum | SQLAlchemy session/repository, FastAPI, DI |

Если для нужного импорта ячейка говорит «нельзя», не использовать локальный
import, `TYPE_CHECKING`, протокол без владельца или service locator как
обход. Сначала исправляется граница ответственности.

## Router (`src/api/<domain>/router.py`)

Файл роутера содержит **только регистрацию эндпоинтов** (`@router.get/post/...`)
и тонкую обвязку: валидация входа делает Pydantic-схема сама, дальше — вызов
сервиса, преобразование результата в response-схему. Никакой прямой работы с
SQLAlchemy-сессией и никакой бизнес-логики внутри хендлера роутера.

**Единственное разрешённое исключение на уровне модуля** — сам объект
роутера, без которого FastAPI буквально не на что регистрировать эндпоинты:

```python
router = APIRouter(prefix="/api")
```

Любой другой module-level объект в файле роутера (локальный клиент, кэш,
инстанс сервиса ради удобства вызова) — не framework-wiring, а обход
DI — запрещено; зависимость запрашивается через `dishka.integrations.fastapi.FromDishka`
в сигнатуре хендлера.

Роутер делает только четыре действия: принимает типизированный ввод,
вызывает один публичный метод сервиса, преобразует DTO в response schema и
возвращает ответ. В нём нет циклов по доменным данным, сортировки,
группировки, транзакций, `try/except` бизнес-ошибок и вызовов репозиториев.
ORM-модель не используется как `response_model` и не возвращается наружу.

`schemas.py` описывает HTTP-форму. Pydantic validator проверяет форму
значения (формат, диапазон, согласованность полей одного запроса), но не
ходит в БД и не реализует бизнес-правило, зависящее от состояния системы.
Такое правило принадлежит сервису.

## Service (`src/api/<domain>/service.py`, класс `<Domain>Service`)

Сервис **живёт в папке своего эндпоинта**, а не в отдельном каталоге на
уровне приложения: он привязан к конкретному домену/роутеру
(`src/api/<domain>/router.py` вызывает `src/api/<domain>/service.py`), и
физическое расположение отражает эту привязку. Заводится, как только
появляется первая бизнес-логика сложнее прямого CRUD (распределение заявок,
перепланирование, сравнение планов, любая оркестрация нескольких
репозиториев, core-сервисов или внешних клиентов).

- Сервис — **всегда класс**. Получает через `__init__` всё, что ему нужно
  (`UnitOfWork`, при необходимости — клиент геокодера/маршрутизации, другой
  core-сервис), — никаких скрытых глобальных зависимостей.
- Сервис **не импортирует FastAPI** и ничего не знает про HTTP/Pydantic-схемы
  запроса — принимает и возвращает DTO или простые типы. Это позволяет
  тестировать сервис без поднятия HTTP-слоя.
- Регистрируется как ещё один `Provider` в `src/core/di/` (DI-провайдеры
  остаются в `core/di/` независимо от того, где физически лежит сам сервис —
  см. «Dependency Injection» ниже), инжектится в роутер.
- Если у домена несколько тесно связанных бизнес-обязанностей — например,
  импорт данных и последующий запуск алгоритма — это **не повод заводить
  два сервисных файла в разных доменных папках**: либо это один класс, либо
  несколько классов в одном `service.py`, если все они обслуживают ровно
  этот эндпоинт. Обязанность, которая переиспользуется несколькими
  доменами (не привязана к одному эндпоинту) — не сервис домена, а
  core-сервис, см. ниже.
- Сервис владеет I/O, транзакционной границей и оркестрацией use-case. Он
  не обязан сам собирать сложное представление ответа. Загрузка нескольких
  коллекций через UoW — обязанность сервиса; индексация, группировка,
  сортировка и сборка вложенных DTO — обязанность presenter'а.
- Простое преобразование одной модели через `DTO.from_orm(...)` остаётся в
  сервисе. Presenter ради одной строки не создаётся.
- Большое число локальных переменных само по себе не нарушение. Сигнал к
  декомпозиции — их роль: если почти все переменные являются индексами,
  бакетами и промежуточными проекциями одного ответа, сервис выполняет
  чужую обязанность. Если они отражают последовательные бизнес-шаги и
  side effects одного use-case, они остаются в сервисе.
- Бизнес-исключения, которые сервис райзит сам — объявляются и
  декорируются (`@http_error(status_code=..., detail=...)`) в
  `src/api/exc/<domain>.py`, не в отдельном `service_exc.py` (такого файла
  в проекте нет, см. «Ошибки и исключения» в `CODE_STYLE.md`). Роутер их не
  ловит — Starlette сам переводит в HTTP-ответ через `register_all(app)`
  (`src/main.py`), поэтому роутер остаётся голым
  `return await service.method(...)`.
- Критерий «эта функция — метод сервиса, а не отдельная функция» — она
  привязана к одной конкретной фиче/домену, даже если по сигнатуре выглядит
  как чистая функция на голых значениях (например, шаг сравнения двух
  версий результата — приватный метод отвечающего сервиса, не отдельная
  функция и не utils).

## Presenter (`src/api/<domain>/presenter.py`)

Presenter нужен только для сложного API read-model: ответ объединяет
несколько коллекций и требует хотя бы двух операций из списка — индексация,
классификация, группировка, сортировка, сборка нескольких вложенных DTO.
Это слой представления, не второй бизнес-сервис.

- Имя — `<Domain>Presenter` или `<Entity>Presenter`.
- Класс stateless: без `__init__`, экземпляров и DI; методы —
  `@staticmethod`, вызов — `ClassName.method(...)`.
- Никаких UoW, репозиториев, HTTP-объектов, `cfg`, клиентов и других
  сервисов. Все данные и параметры передаются явно.
- Никакого I/O, commit/rollback и бизнес-решений, меняющих состояние.
- На входе допустимы уже загруженные ORM-модели/DTO, на выходе — доменные
  DTO. Pydantic response-схемы создаёт только router.
- Закрытые ключи read-model типизируются `Enum`/`StrEnum` в
  `src/api/<domain>/enums.py`; свободные строки и `ClassVar` со списком
  ключей запрещены.

Presenter не создаётся для write-команд, простого CRUD или единичного
`DTO.from_orm`. Нельзя заменять точное имя на `Mapper`, `Helper`, `Builder`,
`Manager`: такие названия скрывают владельца ответственности.

## Parser (`src/api/<domain>/parser.py`)

Parser нужен, когда входной файл/текст имеет самостоятельный формат и его
разбор включает структуру документа, заголовки, преобразование ячеек и
форматную валидацию. Это адаптер входного формата, не use-case.

- Имя — `<Format><Entity>Parser` или `<Domain><Format>Parser`.
- Stateless-класс без DI и экземпляров; методы — `@staticmethod`.
- На входе — bytes/строки/доменный upload DTO, на выходе — типизированный
  parsed DTO.
- Parser может читать лимиты формата через `cfg`, но не использует UoW,
  repository, внешние API, S3 и commit/rollback.
- Parser проверяет корректность формата. Проверки, зависящие от уже
  сохранённых данных или нескольких систем, остаются в service.
- Нельзя складывать разбор большого структурированного файла в набор
  приватных staticmethod основного сервиса.

Для пары простых преобразований значений отдельный parser не создаётся:
достаточно доменных utils по правилам ниже.

## Клиенты внешних API и внутренние core-сервисы (`src/core/<system>/`)

Любая функциональность, которая **не привязана к одному конкретному
эндпоинту**, а переиспользуется несколькими доменами (либо в принципе не
имеет собственного эндпоинта) — интеграция с внешней системой
(S3-совместимое хранилище, кэш, геокодер/роутинг, платёжный шлюз) или
внутренняя предметная логика общего назначения (например, алгоритм
распределения заявок по маршрутам) — отдельный пакет `src/core/<system>/`,
где `<system>` — имя самой системы/протокола/подсистемы, а не абстрактной
роли (`s3`, `routing`, `algorithm`, не `storage`/`cache_client`).

Для интеграций с внешней системой внутри пакета — минимум два файла:

- **`client.py`, класс `<System>Client`** — только подключение: держит
  сырую сессию/пул соединений, умеет получить низкоуровневый клиент.
  Никакой доменной логики — ни одного метода вида `upload_file`/`get_route`.
- **`service.py`, класс `<System>Storage`/`<System>Service`** — вся
  полезная работа поверх `<System>Client`, полученного через `__init__`.
- **`exc.py`** — собственные различимые ошибки подсистемы. Заводится с
  первым публичным исключением; core-ошибка не содержит HTTP-статус и не
  импортирует `src/api`.

Правила внешней интеграции:

- client не создаёт сетевую сессию на каждый вызов; жизненный цикл сессии/
  пула задаёт DI;
- timeout обязателен и приходит из typed config;
- client проверяет транспортный статус и декодирует сырой ответ, service
  проверяет семантику ответа и возвращает собственный DTO;
- наружу не протекают `httpx`/SDK exceptions: пакет переводит их в свои
  конкретные ошибки с сохранением причины через `raise ... from exc`;
- retry не добавляется скрыто. Повтор допустим только для идемпотентной
  операции, с ограничением попыток/backoff и явной эксплуатационной
  причиной;
- логи не содержат секретные headers, полный response body и PII.

Плюс — по мере реальной необходимости, не заранее:

- **`dto.py`** — публичные датаклассы пакета: то, что `<System>Service`
  принимает/возвращает и что нужно за пределами файла. Не заводится, если
  контракт выражается простыми типами.
- **`enums.py`** — публичные закрытые словари значений подсистемы.

Датакласс, который нужен **только внутри одного файла** пакета (внутреннее
состояние конкретной стратегии/алгоритма, не часть публичного контракта) —
не в `dto.py`, а остаётся рядом с кодом, который его использует, с ведущим
`_` в имени — та же логика,
что и для приватных функций/методов (см. `CODE_STYLE.md`, §3.3): без
переиспользования за пределами файла выносить в общий файл незачем, а `_`
явно сигналит «не для импорта снаружи».

Для внутренней логики без внешнего I/O (например, `src/core/algorithm/`) —
`client.py` не нужен, если нет отдельного «сырого» слоя подключения;
`service.py` с классом `<System>Service` — точка входа, которую вызывают
сервисы доменов через DI. Это не бизнес-оркестрация конкретного домена, а
операции над самой подсистемой; сервисы доменов (`src/api/<domain>/service.py`)
зовут `<System>Service` через DI, а не наоборот.

`__init__.py` пакета реэкспортирует только осознанный публичный контракт.
DI-провайдер — `src/core/di/<system>.py`,
собирает зависимости → `<System>Client` (если есть) → `<System>Service`,
регистрируется в корневом контейнере. Не экспортировать внутренний класс
«на всякий случай»: наличие в `__all__` означает поддерживаемый контракт.

## Utils (переиспользуемые функции на голых значениях)

Функция-кандидат в вынос из сервиса — только если одновременно:

1. **переиспользуется в 2+ местах** (2+ вызова, неважно, из одного метода
   класса или из разных), и
2. **работает только с голыми значениями** — никакого `UoW`/репозитория/
   HTTP-объекта/клиента на входе, никакого обращения к состоянию `self`.

Дальше — куда именно выносить, зависит от границ переиспользования:

- **используется только внутри одного домена** (не важно, только внутри
  одного класса-сервиса или ещё и в роутере/другом сервисе того же домена)
  → `src/api/<domain>/utils.py`, без ведущего `_` (это уже переиспользуемый
  публичный хелпер домена, не приватная деталь одного файла). Заводится по
  мере первой реальной необходимости, не заранее.
- **используется в 2+ доменах** (между сервисами/роутерами разных
  `src/api/<domain>/`) → `src/core/utils/<name>.py`.

Если функция на голых значениях реально нужна **ровно в одном месте** — по
умолчанию она вообще не выносится в отдельную функцию/файл (инлайн в месте
использования). Если для читаемости её всё же стоит выделить (например,
большая справочная таблица соответствий), она остаётся в файле сервиса как
метод класса — но раз она не трогает `self`, это **`@staticmethod`**, не
обычный метод (см. `CODE_STYLE.md`, §3.4): вызывается либо через
`self._метод(...)` внутри того же класса, либо через
`ИмяКласса._метод(...)`, если вызывающий метод сам статический.

Функция, которой для работы нужны объекты уровня приложения (`UoW`,
`Request`) и которая специфична одной фиче — не кандидат в `utils` ни при
каком раскладе, независимо от переиспользования: она остаётся обычным
(не статическим) приватным методом сервиса (см. выше), не модульной
функцией с `_`.

Presenter и utils не взаимозаменяемы. Utils — маленькая переиспользуемая
операция над голыми значениями. Presenter — целостная сборка конкретного
read-model, даже если её вызывает ровно один сервис. Нельзя раскладывать
presenter на россыпь функций в `utils.py` только ради уменьшения сервиса.

## DB-слой: модели → DTO → репозитории → UnitOfWork

- **Модели** (`src/core/db/models/`) — источник правды о структуре БД.
  Наследуют `Base` (`src/core/db/models/base.py`), таблица называется
  автоматически как `cls.__name__.lower()`. Каждая новая модель
  **обязательно** импортируется в `src/core/db/models/__init__.py`, иначе
  Alembic не увидит её при автогенерации миграции (см. комментарий в
  `alembic/env.py`).
- **DTO** (`src/core/db/dto/`) — неизменяемые датаклассы для передачи
  данных из слоя доступа к данным наружу, не тянут SQLAlchemy-сессию и
  ORM-специфику. Строятся из модели через `SomeDTO.from_orm(model_instance)`
  (`BaseDTO.from_orm`).
- **Репозитории** (`src/core/db/repositories/`) — один репозиторий на
  модель, наследник `BaseRepository[ModelType]` (`get_by_id`, `add`,
  `delete` уже есть в базовом классе). Специфичные выборки добавляются как
  отдельные async-методы в конкретном репозитории, не в базовом. Доступ к
  репозиторию — только через `uow.<name>`, не создавать репозиторий
  напрямую в сервисе/роутере.
- Репозиторий выражает только чтение/запись своей модели. Он не собирает
  HTTP-ответы, не группирует данные для UI, не импортирует Pydantic-схемы и
  не вызывает `commit()`.
- Запрос с join принадлежит репозиторию корневой сущности результата.
  Если результат не является ORM-сущностью, repository возвращает
  типизированный DB DTO, а не `Row`/tuple неясной формы.
- Стратегия загрузки relationship задаётся запросом явно. Сервис не должен
  случайно запускать lazy load и N+1 при проходе по коллекции.
- **UnitOfWork** (`src/core/db/uow.py`) — держит одну `AsyncSession` на весь
  запрос, агрегирует репозитории как атрибуты и отвечает за
  `commit`/`rollback`. Сервисы получают `UnitOfWork` через DI и работают с
  репозиториями только через него — не создают свои сессии.
- Сервис не использует `uow.session.execute(...)` как короткий путь. Если
  понадобился SQL-запрос, он получает именованный метод подходящего
  repository.

### Транзакционная граница

- `commit()`/`rollback()` вызывает сервис use-case. Роутер и репозитории
  этого не делают. Read-only сервис не вызывает ни commit, ни rollback.
- Один UoW/`AsyncSession` нельзя одновременно использовать в нескольких
  корутинах через `asyncio.gather`; SQLAlchemy session не является
  конкурентно безопасной. Параллельные независимые операции требуют
  отдельных UoW либо выполняются последовательно.
- Долгий внешний HTTP/S3-вызов не держит транзакцию БД открытой без
  осознанной причины. Для смешанного use-case заранее определяются порядок
  side effects, точка commit и компенсация частичного сбоя.
- `flush()` допустим для получения сгенерированного ID, но не заменяет
  commit. Нельзя прятать commit внутри `add()`/`delete()` репозитория.

### Как добавить новую сущность

1. `src/core/db/models/<entity>.py` — SQLAlchemy-модель, зарегистрировать в
   `models/__init__.py`.
2. `src/core/db/dto/<entity>.py` — frozen `<Entity>DTO` с нужными полями.
3. `src/core/db/repositories/<entity>.py` —
   `<Entity>Repository(BaseRepository[<Entity>])` + необходимые выборки.
4. Подключить репозиторий в `UnitOfWork.__init__`
   (`self.<entities> = <Entity>Repository(self.session)`).
5. `make migrate MSG="add <entity> table"` → проверить сгенерированную
   миграцию руками → `make upgrade`.

## Dependency Injection (dishka)

- `Provider`-классы лежат в `src/core/di/`. Один `Provider` = одна связная
  область зависимостей (сейчас — `DbProvider`: движок БД, session maker,
  сессия на запрос, UoW).
- Скоупы:
  - `Scope.APP` — создаётся один раз на всё приложение (engine, sessionmaker);
  - `Scope.REQUEST` — создаётся заново на каждый HTTP-запрос (сессия БД,
    `UnitOfWork`).
- Новый провайдер (сервис планирования, клиент геокодера) — отдельный файл
  в `src/core/di/`, регистрируется в `make_async_container(...)` в
  `src/main.py`.
- В роутере зависимость запрашивается через
  `dishka.integrations.fastapi.FromDishka`, а не создаётся вручную и не
  тянется через глобальные синглтоны.
- Provider содержит только wiring: выбирает scope и связывает конструкторы.
  В нём нет валидации бизнес-правил, SQL-запросов и внешних вызовов.
- Stateless presenter/utils/enums/DTO не регистрируются в DI. Регистрация
  нужна объекту с зависимостями или жизненным циклом, а не каждому классу.
- Service locator запрещён: контейнер не передаётся внутрь service, чтобы
  тот сам доставал зависимости по типу.

## API-слой

- Корневой роутер `src/api/__init__.py` (`APIRouter(prefix="/api")`) —
  точка сборки всех доменных роутеров через `include_router` в
  `src/main.py`.
- Соглашение по доменной папке (заводить по мере появления доменов),
  `src/api/<domain>/`:
  - `router.py` — сам роутер (тонкая HTTP-обвязка, см. «Router» выше);
  - `schemas.py` — Pydantic request/response модели (форма HTTP-контракта);
  - `service.py` — бизнес-логика домена, см. «Service» выше;
  - `presenter.py` — опциональная сборка сложного read-model без I/O;
  - `parser.py` — опциональный stateless-разбор сложного входного формата;
  - `enums.py` — закрытые значения только этого API/read-model; enum'ы,
    которые хранятся в БД, остаются в `src/core/db/enums.py`;
  - `dto.py` — локальные датаклассы сервиса: вход/выход/промежуточное
    состояние его методов, которые не сводятся к Pydantic-схеме ответа и не
    являются ORM-производными DTO из `src/core/db/dto/` (**не путать эти
    два «DTO»** — см. ниже). Тип, присутствующий в публичной сигнатуре
    service/presenter и используемый за пределами файла, переносится в
    `dto.py` сразу — количество типов не имеет значения;
  - `utils.py` — функции, переиспользуемые внутри этого домена на голых
    значениях (см. «Utils» выше); переиспользуемые между доменами —
    `src/core/utils/`, не сюда.

  Датакласс, нужный только внутри одного метода/файла сервиса (не часть
  его публичной сигнатуры) — не в `dto.py`, остаётся на месте с `_` в
  имени, та же логика, что для `src/core/<system>/dto.py` (см. выше).

  **Два разных «DTO» в проекте, не путать:**
  - `src/core/db/dto/` — наследники `BaseDTO`, строятся из ORM-модели через
    `from_orm(model_instance)`, живут на границе БД (см. «DB-слой» ниже);
  - `src/api/<domain>/dto.py` и `src/core/<system>/dto.py` — обычные
    датаклассы без всякой связи с ORM, просто способ не захламлять
    `service.py` формами входа/выхода конкретного сервиса.

  Эти файлы создаются по факту ответственности, не полным комплектом.
  Запрещены универсальные свалки `helpers.py`, `common.py`, `misc.py`,
  `manager.py` и `constants.py` без одного конкретного владельца.
- Исключения домена — не в доменной папке, а в `src/api/exc/<domain>.py`:
  класс исключения и его HTTP-интерпретация объявляются вместе, через
  декоратор `http_error` (см. `CODE_STYLE.md`, раздел «Ошибки»). Туда же —
  собственные перевыбросы исключений core-сервисов. Роутер этот файл не
  импортирует вообще — перевод в HTTP происходит автоматически через
  общий реестр обработчиков.

## Точка входа и сборка приложения

`src/main.py` — единственное место, где:
- создаётся `FastAPI(...)` и DI-контейнер `dishka` (`make_async_container(...)`);
- регистрируются миддлвари (`CORSMiddleware`, `PrometheusMiddleware`,
  `RequestLoggingMiddleware`) — порядок добавления важен: ASGI-миддлвари
  оборачивают друг друга в порядке `add_middleware`, поэтому последняя
  добавленная выполняется раньше при входе запроса;
- подключается корневой роутер `src.api.router`;
- объявлен глобальный обработчик необработанных исключений и служебные
  роуты `/` и `/metrics`.

`src/__main__.py` — просто вызывает `main()` из `src/main.py`, чтобы работал
`python -m src` / `uv run python -m src` (см. `make run`).

## Конфигурация

`src/config/config.py` — один класс `Config(BaseSettings)` с вложенными
секциями (`DatabaseConfig`, `LoggingConfig`, `CorsConfig`, …). Источники в порядке
приоритета: переменные окружения (разделитель вложенности `__`, например
`DATABASE__POSTGRES_HOST`) → `config.toml`. Новая секция конфигурации
(геокодер/маршрутизация) — ещё один вложенный `BaseModel`, подключается в
`Config` как поле. Весь код обращается к настройкам только через единый
`from src.config import cfg`; config-секции не регистрируются в DI.

## Наблюдаемость

- **Логи** — структурный JSON в stdout (`src/core/logging.py`), с
  `request_id` из `contextvars` (`src/core/context.py`), собираются
  Promtail → Loki (docker-compose).
- **Метрики** — Prometheus-миддлварь (`src/core/metrics.py`) считает
  `http_requests_total`, `http_request_duration_seconds`,
  `http_requests_active`, отдаются на `/metrics`; Prometheus + Grafana +
  cAdvisor подняты в `docker-compose.yml`.
- **Request-логи** — отдельная миддлварь (`src/core/middleware.py`)
  логирует каждый запрос (метод, путь, статус, длительность) и прокидывает
  `X-Request-Id` в заголовки ответа.

Доменные Prometheus-метрики объявляются в отдельном `metrics.py` своего
домена/подсистемы и импортируются сервисом. Объявлять `Gauge`/`Counter` в
`service.py` запрещено: это module-level состояние и отдельная
инфраструктурная ответственность.

## Миграции

Alembic настроен на асинхронный движок (`alembic/env.py`), URL берётся из
`cfg.database`, метаданные — из `src.core.db.models.Base.metadata`. Рабочий
цикл — см. скилл `add-migration`.

## Инфраструктура и запуск

`docker-compose.yml` поднимает backend + Postgres + мониторинг-стек одной
командой (`make up`). Для локальной разработки без Docker — поднятый
отдельно Postgres + `make upgrade && make run`. Подробности — `../README.md`.
