# ARCHITECTURE.md

Кто где живёт и что кому разрешено делать — слои `src/api` (router/schemas) →
`src/core/services` → `src/core/db` (models/dto/repositories/uow). Про
наименование, импорты, ошибки, логирование — [CODE_STYLE.md](./CODE_STYLE.md).
Техническая карта (какие модели/эндпоинты реально существуют) —
[PROJECT_CONTEXT.md](./PROJECT_CONTEXT.md), обновляется по факту появления
доменной логики, сейчас пуст — шаблон ещё не оброс сущностями.

## Стек

FastAPI + uvicorn · dishka (DI) · SQLAlchemy 2.0 (async) + asyncpg + Alembic ·
pydantic-settings · prometheus-client · структурные JSON-логи.

## Слои и поток запроса

```
Request
  │
  ▼
src/api/…/router.py        HTTP-слой: FastAPI-роутеры + Pydantic-схемы запросов/ответов.
  │
  ▼
src/core/services/…        Бизнес-логика: оркестрирует репозитории через UoW,
  │                        валидирует бизнес-правила, зовёт внешние клиенты.
  ▼
src/core/db/
  ├── models/…             SQLAlchemy ORM-модели (таблицы БД).
  ├── dto/…                Датаклассы для передачи данных между слоями без ORM.
  ├── repositories/…       Доступ к данным конкретной модели, без бизнес-логики.
  └── uow.py                UnitOfWork — сессия, репозитории, commit/rollback.
  ▼
PostgreSQL
```

**Правило: зависимости идут только вниз.** Роутер знает про сервис, сервис —
про UoW и репозитории, репозиторий — только про свою модель. Модель не
знает ни про DTO, ни про сервис. DTO не знает про SQLAlchemy.

## Router (`src/api/<domain>/router.py`)

Файл роутера содержит **только регистрацию эндпоинтов** (`@router.get/post/...`)
и тонкую обвязку: валидация входа делает Pydantic-схема сама, дальше — вызов
сервиса, преобразование результата в response-схему. Никакой прямой работы с
SQLAlchemy-сессией и никакой бизнес-логики внутри хендлера роутера.

**Единственное разрешённое исключение на уровне модуля** — сам объект
роутера, без которого FastAPI буквально не на что регистрировать эндпоинты:

```python
router = APIRouter(prefix="/api")
```

Любой другой module-level объект в файле роутера (локальный клиент, кэш,
инстанс сервиса ради удобства вызова) — не framework-wiring, а обход
DI — запрещено; зависимость запрашивается через `dishka.integrations.fastapi.FromDishka`
в сигнатуре хендлера.

## Service (`src/core/services/<domain>.py`, класс `<Domain>Service`)

В шаблоне сейчас нет каталога `src/core/services/` — заводится, как только
появляется первая бизнес-логика сложнее прямого CRUD (распределение заявок,
перепланирование, сравнение планов, любая оркестрация нескольких
репозиториев или внешних клиентов).

- Сервис — **всегда класс**. Получает через `__init__` всё, что ему нужно
  (`UnitOfWork`, при необходимости — клиент геокодера/маршрутизации), —
  никаких скрытых глобальных зависимостей.
- Сервис **не импортирует FastAPI** и ничего не знает про HTTP/Pydantic-схемы
  запроса — принимает и возвращает DTO или простые типы. Это позволяет
  тестировать сервис без поднятия HTTP-слоя.
- Регистрируется как ещё один `Provider` в `src/core/di/`, инжектится в
  роутер.
- Критерий «эта функция — метод сервиса, а не отдельная функция» — она
  привязана к одной конкретной фиче/домену, даже если по сигнатуре выглядит
  как чистая функция на голых значениях (пример: шаг сравнения старого и
  нового плана — метод `ReplanningService`, не отдельная функция и не utils).

Ожидаемые для этой задачи сервисы (см. `../../docs/team_discussions/SUMMARY.md`):
- **`PlanningService`** — построение плана: подбор допустимых инженеров под
  заявку по трём обязательным ограничениям (квалификация/время/ресурс),
  вызов алгоритма оптимизации маршрута, сохранение результата как нового
  `Plan`.
- **`ReplanningService`** — принимает событие перепланирования, вызывает
  `PlanningService` заново и сравнивает старый/новый план (`old`/`new`/без
  изменений).
- Расчёт маршрута/времени в пути (геокодирование + матрица расстояний) —
  отдельный клиент по конвенции ниже («Клиенты внешних API»), сервисы
  планирования используют его через DI, не обращаются к внешнему API
  напрямую россыпью по коду.

## Клиенты внешних API (`src/core/<system>/`)

Любая интеграция с внешней системой (S3-совместимое хранилище, кэш,
геокодер/роутинг, платёжный шлюз и т.п.) — отдельный пакет
`src/core/<system>/`, где `<system>` — имя самой системы/протокола, а не
абстрактной роли (`s3`, `dragonfly`, `routing`, не `storage`/`cache_client`).
Внутри пакета — строго два файла:

- **`client.py`, класс `<System>Client`** — только подключение: держит
  сырую сессию/пул соединений, умеет получить низкоуровневый клиент.
  Никакой доменной логики — ни одного метода вида `upload_file`/`get_route`.
- **`service.py`, класс `<System>Storage`/`<System>Service`** — вся
  реальная работа (`upload_file`/`download_file`/`delete_file`,
  `geocode`/`build_route`) поверх `<System>Client`, полученного через
  `__init__`. Это не `src/core/services/` — это операции над самой внешней
  системой, а не бизнес-оркестрация домена; сервисы из
  `src/core/services/` зовут `<System>Storage` через DI, а не наоборот.

`__init__.py` пакета реэкспортирует оба класса. DI-провайдер —
`src/core/di/<system>.py`, собирает сессию → `<System>Client` →
`<System>Service`, регистрируется в `make_async_container(...)`
(`src/main.py`). Эталонный пример — `src/core/s3/` (`S3Client` +
`S3Storage`) и `src/core/di/s3.py`.

## Utils (переиспользуемые функции на голых значениях)

Функция — кандидат в `utils` (`src/core/utils/<name>.py`, заводится при
первой реальной необходимости), только если одновременно:

1. **переиспользуется в 2+ местах** (между сервисами/роутерами), и
2. **работает только с голыми значениями** — никакого `UoW`/репозитория/
   HTTP-объекта/клиента на входе.

Если функция нужна ровно в одном месте — она **не выносится** вообще, даже
если ничего не трогает кроме значений (инлайн в месте использования; вынос
допустим только ради читаемости, не по умолчанию).

Функция, которой для работы нужны объекты уровня приложения (`UoW`,
`Request`) и которая специфична одной фиче — не кандидат в `utils` ни при
каком раскладе: она становится приватным методом сервиса (см. выше), не
модульной функцией с `_`.

## DB-слой: модели → DTO → репозитории → UnitOfWork

- **Модели** (`src/core/db/models/`) — источник правды о структуре БД.
  Наследуют `Base` (`src/core/db/models/base.py`), таблица называется
  автоматически как `cls.__name__.lower()`. Каждая новая модель
  **обязательно** импортируется в `src/core/db/models/__init__.py`, иначе
  Alembic не увидит её при автогенерации миграции (см. комментарий в
  `alembic/env.py`).
- **DTO** (`src/core/db/dto/`) — неизменяемые датаклассы для передачи
  данных из слоя доступа к данным наружу, не тянут SQLAlchemy-сессию и
  ORM-специфику. Строятся из модели через `SomeDTO.from_orm(model_instance)`
  (`BaseDTO.from_orm`).
- **Репозитории** (`src/core/db/repositories/`) — один репозиторий на
  модель, наследник `BaseRepository[ModelType]` (`get_by_id`, `add`,
  `delete` уже есть в базовом классе). Специфичные выборки добавляются как
  отдельные async-методы в конкретном репозитории, не в базовом. Доступ к
  репозиторию — только через `uow.<name>`, не создавать репозиторий
  напрямую в сервисе/роутере.
- **UnitOfWork** (`src/core/db/uow.py`) — держит одну `AsyncSession` на весь
  запрос, агрегирует репозитории как атрибуты и отвечает за
  `commit`/`rollback`. Сервисы получают `UnitOfWork` через DI и работают с
  репозиториями только через него — не создают свои сессии.

### Как добавить новую сущность (например, `Request`/заявку)

1. `src/core/db/models/request.py` — SQLAlchemy-модель, зарегистрировать в
   `models/__init__.py`.
2. `src/core/db/dto/request.py` — `@dataclass RequestDTO(BaseDTO)` с нужными
   полями.
3. `src/core/db/repositories/request.py` — `class RequestRepository(BaseRepository[Request])`
   + доменные выборки.
4. Подключить репозиторий в `UnitOfWork.__init__`
   (`self.requests = RequestRepository(self.session)`).
5. `make migrate MSG="add request table"` → проверить сгенерированную
   миграцию руками → `make upgrade`.

## Dependency Injection (dishka)

- `Provider`-классы лежат в `src/core/di/`. Один `Provider` = одна связная
  область зависимостей (сейчас — `DbProvider`: движок БД, session maker,
  сессия на запрос, UoW).
- Скоупы:
  - `Scope.APP` — создаётся один раз на всё приложение (engine, sessionmaker);
  - `Scope.REQUEST` — создаётся заново на каждый HTTP-запрос (сессия БД,
    `UnitOfWork`).
- Новый провайдер (сервис планирования, клиент геокодера) — отдельный файл
  в `src/core/di/`, регистрируется в `make_async_container(...)` в
  `src/main.py`.
- В роутере зависимость запрашивается через
  `dishka.integrations.fastapi.FromDishka`, а не создаётся вручную и не
  тянется через глобальные синглтоны.

## API-слой

- Корневой роутер `src/api/__init__.py` (`APIRouter(prefix="/api")`) —
  точка сборки всех доменных роутеров через `include_router` в
  `src/main.py`.
- Соглашение по доменным роутерам (заводить по мере появления доменов):
  `src/api/<domain>/router.py` (сам роутер) + `src/api/<domain>/schemas.py`
  (Pydantic request/response модели). Пример: `src/api/plans/router.py`,
  `src/api/plans/schemas.py`.
- Исключения домена — `src/api/exc/<domain>.py`, наследники
  `src.api.exc.base.Base` (см. `CODE_STYLE.md`, раздел «Ошибки»).

## Точка входа и сборка приложения

`src/main.py` — единственное место, где:
- создаётся `FastAPI(...)` и DI-контейнер `dishka` (`make_async_container(...)`);
- регистрируются миддлвари (`CORSMiddleware`, `PrometheusMiddleware`,
  `RequestLoggingMiddleware`) — порядок добавления важен: ASGI-миддлвари
  оборачивают друг друга в порядке `add_middleware`, поэтому последняя
  добавленная выполняется раньше при входе запроса;
- подключается корневой роутер `src.api.router`;
- объявлен глобальный обработчик необработанных исключений и служебные
  роуты `/` и `/metrics`.

`src/__main__.py` — просто вызывает `main()` из `src/main.py`, чтобы работал
`python -m src` / `uv run python -m src` (см. `make run`).

## Конфигурация

`src/config/config.py` — один класс `Config(BaseSettings)` с вложенными
секциями (`Database`, `Logging`, `CORS`, …). Источники в порядке
приоритета: переменные окружения (разделитель вложенности `__`, например
`DATABASE__POSTGRES_HOST`) → `config.toml`. Новая секция конфигурации
(геокодер/маршрутизация) — ещё один вложенный `BaseModel`, подключается в
`Config` как поле.

## Наблюдаемость

- **Логи** — структурный JSON в stdout (`src/core/logging.py`), с
  `request_id` из `contextvars` (`src/core/context.py`), собираются
  Promtail → Loki (docker-compose).
- **Метрики** — Prometheus-миддлварь (`src/core/metrics.py`) считает
  `http_requests_total`, `http_request_duration_seconds`,
  `http_requests_active`, отдаются на `/metrics`; Prometheus + Grafana +
  cAdvisor подняты в `docker-compose.yml`.
- **Request-логи** — отдельная миддлварь (`src/core/middleware.py`)
  логирует каждый запрос (метод, путь, статус, длительность) и прокидывает
  `X-Request-Id` в заголовки ответа.

Расширять наблюдаемость новыми доменными метриками (например, "сколько
заявок не назначено после планирования") — через
`prometheus_client.Gauge`/`Counter`, объявленные рядом с доменным
сервисом, по аналогии с `src/core/metrics.py`.

## Миграции

Alembic настроен на асинхронный движок (`alembic/env.py`), URL берётся из
`cfg.database`, метаданные — из `src.core.db.models.Base.metadata`. Рабочий
цикл — см. скилл `add-migration`.

## Инфраструктура и запуск

`docker-compose.yml` поднимает backend + Postgres + мониторинг-стек одной
командой (`make up`). Для локальной разработки без Docker — поднятый
отдельно Postgres + `make upgrade && make run`. Подробности — `../README.md`.
