## Первичное планирование

`POST /api/planning/initial` принимает multipart-поле `files` с ненулевым
чётным числом `.xlsx`. Для каждого переданного округа обязательна ровно одна
таблица «Синтетические данные» (заявки) и одна таблица «Контрольное
распределение» (инженеры). Округ и вид таблицы определяются по заголовку внутри
книги, поэтому переименование файла не обходит проверку пары.

Сценарий реализован в `src/core/services/planning.py`:

1. разбирает и валидирует все книги;
2. назначает нормативы, приоритет и требуемый навык заявки;
3. получает координаты адресов через `GeocodingService`;
4. сохраняет оригиналы в S3, а нормализованные данные — одной транзакцией БД;
5. при ошибке БД удаляет загруженные в рамках запроса S3-объекты.

Вызов алгоритма пока отмечен `TODO` сразу после успешного commit. До его
подключения ответ имеет статус `imported` и содержит `upload_id` и счётчики по
каждому округу.

## Репозитории (`src/core/db/repositories/`)

- `DataUploadRepository` создаёт выгрузку округа;
- `UploadedFileRepository` сохраняет метаданные оригиналов из S3;
- `RequestRepository` проверяет повторные внешние номера и добавляет заявки;
- `EngineerRepository` добавляет инженеров вместе с навыками.

Все четыре доступны только через `UnitOfWork`.

## Внешние интеграции

`src/core/geocoding/` — интеграция с Nominatim: `client.py` содержит только
HTTP-соединение, `service.py` — поиск координат, нормализацию адресов, кэш и
ограничение частоты запросов. URL сервиса, User-Agent, таймаут и интервал
настраиваются секцией `geocoding`.

## DI-провайдеры (`src/core/di/`)

- `DbProvider` — engine, session maker, сессия и UoW;
- `S3Provider` — S3-клиент и хранилище;
- `GeocodingProvider` — HTTP-сессия, клиент и сервис геокодирования;
- `PlanningProvider` — request-scoped `PlanningService`.
