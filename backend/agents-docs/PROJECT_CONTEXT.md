# PROJECT_CONTEXT.md

Актуальная техническая карта backend. Здесь описано, что реально существует
в коде и какие части не завершены. Нормы размещения и стиля задают
[ARCHITECTURE.md](./ARCHITECTURE.md) и [CODE_STYLE.md](./CODE_STYLE.md), а
процесс структурных изменений — [REFACTORING.md](./REFACTORING.md).

Этот файл обновляется при добавлении/удалении endpoint, модели, репозитория,
DI-провайдера, внешней подсистемы или фонового процесса. Он не должен
оправдывать нарушение архитектуры: фактический техдолг описывается как
техдолг, а не превращается в правило.

## HTTP API

Корневой prefix — `/api`. Реализованы домены:

| Домен | Контракт | Назначение |
|---|---|---|
| planning | `POST /api/planning/initial` | multipart-импорт пар книг округов (`mode`, `strategy` в форме), нормализация, геокодирование, сохранение, initial и baseline |
| planning | `POST /api/planning/replan` | пересчёт одного или нескольких округов; `mode`/`strategy` по умолчанию наследуются от рабочего плана |
| planning | `POST /api/planning/events` | одно внештатное событие округа и связанный pending event plan одной транзакцией |
| plans | `GET /api/plans/current`, `GET /api/plans`, `GET /api/plans/{plan_id}` | текущий план, история шапок, детальное представление с диффом |
| plans | `POST /api/plans/{plan_id}/approve`, `POST /api/plans/{plan_id}/reject` | решение диспетчера; для event plan — согласованно с событием |
| plans | `GET /api/plans/{plan_id}/export` | XLSX любого плана через временную ссылку S3 |
| requests | `GET /api/requests/{request_id}`, `PATCH /api/requests/{request_id}/status` | карточка заявки и ручная смена статуса (отмена — только событием) |
| engineers | `GET /api/engineers/{engineer_id}` | карточка инженера |
| reports | `GET /api/reports/daily` | ZIP с PDF по каждому округу и `summary.pdf` через временную ссылку S3 |

Служебные endpoint вне `/api`: health/ping и Prometheus metrics.

Домены plans и reports строят составные read-model через presenter; requests/engineers —
простой read-only CRUD плюс смена статуса заявки.

## Жизненный цикл планирования

Три вида планов (`PlanKind`): `initial`, `replan`, `event_replan`. План хранит режим
(`DistributionMode`) и стратегию (`PlanStrategy`) расчёта. Статусы `pending/approved/rejected`;
рабочий план — последний approved округа за день; утверждение отклоняет остальные pending.

### Initial

1. валидирует набор и размер файлов, определяет роль книги по колонкам и округ по
   содержимому; книга не за текущий рабочий день отклоняется до внешних вызовов;
2. парсит книги, вычисляет норматив, приоритет, навык и транспортные ограничения;
3. параллельно геокодирует адреса; ненайденный адрес заявки не роняет округ (заявка
   сохраняется неназначенной с причиной `no_route`), бригада без адреса стартует из офиса,
   ненайденный офис — ошибка округа;
4. сохраняет оригиналы в S3 и нормализованные данные в PostgreSQL, при DB-сбое компенсирует
   S3-объекты;
5. фиксирует cutoff, получает у алгоритма запросы матриц, строит их провайдером, считает
   initial выбранной стратегией и baseline, одной транзакцией сохраняет pending `Plan`,
   остановки, неназначенные заявки и `BaselineResult`.

Округа независимы (partial success). После утверждённого initial повторная загрузка округа
за день запрещена; initial утверждается в пределах `approval_ttl_minutes`.

### Replan

Строится от текущего approved округа: фиксирует cutoff, передаёт алгоритму утверждённый план
со статусами заявок, доступностью инженеров, cutoff утверждённого initial и фактами
утверждённых событий дня (время поступления срочных заявок, время возвращения инженеров);
сохраняет полный план дня с `is_locked`-историей. Поздний approve запрещён, если изменённая
кандидатом остановка уже началась или база перестала быть current.

### Event replan

Типы: `urgent_request`, `request_cancelled`, `engineer_unavailable`, `engineer_available`.
Backend валидирует переход по утверждённой цепочке событий (нельзя отменить отменённую или
начатую заявку, повторно выбыть/вернуться, повторить срочную заявку по внешнему ID), один
pending event на округ и день; создаёт событие (и срочную заявку) и передаёт алгоритму
`ReplanEvent`. Событие и план сохраняются или откатываются вместе. Approve применяет
изменение состояния (статус заявки, доступность инженера, сброс «в пути» у заявок, снятых с
выбывшего инженера); reject отклоняет событие без изменения состояния.

Бизнес-оркестрация принадлежит API-домену planning. Алгоритм, геокодер, матрицы и S3 —
независимые core-подсистемы, передаваемые через DI.

## Алгоритмическая подсистема

`AlgorithmService` — чистое вычислительное ядро без БД, HTTP, часов и commit. Методы:

- `prepare_initial` / `build_initial_input` / `plan_initial` / `plan_baseline` /
  `plan_initial_diagnosed`;
- `prepare_replan` / `prepare_event_replan` / `build_replan_input` / `plan_replan`.

Стратегии: `lns` (по умолчанию в API), `layered_graph`, `greedy`, `baseline` (только для
сравнения). Внутри: нормализация окон и SLA аварий, послойные матрицы, точная фаза аварий,
материализация с округлением пробега до 0,01 км, фиксация истории replan, применение
события, страховка «не хуже текущего плана», независимый аудит initial/replan/события.
Версии реализаций — `*-v3`. Контракт и правила — `docs/user-case/ALGORITHM.md`, исследования —
`docs/algorithm/`.

## Внешние подсистемы

| Подсистема | Роль |
|---|---|
| s3 | хранение оригиналов загрузок и временных экспортов (XLSX, ZIP отчёта), presigned URL, lifecycle префикса экспортов |
| geocoding | DaData: адрес → координаты дома, нормализатор адреса, кэш и ограничение параллельности |
| routing | OSRM Table API: матрицы «все со всеми» по профилям car/foot/bike, общественный транспорт оценкой по расстоянию и ожиданию |
| dgis | 2ГИС Distance Matrix: матрица на запрос с прогнозом пробок, лимиты 10×10 и повтор при rate limit |
| travel_matrix | единая точка получения матриц для алгоритма; провайдер выбирается `cfg.travel_matrix.provider` (`osrm`/`dgis`) |
| algorithm | распределение заявок и построение маршрутов без HTTP-зависимостей |

Внешний client отвечает за соединение/сырой протокол, service подсистемы —
за полезную операцию и преобразование ошибок. API-домен переводит ошибку
core-подсистемы в собственную HTTP-интерпретацию.

## DB-модели

| Модель | Назначение |
|---|---|
| DataUpload | факт загрузки одного округа |
| UploadedFile | метаданные оригинального файла в S3 |
| Request | нормализованная заявка (из загрузки или срочная без upload), статус диспетчера |
| Engineer | инженер, смена, старт, транспорт, текущая доступность |
| EngineerSkill | нормализованная связь инженер ↔ навык |
| ReplanningEvent | внештатное событие со статусом, согласованным с его планом |
| Plan | версия результата по округу: вид, статус, режим, стратегия, cutoff, база, событие, агрегаты |
| PlanEngineerState | доступность инженера, зафиксированная в конкретном плане |
| BaselineResult | метрики baseline, связь 1:1 с initial-планом; не план и без lifecycle |
| PlanStop | назначенная заявка и замороженные параметры остановки, `is_locked` |
| PlanUnassignedRequest | неназначенная заявка и причина (включая `no_route`) |

На каждую хранимую сущность есть собственный repository; доступ сервисов к
репозиториям идёт только через UnitOfWork. Семантика и constraints моделей описаны в
`docs/user-case/BACKEND.md` (§3) и в docstring самих моделей. Последняя миграция — `1e820cf38929` (режим и стратегия плана),
перед ней `efec47031ffb` (значение `NO_ROUTE`).

## DTO и схемы

- DB DTO — frozen dataclass-проекции ORM на границе хранения.
- API/core DTO — frozen dataclass-контракты конкретного сервиса/подсистемы,
  не наследуют DB DTO и не зависят от SQLAlchemy.
- Pydantic schemas — только HTTP-контракт router'а.

ORM-модели не являются response model. Pydantic-схемы не проходят в service
и repository. Сложное представление ответа собирается presenter'ом, а не
Pydantic validator'ом и не repository.

## DI

Зарегистрированы provider'ы для:

- БД/session/UoW;
- S3;
- геокодирования (DaData);
- маршрутизации OSRM;
- матриц 2ГИС;
- единого сервиса матриц `travel_matrix`;
- алгоритма;
- каждого API domain service (planning, plans, requests, engineers, reports).

Engine/session factory и долгоживущие клиенты имеют app scope; UoW/session и
доменные сервисы — request scope. Новая зависимость не создаётся вручную в
router/service и не достаётся из контейнера как service locator.

## Исключения

API-домен объявляет свои исключения в общем API exception package и
регистрирует HTTP-представление декоратором. Router не ловит бизнес-
исключения. Core-подсистема не импортирует API и поднимает собственные
технические/доменные исключения без HTTP-статуса.

## Наблюдаемость

- структурный JSON logging в stdout; логи httpx подняты до WARNING, чтобы адреса из
  запросов геокодера не попадали в INFO;
- request id через context variable и `X-Request-Id`;
- request logging middleware;
- Prometheus HTTP counters/histogram/gauge;
- Grafana/Loki/Promtail/cAdvisor в Compose.

Новые метрики живут в выделенном `metrics.py`, не в service/router.

## Проверки

- `make check` и unittest (`tests/`); E2E-наборы G02/T05/G03/T07/T08 требуют отдельной
  одноразовой мигрированной БД `*_test_*` в переменной `<ID>_TEST_DATABASE_URL` и без неё
  пропускаются.
- Полный HTTP-прогон рабочего дня (initial → replan → все события → Excel → дневной PDF)
  выполнен на реальном DaData и локальной матрице с подменёнными часами; реальные матрицы
  OSRM/2ГИС в полном прогоне не проверены.

## Известные незавершённые места

Известных нарушений нормативных архитектурных документов сейчас нет.
Функциональные/интеграционные незавершённости:

- Публичные серверы OSRM блокируют по трафику уже на одном initial крупного округа; для
  работы нужен собственный OSRM или провайдер `dgis`. Отказ OSRM по HTTP-статусу сейчас
  классифицируется как `invalid_routing_response`, хотя по смыслу это недоступность
  (`routing_unavailable`).
- Без `dgis.api_key` провайдер `dgis` недоступен; без `geocoding.api_key` не работает
  геокодирование.
- Replan фиксирует остановку по плановому началу или статусу (§7.2 user case); если инженер
  уже выехал, а статус «в пути» не выставлен, такая заявка может не поместиться в хвост.
- Отдельной причины «SLA аварии истёк» нет: такая авария получает `no_time_slot`.
- Проверка актуальности initial при утверждении — временная эвристика TTL
  (`approval_ttl_minutes`), точный критерий не согласован.
- Открытый выбор иерархии целей: «приоритет → покрытие» (код) против «аварии → покрытие →
  приоритет».
- Глобальный выбор маршрутов инженеров — эвристика: граф точен для одного инженера,
  общий оптимум округа не гарантируется.
- Каталог `src/core/services/` содержит только `__pycache__` и не является частью кода.

Эти пункты нельзя чинить попутно с несвязанным рефакторингом. Они либо входят
в явный scope задачи, либо остаются задокументированными.
