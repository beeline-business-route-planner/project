# PROJECT_CONTEXT.md

Актуальная техническая карта backend. Здесь описано, что реально существует
в коде и какие части не завершены. Нормы размещения и стиля задают
[ARCHITECTURE.md](./ARCHITECTURE.md) и [CODE_STYLE.md](./CODE_STYLE.md), а
процесс структурных изменений — [REFACTORING.md](./REFACTORING.md).

Этот файл обновляется при добавлении/удалении endpoint, модели, репозитория,
DI-провайдера, внешней подсистемы или фонового процесса. Он не должен
оправдывать нарушение архитектуры: фактический техдолг описывается как
техдолг, а не превращается в правило.

## HTTP API

Корневой prefix — `/api`. Реализованы домены:

| Домен | Контракт | Назначение |
|---|---|---|
| planning | `POST /api/planning/initial` | multipart-импорт пар файлов округов, нормализация, сохранение и первичное планирование |
| plans | `GET /api/plans/current`, `GET /api/plans`, `GET /api/plans/{plan_id}` | текущий план, история шапок и детальное представление плана |
| requests | `GET /api/requests/{request_id}` | полная plan-agnostic карточка заявки |
| engineers | `GET /api/engineers/{engineer_id}` | полная plan-agnostic карточка инженера |

Служебные endpoint вне `/api`: health/ping и Prometheus metrics.

Домены requests/engineers сейчас являются простым read-only CRUD. Домен
plans строит составной read-model из плана, заявок, инженеров, остановок и
неназначенных заявок; при его структурном изменении применяется граница
service/presenter из `ARCHITECTURE.md`.

## Первичное планирование

Вход — ненулевое чётное число `.xlsx`: для каждого округа ровно одна книга
с заявками и одна отдельная книга доступных инженеров. Книги в формате
«Синтетические данные» являются штатными реальными входными данными заявок.
Роль книги определяется по обязательным колонкам; исходное имя файла не
валидируется и не используется для классификации, дополнительные колонки
игнорируются. Округ определяется по содержимому книги.

Книги контрольного распределения входными данными не являются. Это только
справочные примеры ручного распределения заявок диспетчером; они не
соответствуют обязательной схеме книги инженеров и не используются backend.

Use-case:

1. валидирует набор и размер файлов;
2. парсит книги и нормализует заявки/инженеров;
3. вычисляет норматив, приоритет, навык и транспортные ограничения;
4. геокодирует адреса;
5. сохраняет оригиналы в S3 и нормализованные данные в PostgreSQL;
6. при DB-сбое компенсирует созданные в рамках запроса S3-объекты;
7. после успешного импорта для каждого округа фиксирует cutoff, получает у алгоритма
   список нужных матриц, запрашивает их у 2ГИС, считает initial и baseline и одной
   транзакцией сохраняет pending `Plan`, остановки, неназначенные заявки и `BaselineResult`.

Бизнес-оркестрация принадлежит API-домену planning. Алгоритм, геокодер,
2ГИС-матрицы и S3 — независимые core-подсистемы, передаваемые через DI.

## Алгоритмическая подсистема

Публичная точка входа — `AlgorithmService`, чистое вычислительное ядро без БД, HTTP,
часов и commit. Методы:

- `prepare_initial` — нормализует сырые заявки/инженеров (эффективные окна, SLA аварии,
  старт инженера не раньше cutoff) и возвращает запросы матриц по слоям и транспорту;
- `build_initial_input` — собирает вход расчёта из полученных матриц;
- `plan_initial` — варианты `layered_graph` (production), `layered_graph_alns`,
  `layered_graph_greedy`, `greedy`, `baseline`;
- `plan_baseline` — официальный baseline п. 2.3 ТЗ;
- `plan_initial_diagnosed` — неперсистентная диагностика.

Каждый результат проходит независимый аудит. Cutoff, запрос матриц 2ГИС и сохранение
`Plan`/`BaselineResult` выполняет API-домен planning. Детали — `docs/user-case/ALGORITHM.md`
и `docs/algorithm/`. Replan и event replan в алгоритмическом контракте пока не реализованы.

## Внешние подсистемы

| Подсистема | Роль |
|---|---|
| S3 | хранение оригиналов загрузок и будущих экспортов |
| geocoding | Nominatim: адрес → координаты, нормализация, rate limit и in-memory cache |
| routing | OSRM Table API — провайдер DI сохранён, в текущем расчёте не используется |
| dgis | 2ГИС Distance Matrix: матрицы времени/расстояния по слоям с учётом транспорта инженера (car/walking/bicycle/public_transport) и прогноза пробок; используется только для матриц алгоритма |
| algorithm | распределение заявок и построение маршрутов без HTTP-зависимостей |

Внешний client отвечает за соединение/сырой протокол, service подсистемы —
за полезную операцию и преобразование ошибок. API-домен переводит ошибку
core-подсистемы в собственную HTTP-интерпретацию.

## DB-модели

| Модель | Назначение |
|---|---|
| DataUpload | факт загрузки одного округа |
| UploadedFile | метаданные оригинального файла в S3 |
| Request | нормализованная заявка |
| Engineer | инженер, смена, старт и транспорт |
| EngineerSkill | нормализованная связь инженер ↔ навык |
| ReplanningEvent | событие будущего событийного перепланирования |
| Plan | версия результата по округу со статусом pending/approved/rejected |
| PlanEngineerState | доступность инженера, зафиксированная в конкретном плане |
| BaselineResult | метрики baseline для сравнения, связь 1:1 с initial-планом; не план и без lifecycle |
| PlanStop | назначенная заявка и замороженные параметры остановки |
| PlanUnassignedRequest | неназначенная заявка и причина |

На каждую хранимую сущность есть собственный repository; доступ сервисов к
репозиториям идёт только через UnitOfWork. Подробная семантика и constraints
описаны в `docs/DATABASE.md`.

## DTO и схемы

- DB DTO — frozen dataclass-проекции ORM на границе хранения.
- API/core DTO — frozen dataclass-контракты конкретного сервиса/подсистемы,
  не наследуют DB DTO и не зависят от SQLAlchemy.
- Pydantic schemas — только HTTP-контракт router'а.

ORM-модели не являются response model. Pydantic-схемы не проходят в service
и repository. Сложное представление ответа собирается presenter'ом, а не
Pydantic validator'ом и не repository.

## DI

Зарегистрированы provider'ы для:

- БД/session/UoW;
- S3;
- геокодирования;
- маршрутизации OSRM (не используется расчётом);
- матриц 2ГИС;
- алгоритма;
- каждого API domain service.

Engine/session factory и долгоживущие клиенты имеют app scope; UoW/session и
доменные сервисы — request scope. Новая зависимость не создаётся вручную в
router/service и не достаётся из контейнера как service locator.

## Исключения

API-домен объявляет свои исключения в общем API exception package и
регистрирует HTTP-представление декоратором. Router не ловит бизнес-
исключения. Core-подсистема не импортирует API и поднимает собственные
технические/доменные исключения без HTTP-статуса.

## Наблюдаемость

- структурный JSON logging в stdout;
- request id через context variable и `X-Request-Id`;
- request logging middleware;
- Prometheus HTTP counters/histogram/gauge;
- Grafana/Loki/Promtail/cAdvisor в Compose.

Новые метрики живут в выделенном `metrics.py`, не в service/router.

## Известные незавершённые места

Известных нарушений нормативных архитектурных документов сейчас нет.
Функциональные/интеграционные незавершённости:

- Для добавленных временных полей остановки требуется отдельная проверенная
  Alembic-миграция и применение к реальной БД.
- Полный HTTP-сценарий импорта с живыми PostgreSQL, S3, геокодером и
  2ГИС не подтверждён одним end-to-end прогоном.
- Недостижимая пара точек способна оборвать расчёт всего округа; семантика
  явной причины неназначения не утверждена.
- Replan и event replan не реализованы (A03–A04, T05, T07).
- Initial orchestration в `planning/service.py` — временный адаптер до T03: нет
  partial success, отката отдельного округа и запрета повторной загрузки после
  approved initial.
- Без `dgis.api_key` первичное планирование недоступно (ответ 503).
- Глобальный выбор маршрутов инженеров — эвристика: граф точен для одного инженера,
  но общий оптимум округа не гарантируется.

Эти пункты нельзя чинить попутно с несвязанным рефакторингом. Они либо входят
в явный scope задачи, либо остаются задокументированными.
