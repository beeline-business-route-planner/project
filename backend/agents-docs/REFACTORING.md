# REFACTORING.md

Обязательный процесс для нетривиального рефакторинга backend. Цель — менять
структуру без случайной смены поведения и не размазывать ответственность по
новым `helper`/`manager`/`common`-слоям.

Правила ниже применяются по масштабу задачи, но сами по себе не требуют
создания плана, рабочего журнала или отдельной папки документации. Если
пользователь хочет формальный план или журнал решений, он запрашивает это
отдельно.

## 1. Перед изменениями

1. Прочитать `RULES.md`, `ARCHITECTURE.md`, `CODE_STYLE.md` и актуальный
   раздел `PROJECT_CONTEXT.md`.
2. Проверить `git status` и `git diff`. Отделить исходные изменения
   пользователя от будущего diff задачи.
3. Найти всех вызывающих и все импорты изменяемых публичных символов через
   `rg`; не судить о назначении файла только по его имени.
4. Зафиксировать инварианты поведения:
   - публичные endpoint, методы и response/request формы;
   - типы и порядок элементов ответа, если порядок наблюдаем клиентом;
   - исключения и HTTP-статусы;
   - commit/rollback и внешние side effects;
   - логирование и метрики, на которые опирается эксплуатация.
5. Сформулировать ответственность «до» и «после» одним предложением на
   каждый затрагиваемый класс. Если новое назначение нельзя назвать без
   слов «разное», «общая логика», «хелперы» — декомпозиция не готова.

Формальный план составляется только по явной просьбе пользователя. Без неё
агент после анализа выполняет рефакторинг автономно в заданном scope. Если
обнаружен выбор, который существенно меняет контракт или границы задачи,
нужно запросить решение, а не создавать документ вместо вопроса.

## 2. Как выбрать место для кода

Для каждого фрагмента задавать вопросы строго по порядку:

1. Это HTTP-регистрация или schema ↔ DTO? → router/schemas.
2. Это бизнес use-case, I/O, UoW, транзакция или оркестрация зависимостей?
   → domain service.
3. Это детерминированная сборка сложного read-model из уже загруженных
   данных? → domain presenter.
4. Это разбор и форматная валидация сложного входного файла/текста? →
   domain parser.
5. Это переиспользуемая операция внешней/внутренней подсистемы? →
   `src/core/<system>/service.py`.
6. Это доступ к одной DB-модели? → repository этой модели.
7. Это ORM-независимая форма передачи данных? → подходящий `dto.py`.
8. Это закрытый словарь значений? → `enums.py`, не tuple/dict/ClassVar.
9. Это чистая операция над голыми значениями, используемая минимум в двух
   местах? → domain utils или `src/core/utils/` по границе использования.
10. Ничего не подошло? → оставить рядом как приватный метод отвечающего
   класса; не создавать `helpers.py` и не придумывать новый слой.

## 3. Декомпозиция класса

Класс делится по причине ответственности, а не по числу строк.

Сигналы, что ответственность смешана:

- класс одновременно делает I/O и форматирует сложный вложенный ответ;
- метод одновременно открывает транзакцию, вызывает внешний API и содержит
  самостоятельный алгоритм;
- большая часть метода — создание индексов/бакетов/проекций, не use-case;
- для работы появились `ClassVar`, справочники или настройки в сервисе;
- приватный метод нужен второму домену;
- тестирование чистой логики требует собирать UoW/HTTP-контекст.

Не являются самостоятельной причиной деления: большой файл, длинное имя,
желание «сделать красиво», один длинный comprehension или гипотетическое
будущее переиспользование.

После деления должен остаться один направленный поток зависимостей. Новые
классы не импортируют сервис обратно, не получают service locator/DI-
container и не обмениваются скрытым глобальным состоянием.

## 4. Реализация

- Сначала вводится новый тип/слой с узким контрактом, затем переводятся
  вызывающие места, затем удаляется старый код. Не держать две активные
  реализации одного правила.
- Не смешивать механический перенос и изменение поведения в одном шаге.
  Если поведение требуется изменить, это отдельный явно названный пункт.
- Не расширять публичный API ради удобства рефакторинга. Приватная деталь не
  становится публичной только потому, что переехала в новый файл.
- Не тащить ORM/Pydantic/FastAPI через границы, где достаточно DTO или
  простого типа.
- Не подавлять ruff/mypy, пока не доказано, что проблема в инструменте, а
  не в дизайне типов.
- Комментарий не компенсирует неверный слой. Если для объяснения
  расположения кода нужна простыня, код расположен неверно.

## 5. Проверка

Минимум для любого рефакторинга:

1. `make check`;
2. поиск старых импортов, имён и путей через `rg`;
3. проверка import/DI-сборки для затронутых provider'ов;
4. сравнение наблюдаемого контракта с инвариантами из раздела 1;
5. просмотр полного diff только по файлам задачи;
6. обновление `PROJECT_CONTEXT.md`, если изменились слой, публичный класс,
   endpoint, provider, модель или процесс.

Отсутствие pytest означает, что нельзя писать «всё протестировано» после
одного `make check`. В финале точно разделять статические проверки, smoke-
проверку и реальный интеграционный прогон с PostgreSQL/S3/API.

## 6. Definition of Done

- у каждого изменённого класса одна формулируемая ответственность;
- направление импортов соответствует `ARCHITECTURE.md`;
- в behavior-файлах нет новых module-level данных и сервисных `ClassVar`;
- нет новых `helper`/`manager`/`common`/бесхозных `constants`;
- поведение либо сохранено, либо каждое изменение согласовано;
- проверки выполнены и описаны без преувеличения;
- агентская карта не врёт о новой структуре;
- несвязанный пользовательский diff не затронут.
