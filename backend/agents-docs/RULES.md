# RULES.md

Жёсткие ограничения для работы с backend. Это не рекомендации по стилю:
без явной просьбы пользователя в текущей задаче агент не выполняет
перечисленные действия, даже если они кажутся удобным продолжением работы.

## База данных и миграции

- Не редактировать существующую миграцию, если она могла быть применена или
  отправлена другим разработчикам. Изменение схемы оформляется новой
  миграцией. Править старую можно только после подтверждения, что она нигде
  не применялась.
- Не выполнять `DROP`, `TRUNCATE`, массовые `DELETE`/`UPDATE`, downgrade с
  потерей данных и другие деструктивные операции на общей/реальной БД без
  отдельного явного подтверждения конкретной команды и цели.
- Не писать фиктивную миграцию руками вместо штатной автогенерации, если
  проект требует подключения к PostgreSQL. Если БД недоступна — подготовить
  модели, описать оставшийся шаг и не выдавать схему за применённую.
- Автогенерированную миграцию всегда читать целиком: проверять upgrade,
  downgrade, enum-типы, nullable/default, индексы, constraints и отсутствие
  случайного удаления чужих объектов.
- Не добавлять тестовую инфраструктуру или in-memory замену PostgreSQL
  «заодно». В проекте пока нет pytest; его подключение — отдельное решение.

## Внешние системы и side effects

- Не загружать и не удалять реальные объекты S3, не запускать массовое
  геокодирование/маршрутизацию и не отправлять данные во внешние API ради
  проверки рефакторинга без явного разрешения.
- Диагностический одиночный вызов внешнего API также требует понимания,
  какие данные уходят наружу, есть ли стоимость/rate limit и не содержит ли
  запрос пользовательские данные.
- Не принимать внешний side effect за часть транзакции PostgreSQL. Порядок
  действий, идемпотентность и компенсация частичного сбоя проектируются
  явно в сервисе use-case.

## Секреты и пользовательские данные

- Не читать и не выводить содержимое `.env`, рабочего `config.toml`, ключи,
  токены, пароли и connection strings. Для структуры использовать example-
  файлы и типизированный config-код.
- Не коммитить секреты и не вставлять в документацию правдоподобные
  секреты. Примеры должны быть явно фиктивными.
- Не логировать сырые строки загруженных таблиц, полные адреса и содержимое
  файлов на `info`/`error`. В логах — идентификаторы, количество записей,
  округ, тип операции и безопасные агрегаты.

## Зависимости и инфраструктура

- Не менять версии в `pyproject.toml`/`uv.lock`, Docker Compose, порты,
  volumes, monitoring и CI попутно с доменной задачей. Это отдельный scope,
  если пользователь прямо не включил его в задачу.
- Не вводить новую библиотеку, если задача решается стандартной библиотекой
  или уже установленной зависимостью без существенного ухудшения решения.
- Не создавать новый инфраструктурный сервис, очередь, кэш или фоновый
  процесс на основании предположения. Сначала требуется отдельное
  архитектурное решение.

## Границы задачи

- Рефакторинг не меняет HTTP-контракт, бизнес-правила, порядок транзакций и
  side effects, если изменение поведения не согласовано отдельно.
- Найденный посторонний баг не чинится молча. Он сообщается пользователю;
  правка выполняется только если входит в согласованный scope.
- Существующий незакоммиченный diff принадлежит пользователю. Не откатывать,
  не переформатировать и не переписывать несвязанные изменения.
- Не создавать абстракцию «на будущее». Новый файл/класс/слой должен иметь
  текущего владельца, текущего вызывающего и сформулированную обязанность.
