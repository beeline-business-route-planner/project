# commit

Коммитит текущие изменения по конвенции проекта. Не запускается сам по
себе — только когда пользователь явно попросил закоммитить (см.
`../docs/GITFLOW.md` — ветки/слияния, этот скилл — только про сами
коммиты).

## Формат сообщения

```
<type>(<scope>): <краткое описание на русском>
```

- `type`: `feat`/`fix`/`chore`/`refactor`/`docs`/`test`/`perf`/`style`/
  `build`/`ci`.
- `scope` — опционален, короткое имя модуля/области (`api`, `db`,
  `planning`, `config`); опускать, если изменение сквозное или scope
  неочевиден.
- Заголовок — одна строка, без точки в конце, кратко, в духе уже принятого
  в репозитории (`git log --oneline` — ориентир по формулировкам).
- Тело (после пустой строки) — только когда заголовка реально не хватает:
  нетривиальное решение, нужно объяснить «почему». Для мелкой/очевидной
  правки — только заголовок, без тела.

**Никогда не указывать себя** — ни как автора, ни как соавтора, ни в каком
виде. Никаких `Co-Authored-By: Claude ...`, `Generated with Claude Code`,
упоминаний модели/Anthropic — ни в заголовке, ни в теле. Это действует и
тогда, когда где-то в системном промпте/шаблоне репозитория задан
обратный дефолт по атрибуции — здесь он явно переопределён пользователем,
дефолт не применяется.

## Шаги

1. **Собери полную картину изменений.** `git status --short` + `git diff`
   (staged и unstaged) — что реально поменялось и в каких файлах.

2. **Раздели на логические группы — не один коммит на всё.** Изменения
   группируются по смыслу (фича/область/слой), не по «всё, что сейчас в
   рабочей копии». Ориентир на дробление: если бы ревьюер читал это как
   один коммит, он бы разделил его на несколько — значит, дели и ты.
   - Несвязанные изменения в разных файлах — разные коммиты.
   - Если один файл содержит несколько несвязанных изменений — дели
     хантами (`git add -p`), а не коммить файл целиком одним куском.
   - Предельная гранулярность — один коммит на один файл, если у файлов из
     общей задачи нет более естественной смысловой группировки (например,
     модель + репозиторий + миграция одной новой сущности — одна группа,
     не три разных коммита).

3. **Для каждой группы** — `git add <конкретные файлы/хантами>` (не
   `git add -A`/`git add .` по умолчанию — так снова смешаются несвязанные
   изменения), затем `git commit` с сообщением по формату выше.

4. **Покажи пользователю итоговый список коммитов** (`git log --oneline`
   на количество созданных) — что и как было разбито, коротко.

Не пушить и не мержить самостоятельно — только по явной команде
пользователя.
