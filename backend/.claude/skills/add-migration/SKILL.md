# add-migration

Создаёт alembic-миграцию для backend'а через `make migrate MSG="..."`
(`uv run alembic revision --autogenerate -m "$(MSG)"`), но не запускает её
вслепую — проверяет head'ы и содержимое до применения.

`alembic/versions/` сейчас пуст — доменных моделей ещё нет, единого
соглашения об именовании ревизий (домен-префикс и т.п.) в проекте пока не
сложилось. Если к моменту вызова этого скилла в `alembic/versions/` уже
есть файлы с явным паттерном именования (домен-префикс + номер) — следуй
ему по аналогии, не выдумывай новый молча. Если паттерна ещё нет — просто
дай автогенерируемое имя ревизии осмысленным (`-m` с коротким описанием
на английском, снейк-кейсом), не придумывай префиксную схему сам без
согласования с пользователем.

## Шаги

1. **Проверь модель.** Новая/изменённая SQLAlchemy-модель в
   `src/core/db/models/` обязательно импортирована в
   `src/core/db/models/__init__.py` — иначе Alembic autogenerate её не
   увидит (см. `ARCHITECTURE.md`).

2. **Проверь текущий head(ы).** Пройдись по файлам в `alembic/versions/`,
   собери пары `revision`/`down_revision`, найди revision id, на который
   никто не ссылается как на `down_revision` — это текущий head.
   - **Head один** (или файлов ещё нет) — новая миграция ставится поверх
     него как обычно.
   - **Head'ов несколько** (параллельная разработка в разных ветках) — не
     выбирай один из них произвольно. Спроси пользователя: смержить головы
     отдельной merge-миграцией (`down_revision: tuple[str, ...]` из обеих
     head-ревизий) или он сам знает, какая ветка сейчас актуальна.

3. **Сгенерируй миграцию**: `make migrate MSG="<короткое описание>"`.
   Открой сгенерированный файл в `alembic/versions/` и проверь руками —
   autogenerate не идеален, особенно для индексов/constraint'ов (см.
   `ARCHITECTURE.md`, раздел «Миграции»): убедись, что `upgrade()`
   действительно создаёт то, что нужно, и ничего лишнего не удаляет/не
   переименовывает по ошибке (autogenerate иногда путает rename колонки с
   drop+add).

4. **Проверь `downgrade()`.** Если откат теряет данные (например,
   `DROP COLUMN` после бэкофилла) — не пиши тихий деструктивный откат:
   `downgrade()` должен либо честно откатывать без потери данных, либо
   `raise NotImplementedError("...")` с комментарием почему.

5. **Не редактируй уже применённую (запушенную/смерженную) миграцию** —
   только новая миграция поверх. Правка существующего файла — лишь если
   пользователь явно подтвердил, что она точно нигде не накатана.

6. **Проверь применимость**: предложи пользователю прогнать `make upgrade`
   (и `make downgrade REV=<rev>` + `make upgrade` обратно, если откат
   реализован) на его локальной БД. Сам против общей/боевой БД миграции не
   накатывай без явной просьбы — деструктивные операции на реальной БД без
   пошагового подтверждения не выполняются.
